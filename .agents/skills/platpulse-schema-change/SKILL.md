# PlatPulse schema change

The Server has two Storage Backends with one logical schema (ADR 0013). The Agent is SQLite-only and versions its schema separately. Work through every item; the change is ready when each one is done or explicitly not applicable.

## Server migration pair

- [ ] Next version `N` = `SERVER_SCHEMA_VERSION` + 1 (`crates/platpulse-server/src/database/mod.rs`). Bump the constant.
- [ ] `crates/platpulse-server/migrations/NNNN_<name>.sql` (SQLite) and `crates/platpulse-server/migrations-postgres/NNNN_<name>.sql` (PostgreSQL) with the **same file name**. The PostgreSQL file's header says it is the counterpart of the SQLite one and names version `N`.
- [ ] Logical equivalence, item by item: tables; columns in the **same declaration order**; type class (SQLite `TEXT` ↔ `text COLLATE "C"`, `INTEGER` ↔ `BIGINT`, `REAL` ↔ `DOUBLE PRECISION`, `INTEGER PRIMARY KEY` ↔ `BIGINT GENERATED BY DEFAULT AS IDENTITY`); nullability; default present; primary key; every index (same name, columns, uniqueness, partial `WHERE`); foreign keys; the same number of CHECK constraints per table; triggers.
- [ ] CHECK expressions and default values are compared by hand: `tests/schema_equivalence.rs` counts CHECKs and only checks that a default exists. Read both files side by side for a weakened CHECK or a different default.
- [ ] A committed migration is never edited, deleted or renamed; fixes go in a new version. `scripts/check-frozen-migrations.py --base origin/main` enforces it in the repository checks.

## Data and code

- [ ] Backfills and data rewrites run in the migration on both backends and produce the same rows.
- [ ] New SQL follows the portable form in AGENTS.md (`$N` placeholders, `ON CONFLICT`, `RETURNING`, qualified `DO UPDATE SET` reads) and decodes through the `sqlx::Any` rules (`i64` flags, `Option<_>` for nullable columns, `database::NullableReal` for a nullable double).
- [ ] Storage Backend Migration (`storage_migration.rs`) copies tables by reading the source schema, so a new table needs no list entry; check that its row digest and the `tests/storage_migration_end_to_end.rs` fixture still cover it when the table holds data that must survive `storage migrate`.
- [ ] Backup/restore records the schema version; restoring a backup from version `N-1` must still be handled the way `restore.rs` documents.

## Agent migration

- [ ] `crates/platpulse-agent/migrations/NNNN_<name>.sql` and `AGENT_SCHEMA_VERSION` (`crates/platpulse-agent/src/database.rs`) + 1. No PostgreSQL counterpart.

## Verify

- [ ] `cargo test --workspace` on SQLite.
- [ ] `cargo test --workspace` on PostgreSQL (the platpulse-pre-push-checks skill has the commands); `schema_equivalence` only runs there and reports itself skipped without `PLATPULSE_TEST_POSTGRES_URL`.
- [ ] Upgrade path: an existing database at `N-1` migrates to `N` on both backends (the migration test suites open a pre-existing database).
- [ ] An externally visible change (new required config, data format, Agent–Server compatibility) is described in the pull request's Breaking change section.
