### 15.28 Home readings over the current list selection: the Node Selection Geo Aggregate (issue #233, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), on top of §15.23 (the search, the Health and Validator status filters and the ordinary Home URL), §15.24 (the card/list View control and the sort keys, nine of them since §15.31) and §15.27 (the toolbar entries):

- The attributable counters read the list selection. Active Nodes counts the matched Active Nodes, Healthy Nodes the matched Nodes whose Server-owned `health` is healthy, and Attention the remaining matched Nodes including Unknown. (The fourth counter this issue delivered, Networks — the Public Network groups that still hold a matched Node — was replaced by the selection-independent Balance in §15.37, issue #246.) While nothing narrows the list the two Node sets are equal and every figure is the reading Home has always shown; a narrowed list is a narrower reading of the same Server values, never a client-side recomputation of them.
- The two cumulative cards keep the Network selection, and say so. `Cumulative blocks` and `Cumulative rewards` are Cross-Network Validator Overview totals the Server publishes per Network over already-deduplicated Network summaries; a Node filter must not re-sum them onto a subset of Nodes, so they keep the whole Network selection and each draws its scope note (`data-slot="validator-overview-note"`, `Whole Network selection, never the filtered list`) in its caption and in its Breakdown as soon as a filter makes the difference visible (platpulse-web/src/components/ValidatorTotals.tsx). The note's copy is revised by §15.36 (issue #245).
- The map reads the same selection through a Node Selection Geo Aggregate. The whole map reading — the country fills, the screen-reader country list, the corner chip and the Known/Unknown/Unknown-reason counts — is summed in the browser over exactly the matched Nodes' own compact buckets (`homeNodeSelectionGeoOverview`, platpulse-web/src/homeGeo.ts); while nothing is narrowed the map keeps the Network-level Geo Insight, field for field. The browser only sums Server facts: it never parses a country, never deduplicates by IP or Peer identity, never derives an Unknown by subtraction, and never invents a count for a Node whose bucket is absent.
- No new request, route or query parameter. Each listed Node in the one `GET /api/public/v1/networks` response carries a compact `peerCountries` bucket — Available Peer records, the Known and Unknown country counts, the two Unknown reasons, and the per-country counts with their Server representative points — instead of a full `PublicGeoInsight`; the Network-level `geo` field, its shape and the request itself are unchanged. On the Server both readings are computed from one batch of per-Node rows (`PublicGeoReadings::load` and its `load_node_geo` batch, crates/platpulse-server/src/http/public.rs), so a Network reading is exactly the sum of its Active Nodes' buckets and the per-Network repeat read the earlier implementation ran is gone. That batch is restricted to exactly the Nodes the same response lists, each with its Network (`PublicGeoReadings::restrict_to_listed_nodes`), because the listed rows and the Geo rows are two reads: a Node activated between them must not enter a Network reading without a listed bucket of its own, and a listed Node the Geo read lost keeps its place in that Network's denominator without a reading of its own, so such a Network can only read `partial`.
- Provider state stays Network-level. `state`, `attribution`, `errorReason`, `lastGoodAt`, `staleSince` and `databaseAgeSeconds` describe the provider and its database, which a list filter cannot make fresh or stale, so they read from the Networks the selection lands in and never from a sum of per-Node values. Visible staleness still follows the selection through each summed country's `staleCount`, and Peer collection freshness follows the selected Nodes the map reads, mirroring the Server's own per-Node aggregation (`PublicNode.peers.freshness`): one selected Node therefore reads exactly as that Node's Detail page and never as the Network-set `mixed` Home's own reading uses.
- A Node the Server never observed contributes no count instead of a zero, at its own scope and therefore in every aggregate over it: a Node whose bucket carries no Known/Unknown denominator leaves the aggregate without a basis for that Node, exactly as its own Node Detail map reports `unobserved`. Never-observed Nodes are not "unknown countries" and are never rendered as 0.
- A selection no Node matches is an empty reading, not a failure, and the whole band says so. The four counters that follow the list read no figure at all — `No match` (`SummaryCard`'s `emptyLabel`, platpulse-web/src/components/HomeDashboard.tsx) instead of a zero, and with no failure tone — while the list states the same thing in its own words under an empty grid (its own count line is removed by §15.35), the map states `No Active Nodes match these filters` with `data-scope-basis="node-selection"` (platpulse-web/src/components/GeoWorldMap.tsx) and draws no country list and no chip, and the two cumulative cards keep the Network selection's totals and their scope note. Without a projection the counters keep reading `Unknown`, which is a different statement from "no Node matches"; nothing in the band adopts failure styling or a fabricated zero.
- The basis is stated on the region. `GeoWorldMap` writes `data-scope-basis="network" | "node-selection"` on its own region and the two cumulative cards carry their scope note, so a reader, a test or a screenshot can tell which selection a reading stands on. Everything else — the routes, the six URL parameters, the sort keys, the card/list views, the empty states, the last-good semantics and the mobile contract — is unchanged.
- Acceptance. The equivalence of the two readings is held on both sides: crates/platpulse-server/src/http/public.rs asserts that a Network's Geo reading equals the sum of its Active Nodes' buckets and that listed Nodes carry compact buckets instead of a full insight, and platpulse-web/src/homeGeo.test.ts asserts that a selection holding exactly one Node reads, field for field, what that Node's Detail page reads. The narrowing itself is held by platpulse-web/src/components/HomeDashboard.test.tsx (the basis attribute, the four counters, the cumulative note and the empty state), platpulse-web/src/components/GeoWorldMap.test.tsx (the basis attribute and the empty arm's copy) and the two Home e2e specs (platpulse-web/e2e/home-search-filters.spec.ts and platpulse-web/e2e/home-geo-map.spec.ts). The decision record is [ADR 0010](../../adr/0010-home-list-selection-geo-aggregate.md).

### 15.30 Home toolbar search: the row's own compact field, and the entry that opens it (issue #241, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), on top of §15.23 (which owns the search itself, the Health and Validator status filters and the ordinary Home URL), §15.24 (the card/list View control and the sort keys, nine of them since §15.31) and §15.27 (the toolbar entries). It revises exactly one thing in §15.27 — the search is no longer only an entry — and leaves every other §15.23, §15.27 and §15.28 commitment in force.

- The search control is the row's own control in two shapes, and exactly one of them is displayed. Where the row has the room for one it is a compact field (`data-slot="home-search-field"` inside `data-slot="home-search-inline"`, platpulse-web/src/components/HomeToolbar.tsx) with its own `Clear search` action inside its own box, drawn while there is a word to clear and absent while the field is empty (§15.33); where it does not, the row keeps §15.27's accessibly named icon entry (`data-slot="home-search-trigger"` inside `data-slot="home-search-collapsed"`) whose surface holds that same field. The two shapes are one control: the same accessible name (`Search Active Nodes`), the same placeholder, the same draft (`queryDraft`) and the same ordinary URL write, so a reader who crosses the width, closes the entry, re-opens it, or returns with Back finds the text, the filter and the state marker exactly where they left them. Nothing about a shape, and no open panel, ever enters the URL.
- The switch is the room the row has left, and CSS is the only thing that decides it. The search slot (`data-slot="home-search-slot"`, platpulse-web/src/components/HomeToolbar.tsx) is one flex item of a fixed 17rem (§15.33) that takes whatever the Network pills, the `Sort & filter` entry and the card/list View control leave over at their own widths — at least 44px, the entry's own width, so the shape it holds when the row is full is never an overflowing control — and it is the query container (`container-type: inline-size`, platpulse-web/src/styles/emerald.css). The rule is one `@container (min-width: 16rem)` rule, and 16rem is the least the slot must hold: the field's readable 13rem, its 44px `Clear search` action and the 4px between them, while the slot itself asks for one rem more (§15.33) so that the row's own room and this rule can never meet on the same pixel. The field is therefore displayed exactly where the row can hold a whole one beside the controls that are already there, and the choice follows the row's own content rather than a column count of the viewport: a 900px desktop whose Networks are lightly named keeps the field, while a 1440px row whose Network names fill the pills keeps the entry. The slot's own width never depends on what it holds (inline-size containment), so the answer cannot change with the shape it decides, and nothing else answers the same question: the component measures that room only to keep the reader's place across a resize (below), never to choose a shape, so there is no second source of truth for the same width to drift from this rule. The shape that is not displayed is `display: none`: it is not painted, not in the accessibility tree, not in the tab walk and not reachable by pointer, which is what "one search control at a time" has to mean for a keyboard reader. It stays in the DOM so the row's own room alone decides, and the shared `role="searchbox"` query every test uses still resolves to exactly one field.
- The field states its own condition. The row's field carries `data-search-state="on"` while the query is not blank, the accent border, and `aria-describedby="home-search-state"` pointing at the `sr-only` sentence `Search is on: <the query>`; that sentence now lives outside both shapes (a hidden shape must not hide the description of the shape that is displayed), and §15.27's drawn marker and described-by sentence stay on the entry for the shape that is behind a control. An active search is therefore discernible in words, in shape and in colour, in both shapes, and never only through hue.
- Escape never clears the reader's word. The field answers `Escape` itself (`preventDefault`, `onKeyDown` in the component): a browser's own action on a search field may revert its text, and Home's query is the reader's filter rather than something a retreat key gets to throw away. Where the field sits behind the entry, §15.27's surface still closes on `Escape` and hands focus back to that entry, with the word and the filter intact; in the field's own shape there is no surface to close, so `Escape` changes nothing at all — the reader keeps the field, the text and the narrowed list.
- Room is taken from no one. The shape the row displays is one fixed 17rem — the field is 13rem of text with its `Clear search` action inside its own box, a readable search box rather than a squeezed one — and the switch above is the 16rem floor, so a displayed field is never a partial version of itself, its text keeps the theme's own size instead of being shrunk to fit, and the Network pills are never the thing that pays for its room: where the row cannot hold a whole field beside them, the field is not displayed at all, which is the collapsed shape's whole purpose. A resize is read the same way, which is why narrowing a desktop window moves a reader from the field to the entry rather than shrinking either one.
- The walk changes with the shape, and only with the shape. Where the row holds its own field the delivered walk is the Network control (one tab stop; the arrow keys move between the pills) → the search field → its own `Clear search` while there is a word to clear → the `Sort & filter` entry → the card/list View control → the first filtered card; where the entry is what the toolbar shows, the walk is … → the search entry → the `Sort & filter` entry → the card/list View control → the first filtered card, and the field the entry opens joins the walk only while that surface is open. A shape change under the reader's hands keeps their place: the component measures the slot's room against that same 16rem (one ResizeObserver on the slot, HomeToolbar.tsx) and, only when the reader is inside the search control as that line is crossed, hands the keyboard to the shape that took over — to the field when the row has grown the room, closing the entry's surface as the field becomes the row's own control, so no surface stays open behind a shape that is not displayed, and to the entry when the field goes out of sight, still marked as the narrowed list the reading is. The word, the draft and the filter are never touched by any of it. Every other commitment of §15.23, §15.24, §15.27 and §15.28 is unchanged: the same trim-then-case-insensitive substring over the public Node display name, Node ID and Network display name; the same AND-combination with the Health and Validator status filters; `Clear search` clearing only the query while `Clear filters` still clears only the two status filters; the same ordinary URL, visible fallback, one-history-step-per-action, refresh/direct-link/back-forward and Node Detail return; the same matching and in-scope counts, empty states and selection-scoped counters and map. No request, route, query parameter, permission, Server behaviour or dataset changed.
- Acceptance. The switch itself belongs to the browser, so the browser owns it, and the component tests own the one-query contract both shapes share. platpulse-web/src/components/HomeDashboard.test.tsx names the shape it reads (`searchSlots`, `inlineField`, `collapsedField`) and holds the row's own field's accessible name, state, described-by sentence, draft sharing, `Escape`-keeps-the-word behaviour, query-only clear, and the focus handoff a resize needs (that one observer is driven by hand, because jsdom lays nothing out and has none). platpulse-web/e2e/home-toolbar.spec.ts works the expected shape out for itself from the row's own geometry — `searchRoom`: the row's width, minus the Network pills at their content width and the two other controls at the widths they are drawn, minus the gaps between them — and requires the displayed shape to match the room the stylesheet's 16rem is about, so a build that simply never displayed the field fails on a row that has the room; it then asserts one shape displayed and the other hidden, one exposed field, the same word in either shape, the field's full 13rem and the theme's text size, Network pills that were not the ones that paid, no horizontal overflow, and 44x44 targets in Light and Dark. The same file resizes a live page across the line in both directions (`crosses between its own field and the entry without losing the reader`): the reader types in the field the entry opened, the row grows the room, and the field takes the word, the keyboard and the described-by sentence while no surface is left open; narrowing again returns the marked entry with the word untouched. platpulse-web/e2e/home-search-filters.spec.ts walks the toolbar from the keyboard in whichever shape the room gives — the field and its `Clear search` as row stops, with `Escape` in the field keeping a word that is still in force so the walk goes on through the enabled `Clear search` to the filtered card, or the entry that opens the field and hands focus back on `Escape` — and reads the URL, history, empty-state, counters and map cases through the same helper. Every other Home spec that types into the search (`openHomeSearch`, platpulse-web/e2e/helpers.ts) keeps working in both shapes by construction, because the helper opens the entry only where there is one. Screenshots are review evidence, not a re-recorded baseline.

### 15.31 Home Disk, Uptime and Attention First stable sorts (issue #242, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), on top of §15.23 (the ordinary Home URL), §15.24 (the card/list View control and the Sort control) and §15.27 (the toolbar entries). It adds three keys to the one Sort control and revises nothing else: the six keys §15.24 delivered keep their key, their direction and their accessible name, `Health` stays the default, the top Attention count and the map keep reading the list selection exactly as §15.28 states, and no sort direction control is added.

- `HOME_SORTS` (platpulse-web/src/homeFilters.ts) now reads `['health', 'name', 'head', 'peers', 'process_cpu', 'process_memory', 'disk', 'uptime', 'attention']`. The three new keys are appended, so every existing `sort=` link still means what it meant and no delivered key moved; the Sort select (`sortOptions`, platpulse-web/src/components/HomeDashboard.tsx) offers the nine in that order as `Health`, `Name`, `Current Head`, `Peers`, `Process CPU`, `Process memory`, `Disk`, `Uptime` and `Attention First`, each key carrying its own direction, so the surface still holds no second control and no clickable column header invents one. `disk`, `uptime` and `attention` are ordinary values of Home's own `sort` parameter: refresh, bookmark, back/forward and direct navigation restore them with the rest of the link, and a value this deployment never published (`sort=disk_percent`) is refused exactly like any other — it falls back to `health` and names itself in §15.23's visible notice.
- `Disk` reads the Node data directory ratio and nothing else. `nodeDataRatio(node)` is `nodeDataProgress(node.nodeDataDirectorySizeBytes, node.nodeDataDirectoryCapacityBytes)` — the same platpulse-web/src/nodeData.ts call the Home card's Disk column and the Node Detail hero already make — so the order and the column can never disagree about which Nodes have a ratio at all, and a ratio that is missing from the order is missing from the column for the same reason. That shared helper is now the one place the two byte counts are validated, exactly as the Node Detail hero used to guard them before calling it: a size or a capacity that is absent, negative, non-finite, or a capacity that is non-positive yields no ratio, so every reader publishes `Unknown` instead of a number no reader could stand behind. `hostStoragePercent` is a different observation of a different subject and is never read here. The attested ratios rank descending, and a measured `0` — an empty data directory — is a value like any other.
- `Uptime` reads `processUptimeMs`, descending, under the same rule: a real `0` — a process that has just restarted — is a value, and a process the Server never observed is Unknown and sorts last.
- `Attention First` is its own order over the Server's `health` value: Unhealthy, then Unknown, then Healthy. It is `ATTENTION_SORT_ORDER` ranked by the one `healthRank` helper, which the delivered Health key reads as `HEALTH_SORT_ORDER` — one classification, `healthCategory`'s same three words the Health filter, the Health cell and the Health sort already read, arranged two ways. It reads nothing else, and nothing else can promote a Node in it: a Producing or Observing Activity, consensus membership, a resource percentage, a height lag or a `resyncing` process is not a health verdict and never becomes one here. Where §15.24's `health` key ranks Unhealthy → Healthy → Unknown, this one ranks Unhealthy → Unknown → Healthy: two readings of one Server value, neither rewriting the other. The default sort, the top Attention count (the matched Active Nodes whose health is not healthy, Unknown included) and the map's range are unchanged by the new keys, because none of them reads the order.
- One value rule covers every numeric key. A value the Server never attested (`null`/`undefined`) or published as something no browser can rank (a non-finite number, through `attestedValue`) is Unknown to the order and sorts last, while a measured zero keeps its place in the ranking; the six delivered metric keys read their values through the same helper, which changes no finite value they carry. `Disk` applies the rule twice on purpose: the shared ratio helper refuses byte counts that are not measurements, and the order still refuses a quotient it could not rank. Every key still ends on the same deterministic tie-break as every other key — the Node's displayed name and then its identity, exactly as §15.24 states it (§15.34) — so equal values never reorder between refetches and the same link always produces the same list whatever order the projection arrived in.
- The Compact list is untouched by all three keys: they sort the same matching collection the cards read — switching between the two views keeps the order and the filters — and the list gains no column, no pagination and no request, because a sort key is not a column. This ticket adds no route, no `PAGE-*`, no `PATTERN-*`, no `SCN-*`, no API, no DTO, no Server behaviour and no regenerated client: the three keys are Web-side ordering over fields the one Public projection already carries.
- Acceptance. The pure rules are held by platpulse-web/src/homeFilters.test.ts (34 cases; the six added here cover a Disk ranking measured against a Host storage percentage that disagrees on every Node, a real zero ratio, an uncomputable one and two byte counts no Server can attest, an Uptime ranking with a real zero and two values no browser can rank, the Attention order read beside the delivered Health order with every non-health signal overloaded on one Node, the whole Activity × health matrix ranked by health alone under both keys, and one order per key from four input permutations of the same set); the shared ratio those keys and the card both read is held by the new platpulse-web/src/nodeData.test.ts (a real zero, and every pair a capacity cannot divide). The surface is held by platpulse-web/src/components/HomeDashboard.test.tsx (`sorts by Disk, Uptime and Attention First through the one sort entry, in both views`: the nine options with no direction control, the three card orders, the Disk column read as the Node data ratio rather than the Host's percentage, and the list reading the same order). The browser acceptance is the new platpulse-web/e2e/home-sort-keys.spec.ts (2 cases at the five fixed viewports in Light and Dark over the production WebUI, a real Server HTTP surface and a temporary SQLite database): the three rankings over a projection the spec serves itself, read through the visible Sort entry, with the Disk reading taken from the card's own labelled resource region and the Host percentage proved absent from that card; every one of the nine keys read again in the Compact list, which the new keys give no column to; the new keys composed with the search and with the Health and Validator status filters over the narrowed selection; the invalid-value fallback; the keyboard, touch and 44px reachability of the entry in both themes with no horizontal overflow; and a `#242` key through a direct URL, a refresh, back/forward and a Node Detail return on the shared Server's convergence Network, where the two health keys rank the same six Nodes differently and the return puts the reader back on the Node they opened with the sort key they left in force. platpulse-web/e2e/home-list-view.spec.ts keeps §15.24's own six keys in force with the nine-key vocabulary in place.
