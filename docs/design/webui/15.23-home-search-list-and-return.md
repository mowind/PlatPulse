### 15.23 Home Node search, filters, and the ordinary Home URL (issue #222, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), the Active Node dashboard:

- The narrowing happens in the browser, over the one projection the Server already serves. `GET /api/public/v1/networks` (crates/platpulse-server/src/http/public.rs:2334 `public_networks`) takes no query parameter and answers with every Active Node of every Network in one response, so Home adds no search endpoint, no pagination and no second read. The pure seam is platpulse-web/src/homeFilters.ts with its unit tests platpulse-web/src/homeFilters.test.ts (27 cases with §15.24), the surface is platpulse-web/src/components/HomeDashboard.tsx, and the browser acceptance is platpulse-web/e2e/home-search-filters.spec.ts (10 cases at the 5 fixed viewports) over the production WebUI, a real Server HTTP surface and a temporary SQLite database.
- The search is a case-insensitive substring match over three public fields and nothing else: the Node display name, the Node ID, and the Network display name (`homeNodeSearchValues`, platpulse-web/src/homeFilters.ts). The needle and the haystack are trimmed and lowercased and the three values are joined before matching (`homeNodeMatchesQuery`), so a Node with no display name is still found by its Node ID, and a needle may span two of them (the Node name and its Network name) — the same behaviour as the existing Admin search (platpulse-web/src/validators.ts:326 `validatorMatchesQuery`), because Home and Admin are two surfaces of one product and must not disagree about what "search" means. Linked Validator identifiers or names, Host or Agent names, health reasons and identity reasons are never searched.
- The three filters are AND-combined with each other and with the search. Health reads the Server's own `health` value with the vocabulary `all`, `healthy`, `unhealthy`, `unknown`; Validator status reads `validator.currentValidatorStatus` with `all`, `validator`, `not_validator`, `unknown` (crates/platpulse-server/src/validator/status.rs `current_validator_status`) and the client maps nothing onto it: a Node with no Link is `unknown` and never `not_validator`, and Activity, Consensus membership or an absent Validator section cannot produce a Validator verdict. Unknown keeps its own filter instead of being folded into unhealthy.
- The Network selection scopes the reading. This bullet's original rule — the six summary cards, the Attention count, the cumulative cards and the Peer country map all keeping the whole Network selection — was revised by §15.28 (issue #233): the four attributable counters and the Peer map now read the narrowed list selection, while the two cumulative cards keep covering the whole Network selection and state that scope as soon as a filter makes the difference visible. The sort only reorders the list. Both numbers are stated: the result line (`data-slot="home-result-count"`, `role="status"`, `aria-live="polite"`) reads the one number it lists while nothing narrows it — `<n> nodes`, because `Showing <n> of <n>` under a summary band that already states the same number says it twice (§15.33) — and `Showing <matching> of <in-scope> nodes[ in <Network>].` once a search or a status filter narrows the list. An empty list says which case it is: an empty Network selection reads "No Active Nodes in this view." with "Retired Nodes are not listed on Home.", and a filtered-empty list reads "No Active Nodes match these filters." with "Clear the search or widen the filters to list all <in-scope> Active Nodes in this Network selection." Neither is rendered as a failure and neither invents a zero.
- The URL is ordinary and not a capability. `network`, `q`, `health`, `validator` and `sort` are read and written in that fixed order (`HOME_PARAMETERS`, platpulse-web/src/homeFilters.ts), each parameter's default value is omitted from the URL, and refresh, bookmark, back/forward and direct navigation restore exactly what the link carries. A Home link is explicitly not a protected sharing link and not an authorization token: it grants nothing and is never read as permission. The compact list view and the seven list columns are delivered as §15.24, and the nine sort keys as §15.24 and §15.31.
- A value this deployment cannot honour is reported, not obeyed. `readHomeFilters` validates each parameter against its own vocabulary — an unknown Network key is judged only once the projection is available, because `networks === null` means the projection has not loaded, so a selection stays provisional and is never called stale — drops a refused value to its default and names it to the reader in a visible notice (`data-slot="home-filter-notice"`, `role="status"`): `This Home link asked for Network "gone", health "critical" and sort "size", which this deployment does not offer, so they fell back to their defaults. The rest of the link was applied unchanged.` A load never rewrites the link; only a reader action does, so back and forward do not churn. One reader action is one history step: a Radix pill reports its value both when it takes the focus and when it is pressed, so a request for the URL the address bar already carries, or is already being asked for, is dropped instead of written twice and one Back step undoes exactly one action. An empty value counts as absent rather than as a refusal, and a parameter Home does not own (`to`) is left alone (`view` became Home's own parameter in §15.24).
- The toolbar holds the responsive and accessibility contract at 360x800, 390x844, 768x1024, 1280x800 and 1440x900 in Light and Dark: the Network pills scroll inside their own control rather than the page, the search field is a labelled `role="searchbox"` in whichever of its two shapes the toolbar shows it — the row's own compact field, or full width inside the surface the entry opens (§15.27, §15.30) — and one fixed track from sm, the Health, Validator status and sort selects keep their accessible names and 44x44 targets, focus stays visible (the field's own ring is its indicator) and the walk this section delivered — Network (one tab stop; the arrow keys move between the pills) → sort → search → Health → Validator status → the first filtered card — is the one §15.27 replaced rather than the one in force. §15.24 inserted the card/list View control as one more independent tab stop between the sort select and the search field, so the walk there was Network (one tab stop) → sort → view → search → Health → Validator status → the first filtered card, also superseded by §15.27. §15.27 then moves the sort, the search, the Health and the Validator status behind two entries and leaves the row's own stops exactly where they were: with both surfaces closed the delivered walk is Network (one tab stop; the arrow keys move between the pills) → the search control → the `Sort & filter` entry → the card/list View control → the first filtered card, and the selects are reached only inside the surface that is open, because a hidden control is not in the tab walk at all. §15.33 moved the search control to the stop right after the pills — the row's own field where the row has the room for one, and the entry that opens that same field where it does not — so the two entries and the View control follow the search instead of preceding it.
- The search field owns its own text while the reader types and hands it back to the URL on blur (`queryDraft`, platpulse-web/src/components/HomeToolbar.tsx; decoupled from `HomeDashboard.tsx` in #265): typing updates the local draft immediately and commits the URL with 150ms debounce and `replace: true` (flushing immediately on other filter interactions and clearing immediately on `Clear search`) so history does not grow per character and high-frequency typing does not churn the filter pipeline. The URL ends up with the same text; only fast typing is kept whole. The draft is dropped as soon as the address bar carries the same text, which is the frame after the commit a keystroke asked for, and whenever the URL changes from outside the field — a back/forward step or a pasted Home link — so the field shows the link the reader actually reached even while it still holds focus. Leaving the field is not itself such a change: a blur drops the draft only while the address bar already agrees with it, because reading the URL a frame early would empty the query for that frame and take the reader's own search, and the marks that state it, out from under the Tab pressed on the way out (§15.33).

### 15.24 Home compact cards and the seven-column list, with stable sort keys (issue #223, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), on top of §15.23:

- The reader chooses the Compact card view or the list view, and `view` joins the ordinary Home URL as one more parameter Home owns (`HOME_VIEWS = ['card', 'list']`). `card` is the default and is omitted from the URL like every other default value, so the six parameters are now read and written in the fixed order `network`, `q`, `health`, `validator`, `sort`, `view` (`HOME_PARAMETERS`, platpulse-web/src/homeFilters.ts). Refresh, bookmark, back/forward and direct navigation restore the view with the rest of the link, and a value this deployment cannot honour (`view=grid`) is refused exactly like a refused Network key or sort key: it falls back to the cards in place, names itself, and joins the same visible notice (`view "grid" … fell back to its default`). The pure seam and its unit tests are platpulse-web/src/homeFilters.test.ts (27 cases), the surface is `HomeNodeList` in platpulse-web/src/components/HomeDashboard.tsx, and the browser acceptance is platpulse-web/e2e/home-list-view.spec.ts (3 cases at the 5 fixed viewports) over the production WebUI, a real Server HTTP surface and a temporary SQLite database.
- The list carries seven public columns and nothing else: Node, Network, Health, Current Head, Peers, Process CPU and Process memory (`data-column="name|network|health|head|peers|process-cpu|process-memory"`). The column order is the one this ticket fixes, so the Network name sits between the Node name and its health. Every cell reads the same public field through the same formatter as the card (`homeNodeLabel`, `formatNumber`, `formatPeerCount`, `formatPercent`, `healthLabel`), which is why the list cannot disagree with the compact card: a Node with an authoritative empty peer set shows `0` in Peers, a Node the Server never observed shows `Unknown`, and the two are never interchanged. A Peer count that was observed once and then retained keeps its number and carries the list's half of the card's sentence under it — `peerRetentionCue`, `data-slot="node-list-peers-cue"`, e.g. `last good (collection error, freshness stale)` — so a retained snapshot is never read as a current one, while a fully current observation (an authoritative zero included) and a count the Server never attested carry no cue at all. Statements that belong to Node Detail or to the card's own identity entry rather than to a column — QC, Locked, Committed, Txs, Activity, the Linked Validator block, the Details and copy controls — get no column, and the table never opts into the stacked-card treatment that `table[data-stack]` gives the Admin tables.
- One sort control, stable keys. The single Sort select offers exactly the nine keys of `HOME_SORTS = ['health','name','head','peers','process_cpu','process_memory','disk','uptime','attention']` in that order (`Health`, `Name`, `Current Head`, `Peers`, `Process CPU`, `Process memory`, `Disk`, `Uptime`, `Attention First`; the snake_case keys follow the existing `not_validator` vocabulary), and no clickable column header invents a second way to sort. This ticket delivered the first six, which keep their key, their direction and their accessible name because §15.31 appends the last three; that section owns the Node data ratio `Disk`, the process `Uptime` and the `Attention First` order over the Server health value. The numeric metric sorts put every never-observed value last (`compareUnknownLast`): a `null` means the Server never attested a value, so it is neither a small number nor a zero, and the attested values rank descending. Health is graded by the same rule in the health vocabulary instead of in numbers: an unhealthy Node leads, a healthy Node follows, and a health Home can only read as Unknown sorts after both (the module-local `healthSortRank` over `healthCategory`, the same three words the Health filter and the Health cell already read). Attention still leads and no unattested health ever outranks an attested one, so the two families of sort keys differ only in how they spell "the Server never attested this". Every sort ends on one deterministic tie-break — the Node's displayed name ascending (`homeNodeLabel`), and the Node identity (`nodeId` ascending) only where two Nodes carry one name (§15.34) — so equal values never reorder between refetches, a run of equal values reads as a name list a reader can hunt in rather than as whatever order the identifiers happened to have, and the same link always produces the same list.
- On a narrow viewport the seven columns are wider than the page, so the table keeps its own minimum width (45.5rem, and 60.5rem from the sm breakpoint) inside one local scroller (`data-slot="node-list-scroll"`, `overflow-x-auto`) and the page keeps no horizontal overflow at 360x800 or 390x844. At 360x800 the three leading phone columns — Node 7rem, Network 6rem, Health 6.5rem, 312px of the 328px content box — are all inside the visible band of the list surface before any horizontal scrolling, so a reader on a phone learns the shown unit's health without touching the list; the table's own minimum width is the sum of its seven phone columns (45.5rem), and 60.5rem from the sm breakpoint. The Node name stays pinned to the left edge and its health parks beside it once the columns still to its right have slid under them: both cells are `position: sticky` with the health offset equal to the name column's width at every breakpoint, and both paint the same opaque `--background` the scroller paints — the reason the list uses that surface rather than the translucent card surface — so the identity and the health of every row stay readable at the far end of the list. The column widths and the sticky offsets are declared in one block in platpulse-web/src/styles/emerald.css precisely because the health offset must track the name width. Each row's Node name is one link with the same `homeNodeLabel` accessible name the card link carries, a 44x44 target and a visible focus ring; health is never reduced to a colour alone. At a phone width the toolbar row wraps instead of squeezing the pills: the Network pill row keeps the whole width of the surface on its own line and the sort control and the View control share the next one, so the delivered §15.23 pill behaviour is untouched and only the wrapping is new; the reading order and the row's own tab stops are unchanged, and §15.27 moves the sort control behind an entry without moving the entry's own place in them. The walk this section delivered gained the View control between the sort control and the search field: Network (one tab stop; the arrow keys move between the pills) → sort → view → search → Health → Validator status → the first filtered card. §15.27 then collapses the sort, the Health, the Validator status and the search behind two entries, so the delivered walk is Network (one tab stop) → the `Sort & filter` entry (sort, Health and Validator status inside its surface) → the View control → the Search entry (the search field inside its surface) → the first filtered card. Every other toolbar, focus, touch and local-scroll commitment of §15.23 holds unchanged.

### 15.25 Same-tab return to the Home reading and the Node it was left from (issue #224, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), on top of §15.23 and §15.24, and to the return links of `PAGE-HOME-NODE` (`/nodes/:nodeId`):

- The departure is neither a Home parameter nor a scroll offset: it rides in the tab's own react-router navigation state under the key `homeReturn` (`HOME_RETURN_STATE_KEY`, platpulse-web/src/homeReturn.ts), written by the two Node links of Home and read by the `Back to Home` links of the Node detail page (platpulse-web/src/pages/HomePages.tsx). Nothing about a reading position enters the URL: the arrival's address bar carries exactly the Home reading the reader left, in Home's own parameter order (`network`, `q`, `health`, `validator`, `sort`, `view`), and no offset, no place and no second position parameter is ever written to it. Navigation state is chosen over a URL ticket because it dies with the tab: a middle-click, a new tab, a copied link, another session or a later visit cannot inherit it. It is also refused to another document: the departure carries the reading token of the document that wrote it (`tab`, one `crypto.randomUUID()` per loaded document, `homeReturnTab()`), so a reload of the Node page, a new tab and a browser session the browser restored from disk are all a different document and are handed nothing. That is stated as the cost it is: reloading the Node page loses the return context, and the `Back to Home` links of that page then read as ordinary links to `/`. Browser-native history scroll restoration keeps owning Back and Forward; this return owns the one tab-local journey Home → Node Detail → Home.
- What the document remembers is small and closed: `HomeReturn { nodeId; search; position: { index; count } | null; tab }`, where the place is the 0-based index the Node held when the reader left (the state stores `index + 1`) and is `null` unless `0 <= index < count`, and `tab` is the reading token of the document that wrote the departure. `readHomeReturn(state, tab)` accepts it only when that token is this document's own and the Node ID matches `NODE_ID_PATTERN` (`/^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$/`), the search is a string no longer than `MAX_RETURN_SEARCH` (4096), which `homeReturnHref` reads back into Home's own vocabulary, and the place is a whole number in `1 <= index <= count`; a state that is not a departure at all (the login flow's `{ from, sessionExpired }`, an older deploy, a hand-written `history.state`) is refused whole, and a bad place drops only the place, so a wrong place can never displace the Node identity it travels with.
- The Node ID decides where the reader lands, and the place only decides the fallback. `landHomeReturn(scoped, matching, target)` looks the Node up by ID in the in-scope projection first and then in the filtered result, so a refetch that reordered the list changes the row's index and never the Node the reader is put back on — the whole point of remembering an identity beside a position instead of a pixel offset, which would land on whatever now happens to be at that offset. Three outcomes: the Node is in `matching` → no notice at all, the reader simply continues where they were; the Node is in `scoped` but not in `matching` → `filtered`, and the notice names the Node the way the reader reads Nodes, by display name; the Node is in neither → `missing`, and the notice names the Node ID it was left from. The fallback place is `homeReturnFallbackIndex(count, position) = min(position.index - 1, count - 1)`, `null` when there is no place and no list, so a list that shrank never leaves the reader on blank space and a search that matches nothing keeps §15.23's own empty statements instead of inventing a row.
- The notice is one sentence the reader can act on, in the Home filter notice's own audited tone: `<label> is no longer shown by these filters.` or `<label> is no longer in this view.`, followed by ` Showing the nearest matching Active Node instead.` or ` Showing the nearest Active Node instead.` It renders as `data-slot="home-return-notice"` with `role="status"` on the amber `bg-amber-400/10` surface with `text-amber-600 dark:text-amber-400`, in a `px-4 pt-4` wrapper beside `data-slot="home-filter-notice"`, so the two refusals of one link — a value this deployment does not offer and a Node it can no longer show — are both readable on the same paint. The notice is dropped the moment the reader asks for another reading (any toolbar action) and on a `popstate` takeover, so a sentence about a Node never sits over a view the reader has just changed.
- The departure is consumed exactly once. The first render that can place it re-writes the same URL with `setSearch(search, { replace: true, state: null })`: the address bar is unchanged, the departure is gone from the history entry, and no history step is added, so an arrival entry can never be re-inherited by a refresh or by back/forward and the URL the reader could copy carries no reading position. It is consumed only once the reading on screen is really the one the departure names: while a refetch of the Public reset that followed the departure is still in flight, the projection can still be the cached one, and a landing computed from it would put the reader beside a Node the fresh reading still holds. The departure and its search therefore wait in `pendingReturn` until the settled projection answers the search the URL carries, and the landing of a reading that is still being refetched is provisional. `landedReturn` holds the place the arrival reached together with whether it is still provisional (`{ index, notice, provisional }`, where `provisional` is the `refreshing` prop, `networks.isFetching` in the routed Home): the first landing places the reader in the reading on screen, and when the settled projection puts their Node somewhere else the arrival places them again — once, and silently, because a sentence here would say nothing the reader cannot see — while a Node the settled reading did not move is never re-placed and a live reorder the reader is watching never moves them at all. A toolbar action and a `popstate` takeover clear the pending departure, the landed place and the notice together (`finishReturn`), because nothing is owed to a reading the reader left by another door. The reveal itself runs once per arrival, through React callback refs keyed by Node ID (`Map<string, HTMLElement>` held in a ref, attached to `data-slot="node-list-row"` and `data-slot="node-card-frame"`) rather than by querying the DOM: the located row is scrolled with `scrollIntoView?.({ block: 'center' })` and the Node link inside it is focused with `{ preventScroll: true }`, so a keyboard reader continues from the row they returned to and a touch reader is not moved twice; a `null` ref, or a Home whose projection is not available yet, is handled without touching geometry.
- No scroll offset is stored anywhere — not in the URL, not in navigation state, not in `sessionStorage` — so a fresh, direct or bookmarked Home entry (a new tab, a typed URL, a link from anywhere else) renders exactly the reading its URL names and inherits no place of its own: one arrival has exactly one owner. A PUSH arrival at `/` that no departure of this document claims is moved to the top (`document.scrollingElement?.scrollTo({ top: 0 })`, platpulse-web/src/layouts/HomeLayout.tsx), while an arrival that is this document's own return is left where it is, so the reveal that places the reader on their Node is the only thing that moves them; the guard is the departure itself (`readHomeReturn(here.state, homeReturnTab()) !== null`) rather than the render order of two effects. The departure also cannot cross an identity change, and the boundary that catches one is the boundary that outlives every shell: `syncHomeReturnReader(reader)` runs in the authentication provider (platpulse-web/src/auth/AuthContext.tsx) with the reader as `role + ':' + userId`, or the authentication state itself — not in `HomeLayout`, because signing out and signing in as somebody else happens while no Home shell is mounted, so a rotation kept in Home would never see the reader change. The first reader a document observes adopts the token that document already holds, so a reader whose own identity is re-established (a session re-check republishing the same principal at a new authorization generation) keeps the entry they wrote; any other reader rotates the token, so a sign-out, a sign-in as another reader or an expiry starts from a Home with nothing inherited. A Public cache reset alone does not rotate it — republishing the projection does not change who is reading — so a reader who never signed out keeps their own departure through the reset a Purge triggers.
- The contract is held to the routed Public surface and never to private internals: the departure and the reveal are exercised through the Node links' `data-slot="node-link"`, the `homeNodeLabel` accessible names of the row and card links, the `role="status"` notices and the address bar. No React state, CSS class, private DOM attribute or hand-edited `history.state` is read by the acceptance, because the departure and the reveal are driven entirely through the links, the accessible names, the notices and the address bar. A story whose subject is the world changing under the reader is aged with a real Admin write — a Node rename through `PUT /api/admin/v1/nodes/{node_id}/metadata` — instead of by editing the history state react-router wrote. This ticket adds no schema, no endpoint, no DTO, no OpenAPI change and no regenerated client: where a reader was reading is browser-side navigation state the Server neither stores nor needs to observe, and the reading a return restores is still `GET /api/public/v1/networks` through the generated client of §15.23. The browser acceptance does write to the Server, through the Admin routes that already exist — it renames a Node and, on a Server of its own (§6), purges one, because a Purge is irreversible — and the reading it comes back to is that Server's own answer over the fixture database, not a private client cache.
- Acceptance. The pure seam and its unit tests are platpulse-web/src/homeReturn.test.ts (19 cases: building a departure, refusing a hand-written state, another document's departure and a rotated token, one token per reader with the first reader adopting the document's own, rebuilding the return link into Home's own vocabulary without writing a place to a URL, and the three landing outcomes with the notice copy) and the arrival behaviour in platpulse-web/src/components/HomeDashboard.test.tsx (`Public Home same-tab return`, 8 cases, including a place a reordered list has moved past, a Node the restored filters hide, a landing re-computed and re-noticed when the refetch settles without the Node, and a reader placed again when the settled reading has moved their Node); the reader boundary in platpulse-web/src/auth/AuthContext.test.tsx (1 case: the entry a reader wrote survives their own session re-check, and a sign-in as somebody else starts a new reading); the production-router round trip in platpulse-web/src/App.test.tsx (46 tests) follows the `Back to Home` link back to a bare Home and holds the two arrivals apart: a fresh arrival at Home gets the top of the page, the reader's own return does not. The browser acceptance is platpulse-web/e2e/home-return.spec.ts (10 cases) over the production WebUI, a real Server HTTP surface and a temporary SQLite database (§6), at the five fixed viewports: a list return whose address bar is exactly the departure reading with no place in it, a Node ID that wins over a place a rename has moved past (the rename is a real Admin write), a Node a restored filter now hides under the name it now has, a card-view return taken with the keyboard, a touch tap on the two touch projects, a reloaded Node page that has no reading to come back to, a fresh Home that inherits no reading position (`window.scrollY === 0`, no notice, no focused Node link), a fresh arrival at Home that starts at the top of the page, the Dark surface where the return notice and the filter notice are painted together in the same tone, and — on a disposable Server of its own, so it runs on one project — a Node really purged through `POST /api/admin/v1/nodes/{node_id}/purge`, after which the reader's return lands beside the row that took its place and says, by Node ID, that the Node is no longer in this view. Screenshots may be recorded as review evidence at that matrix and are never compared (ADR 0002).
- The Node detail breadcrumb was renamed from `All Networks` to `Back to Home` because it no longer leaves for an unfiltered Network list: it returns to the reading and the Node the reader left, and it carries the same departure as the error-branch and empty-branch links of that page. An arrival from anywhere else carries no departure, so those three links still read `/` and Home renders the bare reading its URL names.
