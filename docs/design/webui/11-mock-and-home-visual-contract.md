## 11.1 Accepted Home and Node Detail visual contract (Issues #75, #97, and #151)

The accepted direction from Issue #75 and the compact Home contract from Issue #97 remain the production structural baseline for the public Home surface. The visual layer adopts the supplied Emerald reference and the inspected Tokinx/komari-theme-emerald source at commit c2c5e88ea19c7cbe18d14a50414e10deca3cc66e, without importing its server, pricing, or remote-control data model.

### Visual language

- The shared theme foundation offers Auto, Light, and Dark (see "Theme behavior" below). Light uses a Slate-50-like canvas; Dark uses a coordinated near-#141923 slate canvas with the same restrained Emerald/Lime top atmosphere. Home, public Node Detail, and Login carry one shared top atmosphere: the Emerald default background at `c2c5e88ea19c7cbe18d14a50414e10deca3cc66e` ported faithfully in both themes — the full-viewport neutral base, the emerald/lime atmosphere with its `farthest-side` top radial mask at `opacity: 0.4`, and the low-contrast inclined SVG grid with the upstream `black/40` fill, `black/50` stroke and `mix-blend-overlay` treatment over four local filled cells, plus the Dark variants (`emerald/30`-`lime/30`, `white/2.5` fill, `white/5` stroke, vertical mask). The one deliberate deviation is width: the atmosphere spans the full viewport instead of the upstream fixed 1300px, so it never reads as a partial band on a wide viewport. The layer is decorative, pointer-inert, absent from the accessibility tree, shared rather than per-page, and fades before the lower reading surface. Admin retains the Emerald brand but uses the stable, undecorated workbench background in both themes as specified in §8.5; this exception does not change Home or Login.
- Public display cards follow Emerald default surfaces at `c2c5e88ea19c7cbe18d14a50414e10deca3cc66e`: borderless white in Light and `oklch(0.141 0.005 285.823)` in Dark, both at 60% opacity at rest, and Node Detail orders them into the three reading tiers defined in item 10 below. Home display cards retain their existing opaque-on-hover behavior on hover-capable devices; static Node Detail summary/observation/Validator performance/chart/disclosure surfaces keep their resting opacity on hover. Home Node cards explicitly opt into interactive-card feedback and alone gain the emerald-600/10 glow and 2px lift; statistics and detail/chart/disclosure cards have no decorative shadow or lift (statistics cards adopt Emerald's subtle muted auxiliary icon resting appearance and smooth hover highlight, with motion-reduce:transition-none). This does not change the page canvas, atmosphere, layout, internal separators, or semantic status colors. No custom background image or default `backdrop-filter` is introduced. Admin, Login, menus, forms, dialogs, and overlays retain their existing surfaces. Read-only Admin panels stay non-interactive: they use the static surface and gain no hover glow, lift, or opacity change (issue #199).
- Public Home and Node Detail use Emerald’s system font stack (`system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`), including navigation and controls. Card typography follows the corresponding Emerald heading, metric, and responsive detail tiers while retaining tabular numerals and overflow safeguards. No font binaries are copied or downloaded; Admin and Login retain Inter.
- Primary numbers and page titles use high contrast and strong weight. Secondary labels, timestamps, identifiers, and explanatory copy are quieter without being reduced below readable body sizes. Important values use tabular numerals where appropriate.
- Emerald is a measured brand accent and selection cue, not a replacement for every primary action. Neutral primary controls, blue chart series, amber warnings, red destructive/error states, and neutral Unknown/Unsupported states remain distinct. Emerald's coral `#FF6B6B` is authorized for the CPU and Process memory curves, and Inbound peer connections (matching Emerald's Connections TCP; deviations 31, 33 (f), and 35); red remains the destructive/error state colour and no status semantics ride on a chart series.
- Cards, pills, separators, fine 4px progress tracks, and focus states share one spacing and radius system. Clickable cards may use a 150–200ms hover lift of about 2px and a faint Emerald shadow only on hover-capable devices; static containers do not imply interactivity. Reduced motion removes the lift and non-essential transitions.
- The visual contract does not authorize fields that are absent from the Public Projection. Node Detail may show the monitored PlatON process CPU/memory, process start/uptime, last Agent report time, Node Data usage/capacity, and sampled Host network receive/transmit rates supplied by the Server; it does not add pricing, raw Peer identity, Host identity, or RPC Endpoint text.
- The default geometry is adapted from the Emerald repository's inline `Background.vue` SVG under its MIT license. Keep the copyright and license notice with the adaptation; do not copy Komari branding, logo assets, external flags, fonts, or theme-management behavior.

### Home composition (`PAGE-HOME-NETWORKS`)

The root dashboard flattens the returned Active Node projection. It remains read-only and never reorganizes the view around Agent or Host topology.

**Root `/` (`PAGE-HOME-NETWORKS`):**

1. A compact header with the PlatPulse brand link at left and one Owner-only Admin link at right that pairs a gear icon with visible `Admin` text. The brand returns to Home; the Admin link enters the Admin Overview route and does not expose Admin data inside Home.
2. A page heading, Public Projection copy, and a Server-authoritative live/realtime indicator.
3. A compact six-card overview beside a transparent Peer country map. Reading/DOM order is Active Nodes, Healthy Nodes, Attention, Balance, Cumulative blocks, Cumulative rewards (§15.37, issue #246, which removed the earlier Networks counter). The three attributable statistics read the current list selection: Active counts the Active Nodes that match, Healthy counts their Server-owned Healthy state, and Attention counts all remaining matched Nodes including Unknown. While nothing narrows the list that selection is the whole Network selection; once the search, Health or Validator status narrows it, the same three figures and the Peer country map read the narrowed selection (§15.28, issue #233). Balance is the Reward Wallet Balance — the fixed Reward Wallet's freely available LAT as PlatScan reports it — and follows neither the Network selection nor the list filters (§15.37). The two cumulative cards keep the approved Cross-Network Validator Overview over the whole Network selection — the Server publishes those totals per Network and a Node filter must never re-sum them — and each states that scope on itself as soon as a filter makes the difference visible. Sorting only changes Node order. The Attention tile states on its own face which two Server verdicts it counts — `Unhealthy or Unknown` — and carries the whole sentence as that reading's `title`, so the compact band explains its own figure without growing (§15.32).
4. Network filter pills, a labelled search control (`Name, Node ID, or Network`) that is the row's own compact field where the row has the room for one and the accessibly named entry that opens that same field where it does not (§15.30, issue #241), labelled Health, Validator status and sort controls, and a View control that switches the Compact card and the list view. The sort offers all nine stable keys (`Health`, `Name`, `Current Head`, `Peers`, `Process CPU`, `Process memory`, `Disk`, `Uptime`, `Attention First`, §15.31), and the list shows the seven public columns (Node, Network, Health, Current Head, Peers, Process CPU, Process memory) in one local horizontal scroller with the Node name and its health parked at its left edge. The Network selection scopes the reading, and the search, Health and Validator status narrow the Node list: the three attributable counters and the Peer map read that narrowed list selection while the two cumulative cards keep the Network selection and say so and the Balance follows no selection, and the sort only reorders the list, so the list states both of its numbers (`Showing <matching> of <in-scope> Active Nodes`). The one order whose name does not say what it leads with, `Attention First`, is explained where it is chosen: while it is selected the Sort control carries an `sr-only` sentence naming Unhealthy before Unknown and Healthy last, and no other key gains copy or a visible line (§15.32). The details, vocabulary and URL contract are the ones in §15.23, §15.24, §15.28 and §15.31 (issues #222, #223, #233 and #242), and the same-tab return that brings this reading back — and puts the reader on the Node they left from — is the one in §15.25 (issue #224): the departure travels in the tab's own navigation state and never in this address bar.
5. Compact Active Node cards do not equalize heights across grid rows; cards within one row still stretch to align their bottoms. A stretched semantic Node-name link opens Node Detail; copy/Details controls remain independent buttons, never nested in the link. The three-state Server-owned Node Health marker stays before the Node name — Healthy in the theme's own emerald, Unhealthy in the error colour and Unknown in the warning colour, so a Node whose evidence is missing is never painted as a confirmed failure, and the retired grey two-state treatment is gone — and the independent PlatScan Validator Activity badge keeps the top right with the upstream activity vocabulary and provenance (§12, ADR 0006); it is not an Agent online flag and its `Producing`/`Verifying` states are not the Health marker's state. A compact secondary line directly under the name (about 6–8px, with about 12px before the resource block) carries the Node's environment instead of a Node-role chip: the Network display name, the process uptime and the Peer count, with one short qualifier only when the count needs it (`last good (…)` for a retained observation, `no successful snapshot` for one never observed, `Empty; authoritative zero` for a confirmed empty peer set). A long Network name wraps inside that line instead of squeezing the Peer count or the status and identity controls, and the identity explanation keeps the whole name and additionally states the Peer observation, its freshness and any collection error, plus the Node data directory's used/capacity bytes. Healthy Nodes omit routine prose; an exceptional Node may show one short diagnostic line — the Server's own reason shortened to one line, with the whole reason on that line's own `title` and in the identity explanation, and the line's tone taken from the Server's own verdict rather than from the length of its sentence, so Unhealthy reads in the error colour and Unknown in the warning colour (§15.32).
6. Card data ownership is explicit and compact (issue #237, slice 1 of 6). Below the identity line the card keeps three regions: the resource block, the chain block and the Linked Validator block. The resource block reads exactly three columns — `CPU`, `Mem`, `Disk`, with the full `Process CPU`, `Process memory` and Node-data-directory names kept as each label's title and as its bar's accessible name — each a muted short label at its left with the tabular percentage right-aligned on the same line. The shortened `Mem` is what keeps the longest label and its percentage on one line at the auto-fill grid's own 22.5rem minimum track; only a value that is not a percentage (an unattested word, or an unusually long value) may take its own right-aligned line rather than overflowing, being clipped or being shrunk, and one thin bar per column shares the row beneath them so the three tracks stay on one line. `CPU` and `Memory` are the monitored PlatON process's own percentages (`processCpuPercent`/`processMemoryPercent`), never the Host's; `Disk` is the Node data directory's size as a share of the capacity of the filesystem that holds it (`nodeDataDirectorySizeBytes` over `nodeDataDirectoryCapacityBytes`), never whole-filesystem fullness and never the Host storage percentage. PlatPulse owns no occupancy percentage threshold for these bars, so the ordinary fill is the theme's own success green — the approved colour for a reading the Server published — rather than the default primary (white in the dark theme), and that colour states no verdict of its own: no success/warning/error condition is invented, and a Server-owned rule can replace it without touching the columns. A ratio the Server attested as zero stays `0.0%` with an empty track; a ratio that is missing or cannot be computed says `Unknown` and draws no value at all; the used/capacity byte caption moves to the identity explanation, which also names the Disk source. The shared Host network line keeps the two labelled directions as one compact key-value line — the green up arrow with the upload rate and the blue down arrow with the download rate, each keeping its accessible direction name — converting bytes per second to a decimal bit-rate with the existing unit-boundary rounding rules, never summed across Nodes that share a Host and never drawn as a chart. The chain block carries only the current Block Height (`currentHead`) as one compact key-value line, keeping the label so it matches the list view's `Current Head` and Node Detail's vocabulary; QC, Locked, Committed and the transaction count are Node Detail statements now, with their response fields, collection, history and Node Detail presentation unchanged, so this supersedes the earlier Home four-height chain block (Head/QC/Locked/Committed/Txs/Peers as paired rows plus count rows) and a consensus height Home no longer restates prints no stale or removed-row marker there, while an absent or unusable height stays explicitly Unknown rather than a fabricated zero. The Peer count leaves the metric rows for the identity line described in item 5, and the earlier full-width Node data caption and two/three-column chain fallback are superseded by the three fixed resource columns above. The width switch that remains is a CSS container query on the card, not a viewport breakpoint or a JavaScript size listener. The Linked Validator block shows the three-item summary issue #238 specifies: Network rank, Cumulative blocks and Cumulative rewards as compact label-over-value cells that take three columns once the card's own container query reaches 25rem and two otherwise, with the third cell keeping the whole row width when only two fit. Every cell paints the short name and keeps the full field name as its accessible name and title, so the compact vocabulary always means the full metric; an unattested metric says Unknown while a real zero stays `0`; exceptional values stay bounded on one line instead of being clipped or shrunk; exact digits stay reachable from the command that abbreviates them; and Unranked, a retained last-good rank and Unknown remain distinct. Current Validator Status alone decides identity: a confirmed non-Validator or an identity that cannot be confirmed replaces the three cells with one short identity line that reserves no metric height — a confirmed non-Validator says the one word `Non-validator`, with its reason on that line's own `title` and in the card's identity explanation, while an identity that cannot be confirmed keeps `Validator unknown — <reason>` visible, so an unproven role is never read as a confirmed absence (§15.32) — and Observing, consensus membership or a missing rank/reward/history is never read as evidence of identity. The full six metrics, their states, exact values and long exception explanations stay on Node Detail. An exceptionally long compact value stays on one line and makes only its own summary cell span the full row instead of shrinking, clipping or splitting digits. Missing values remain explicitly Unknown rather than zero; historical values, real zero, Unranked, Not applicable and independent stale/error dimensions must survive compaction. The content-driven three-item Validator summary and the content-driven grid are implemented as issue #238. The chain block's evidence-based Block Height comparison and the separate Resyncing hint are implemented as issue #239 (slice 3 of the same issue): Home keeps the absolute Block Height in its own value element and paints one short comparison beside it — `At observed head`, `Behind <n> block(s)` or `Ahead <n> block(s)` — only while the same conservative gate the Node Detail page uses holds (valid non-negative safe-integer Node and reference heights, `rpcState` ok, a parseable observation time, Server-owned Healthy and `high` reference confidence), with that page's own tone scale (an exact match is the success tone, a lag of 1–10 blocks the warning tone, more than 10 the error tone, and a Node ahead of the reference the neutral tone — a leading state never clamped to the reference and never written as synced). The comparison is right-aligned on the height's line while that line holds both and takes its own right-aligned line when the card's tightest track cannot, so the reading is never clipped, shrunk or overflowed. `Observed Network Head` is the deployment-local Server reference: it is never called a canonical, public or explorer head and never proves synchronization, and its availability, the reason a comparison is absent, and the fact that the tone is a display level rather than a health, alert or Attention rule all stay in the card's existing explanation entry. While no comparison is supported the card keeps only the absolute/last-good Block Height: `Unknown` for a height the Server never validly observed and for a height that cannot be one at all (negative or fractional), and never a fabricated zero, and the same short `Last-good` mark Node Detail prints for a value a failed collection kept when the Server still holds the height but is not confirming it as current — a failed or unknown RPC collection, an unknown observation time, or a health verdict that does not confirm it — with the Server's own reason in that mark's title and in the card's explanation entry. The mark replaces the comparison rather than joining it, because a comparison needs exactly the observation that is missing, so the two can never share the line, and a height whose only missing evidence is the reference's stays an unmarked confirmed current reading. The comparison itself adds no control: the card keeps one link to its Node and one identity explanation entry, reached by keyboard and by touch, and the entry names the retained height, the reason, and which references a comparison would have read. Resyncing continues to read the Server's `resyncState` and stays independent of Node Health, Activity, Current Validator Status and that comparison: it shows its short percentage only when a valid current height and a valid, computable Historical High-Water Mark target both exist — the target is never the Observed Network Head — and without one the cue keeps the Server's state word alone with no `Resyncing Unknown` area, while the retained target and the real last-progress timestamp stay reachable from the same cue.
