### 15.19 Recorded sync and consensus state history on the Node detail page (issue #217, delivered)

Applies to `PAGE-ADMIN-NODE-DETAIL`:

- `PAGE-ADMIN-NODE-DETAIL` carries a third history panel, `Sync and consensus history` (`data-slot="state-history-panel"`, `data-surface="node-state"`), rendered between `Metric history` and `Host metric history` (platpulse-web/src/pages/AdminNodes.tsx:651-653), so the page's three panels are told apart in the DOM by `data-surface="node-process"`, `"node-state"` and `"node-host"`. It is not the metric component: it renders `StateHistoryBody` (platpulse-web/src/pages/stateHistoryPanel.tsx) over the pure view module platpulse-web/src/stateHistory.ts, and it reads the Owner-only `GET /api/admin/v1/nodes/{node_id}/state-history` (`AdminStateHistoryResponse` with `AdminStateEntry`, `AdminStateGap` and `AdminStateSeries`), asking for `limit` 20000 (`METRIC_HISTORY_SAMPLE_LIMIT`, platpulse-web/src/metricHistory.ts:246, which is the Server's `MAX_STATE_LIMIT`) with the presets and the fixed window of §15.16.
- The card renders recorded evidence rather than a reconstructed series: one row per state the Server actually recorded, in the Server's own order — it says so itself, `Oldest recorded state first, in the order the Server answered them.` — and the newest state is aged against the end of the window instead of the silence after it being claimed as a gap. Every value in the card comes from the answer, so a state the Server never recorded is shown as absent rather than as a value, and a failed probe is never read as `false`.
- The component switch is a `Component` select over `Sync` and `Consensus` (`STATE_HISTORY_COMPONENTS`), and the window controls are the §15.16 range presets (1 hour/6 hours/24 hours/7 days/30 days) plus `Reload window`. Switching the component or the range returns to the newest page, and the query is keyed by the Node, the component, the answered range, the paging cursor (`before ?? 'newest'`) and the access generation, and it stays disabled until the Node and the component both have an identity — an unanswered switch never renders evidence the Server did not record (platpulse-web/src/api/admin.ts:836 `useAdminNodeStateHistory`).
- The rows are evidence columns: `State` (`Change` or `Anchor`), `Observed` with the receipt beneath it, `Value age`, `Collection` (`Collection succeeded`, `Collection failed`, `Collection is off`, `Collection is unsupported`, `Collection has just started`), `Value source` (`Value observed now`, `Retained last good value`, `No value`) carrying the evidence badge `Current`, `Last good`, `Failed`, `Not collected`, `Unsupported`, `Starting` or `Unknown`, `Syncing` (`Syncing`, `Not syncing`, `Unknown`), `Failure` (`None recorded` or the Server's code), `Delay`, and `Clock` (`Clock in step` or `Clock suspect` with the Server's note). A flag the collection could not read is `Unknown` and never `false`; a retained value keeps the instant it was really observed at, so `Value age` reads the age of the value rather than the freshness of the row.
- Above the plot the card states what the Server knows about the series itself, independent of the window: `Deliveries recorded`, `Changes recorded`, `Anchors re-recorded`, `First observed`, `Last observed`, `Anchor interval` (`<duration> at most`, or `Not recorded`), `Reporting cadence` (a duration or `Unknown`), `Covered stretch` (or `No stretch proven`), `Retained window` (`<n> days`) and `Released before` (or `Nothing released`). A series nobody observed prints `Never observed` and `None recorded` rather than a zero, and a release floor is shown as a boundary so a missing early row is not read as a quiet start.
- The anchor rule is disclosed on the card in the Server's terms rather than left to the reader: `An unchanged state is recorded again at most once every 1 hour, which is what keeps a constant state provable: an anchor row proves the Node was still reported on, so a stretch without an anchor is a missing report rather than a quiet Node.` Under it the card prints the cadence it measured — `This Node reported every 5 minutes; the silences below are what the record holds, not what a cadence was assumed to allow.`, or, when no cadence could be measured, that no silence below is measured against one — the covered stretch (`The record proves 1 hour of 24 hours: only the stretch between two recorded states is covered, and the time after the newest state is left to the reader instead of being claimed.`), the age of the newest recorded state, and the Server's latest word for the component from the ledger.
- The plot (`data-slot="state-history-chart"`, `role="img"` with a label naming the component, the number of recorded states and the number of silences) draws one marker per recorded state — `Change` above the baseline and `Anchor` beneath it, tinted by evidence — one band per silence, and the stretches two adjacent recorded states prove. A stretch the Server reported as a gap is never drawn as proven, and a window with no markers and no bands draws no plot at all.
- Silences keep their kind and their cost: `Silences in this window` lists every gap with the Server's own kind label, its `from → to (duration) · reason`, the observations it swallowed when the Server counted them, and a claim sentence that differs by kind — a collection gap says nobody observed this Node across the stretch so nothing is claimed about its state in it, while a protection pause says the operator paused history collection, that a paused stretch is neither a state nor a change, and that the skipped observations behind it are disclosed rather than lost. The whole window's pauses are summed above the table when there are any.
- Truncation and paging are explicit: a truncated answer prints the newest states it carries and reports the older ones instead of dropping them silently, offers `Load older states` only when the Server returned a continuation, and passes that coordinate back as the exclusive `before` cursor; an older page says `An older page of recorded states is shown.` and offers `Return to the newest states`. An answer clamped to the retained window or older than any retained state says so in its availability notice, so a partial answer never passes itself off as the requested range.
- The states around the card stay distinct: a `role="status"` line (`Loading the recorded states...`) while the first read is in flight, a `role="alert"` carrying the Server's sanitized reason with `Try again` when the read fails, and, when a refresh fails, a `role="alert"` that keeps the last recorded states on screen labelled as what they are (`Failed to refresh; showing the last recorded states the Server answered with.`) instead of presenting them as current. A component that was never observed renders `Never observed` with the notice that a component never observed is not current, not healthy and not zero.
- The card offers no control that writes history, edits a retention policy, pauses collection or deletes rows. It is Owner-only behind the same existing CSRF/Origin middleware as the rest of the page, its query cache is generation-scoped with no placeholder, and it holds the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus and 44x44 touch targets, with the states table inside its own keyboard-reachable scroll region (`data-slot="state-history-table-scroll"`, `role="region"`) that stacks on narrow viewports and never widens the page.

### 15.20 Automatic Validator identity and current status on the Admin surfaces (issue #218, delivered)

Applies to `PAGE-ADMIN-VALIDATORS`, `PAGE-ADMIN-VALIDATOR-DETAIL` and `PAGE-ADMIN-NODE-DETAIL`:

- The Admin navigation gains one page group, `Validators`, registered after `Networks` with the `BadgeCheck` icon and the label `Validators` (platpulse-web/src/layouts/AdminLayout.tsx:255), and the two routes above are registered pages rather than wildcard fallbacks (platpulse-web/src/App.tsx, asserted by platpulse-web/src/App.test.tsx). An unknown Validator id renders the `Validator unavailable` page with the link `Back to Validators` instead of a generic not-found page.
- Both pages read one Server projection, so they cannot disagree: the coverage table and the Node panel read `GET /api/admin/v1/validator-identities` and the embedded `validator_identity` of the Node detail, which the Server answers from a single `list_node_validator_identities` query; the registry and the detail read the existing Admin Validator endpoints, whose insight now carries the derived `activity`, `currentValidatorStatus`, its qualifier and state, and their own `activityReceivedAt` confirmation time. Detail metric receipts/age remain independent from that verdict. Identification (this Node's Network plus the full P2P public key its Agent observed) and current staking validity (Provider evidence) stay two answers, and neither is inferred in React.
- The coverage card is `Automatic Validator identity`, placed after the registry and collapsed to its summary by default (§8.7): its badge reads `Resolved` when every evaluated Node is identified, `<n> unresolved` (warning tone) when an evaluated Node is not, and `Nothing evaluated` (neutral tone) when the Server has evaluated no Node at all. All three are computed from the whole answer and never from the search-filtered rows, so a search can neither hide an unresolved Node nor certify coverage; the line beside it counts `<total> Nodes · <evaluated> evaluated · <identified> identified · <unresolved> unresolved` (plus `· <n> not evaluated` when any), where a Node whose state is still `not_evaluated` counts as a known Node rather than as evaluated work. Its copy states that coverage is counted per Node rather than per Agent and that `an unresolved state says the evaluation did not establish an identity rather than that the Node does not stake`. The Server's own `reason` is printed under each state, so an unresolved row explains what evidence was missing.
- The coverage table (`data-slot="validator-identity-table"`, `data-stack`, inside its own `overflow-x-auto` container) has the columns `Node`, `Identity state`, `Observed P2P key`, `Validator`, `Public association` and `Evaluated`. The Node cell links to `/admin/nodes/:nodeId` and names the Network beneath it; the state cell prints the Server's state label plus the reason; the key cell prints the short key with the whole observed key as its `title`; the Validator cell links to `/admin/validators/<validatorId>` or reads `Not established`; `Public association` prints `Shown` with `Active Node with an open Link`, `Not shown` with `Open Link, Node not Active`, or `No Link to project` when the Server holds no association to project. That decision is the Server's own `validatorId`/`associationEffective` and never the discovery state, so an interval that is still open while the current evidence no longer identifies a key still reads `Shown` or `Not shown` — the page never claims an association the Public projection does not show; `Evaluated` prints the instant or `Never evaluated` with the Node's lifecycle beneath it.
- A Node the Server has never evaluated is a row reading `Not evaluated`, not a missing row, and the empty states are distinct: `No Node has been evaluated for an automatic Validator identity yet.` for a Server that has evaluated nothing, `No Node matches this search.` for a search that matched nothing, `No Validator has been resolved yet. A Validator appears once an Agent observation establishes one.` for an empty registry and `No Validator matches this search.` for a filtered one. One search field (`Search Validators and Nodes`, placeholder `Display name, Node ID, or identity key`) filters both tables by Node label, Node id, Validator display name and identity key.
- The registry card `Validator registry` (`data-slot="validator-table"`, `data-stack`, own scroll container) has the columns `Validator`, `Current status`, `Last confirmed at`, `Rank`, `Stake`, `Delegators`, `Metrics evidence` and `Nodes`. `Current status` is the Server's canonical label plus its qualifier with the evidence word beside it and the activity line beneath it; `Last confirmed at` is the verdict's own `activityReceivedAt`, or `No confirmed verdict` when absent, never the last detail metric receipt. Rank has its own freshness, outcome and last-good receipt beside the value: a successful complete cohort can prove `Unranked`, a never-observed/failed first rank is `Unknown`, and a retained rank after failure is labelled stale regardless of detail freshness. `Metrics evidence` independently labels detail metric freshness and its last-good age/receipt, or explicitly states that metrics were never observed; a fresh verdict or rank cannot renew older staking metrics. It separately discloses the latest detail refresh outcome and sanitized diagnostic: chronologically fresh LastGood values may be retained after a failed refresh, so Fresh metrics must not hide that latest Error. An authoritative absence is a detail verdict, not a fabricated new metric sample. A missing amount or delegator count is `Unknown` and never `0`; `Nodes` is the Server's count of the association intervals it recorded for that identity, which includes ended intervals and counts a Node this identity was linked to twice twice, so it is an interval count rather than a distinct-Node count.
- The detail page's `Current Validator status` card renders `Evidence`, `Last confirmed at`, `Activity` and `Validator key`, states that a locked or exiting identity is confirmed valid but not normally participating, and, for a verdict the Provider could not refresh, adds the note that the last successful verdict is retained and that an unestablished status is not a negative conclusion.
- The detail page's `Provider evidence` card renders `Source`, `Freshness`, `Outcome`, `Counter state`, `Observed at`, `Provider timestamp`, `Attempted at` and `Diagnostic`. `Counter state` prints the Server's value only for a read that succeeded (`success`/`empty`); when the latest refresh failed but an earlier good answer exists it prints that retained value as `<state> (retained)`, and otherwise `Not observed`, because the Server synthesizes the same `normal` default both for a deployment it never read and for a first failure with no good answer. The card's copy states that a Provider failure is reported as unavailable evidence and is never turned into a negative verdict or a fresh zero. A Provider the Server reports as unconfigured is rendered by `validatorSourceLabel` as `Not configured` rather than as the raw `disabled` value, so a missing Provider cannot be misread as a measurement; absent values read `Not observed`, `Never observed`, `Not reported` or `Unknown` rather than a blank or a zero.
- The detail page has a separate `Rank evidence` card with `Rank`, `Rank freshness`, `Rank outcome`, `Rank attempted at`, `Rank last-good received at`, `Rank last-good age` and the sanitized `Rank diagnostic`. These belong to the Network ranking request, not the detail metrics; failed/never-observed ranking cannot appear current because the detail request succeeded. The repair and its actual regressions/gates are recorded in [Issue #202 — Validator evidence repair](../../research/archive/issue-202-validator-evidence-fix.md).
- The detail page's `Staking metrics` card prints the Provider's staking facts with `Not set` for an absent display name, and its `Node associations` card prints every association the Server recorded with the columns `Node`, `Valid from`, `Valid until` and `Role` (`data-slot="validator-links-table"`). A link with no role states `Automatic identity, no manual role`, and an interval that ended at a key change stays readable. A Node Purge is the exception the card must not paper over: purging a Node deletes the intervals owned by that Node together with the Node, so that Node disappears from both the coverage list and this table (the count falls by that Node's intervals and reads 0 only when the purged Node held this identity's only association) and the deleted association reads back as unavailable instead of being reconstructed, while the shared Validator identity and its recorded history remain — Node-owned monitoring history is deleted with the Node, shared identity is not.
- The `Validator identity` panel of `PAGE-ADMIN-NODE-DETAIL` (platpulse-web/src/pages/AdminNodes.tsx:1271-1343, mounted at :660 between the identity and RPC-diagnostics panels) states the same identification for one Node: the Server's state label and reason, the observed full P2P public key, the chain Validator as a link to `/admin/validators/<validatorId>` or `Not established` when none is resolved (`Not evaluated` when the Node was never evaluated), whether the automatic Link is actually projected (`Open, and shown in the Public projection`, `Open, but the Node is not Active so Public shows no association`, `No automatic Link to project`), `Evaluated at` with `Never evaluated`, and the Node's lifecycle. A Node that was never evaluated reads `Not evaluated` rather than an absence of a Validator, and the panel never states ownership, a primary/standby/observer role, or consensus membership.
- States stay distinct on both pages: a `role="status"` `Starting` line while a read is in flight, an `Unavailable` block with `role="alert"` and `Try again` when a read fails, and, when a refresh fails, a `role="alert"` that keeps the last successful answer labelled as what it is (`Failed to refresh; showing the last successful identity coverage.` and `Failed to refresh; showing the last successful Validator values.`) instead of presenting it as current.
- Contracts: both pages are Owner-only behind the existing CSRF/Origin middleware and the Admin shell's access-generation handling; their queries are keyed by the access generation with no placeholder data, are invalidated by the realtime signal for Network, Validator and Validator-Link changes — including the invalidation the Server's own automatic-identity discovery pass publishes the moment it opens or closes a Link, so an already-open page refreshes without a navigation and without a Provider — and render only sanitized Server errors. Neither page offers any control that writes an identity, a role or a Link — no manual association entry exists. The tables use `data-stack` with their own keyboard-reachable scroll containers and never widen the page (no primary horizontal overflow) at the fixed 360/390/768/1280/1440 viewports in Light and Dark, with visible keyboard focus and 44x44 touch targets.

### 15.21 Validator snapshot trends on the configured local calendar (issue #219, delivered)

Applies to `PAGE-ADMIN-VALIDATOR-DETAIL`:

- The detail page gains one `Daily trend` card (`data-slot="validator-trend-panel"`) under `Node associations` (platpulse-web/src/pages/AdminValidators.tsx:525, platpulse-web/src/pages/validatorTrendPanel.tsx:325). It is the only reader of `GET /api/admin/v1/validators/{validator_id}/trend` (platpulse-web/src/api/admin.ts:1059 `useAdminValidatorTrend`), keyed by the Admin access generation *and* the requested window with no placeholder data, so an identity change or a window change can never render another window's rows.
- Its intro states the four things the card will not do: one stored snapshot per configured local day over a bounded window, the configured day and month boundaries mapped into UTC (so a daylight-saving day is 23 or 25 hours wide "instead of a pretended 24"), no stored bucket silently re-bucketed into UTC, and a day with no snapshot is a silence while a metric the row never carried is Unknown — never a zero.
- The window control is a `role="group" aria-label="Trend range"` of the presets `7 days`, `30 days`, `90 days`, `180 days` and `365 days` with `aria-pressed` on the selected one, plus `Reload window`. A preset fixes the requested window once per selection (`validatorTrendRange` asks in UTC instants at canonical seconds precision) and `to` includes the local date its instant falls into, so an N-day window touches N+1 configured local days. The page size is bounded to `VALIDATOR_TREND_PAGE_DAYS = 31` (platpulse-web/src/validatorTrend.ts:49): the 7- and 30-day presets are answered in one page, the longer presets ask for 31 local days at a time, so `Load older days` (the Server's exclusive `before` cursor, enabled only when the answer reports a continuation) and `Return to newest` are reachable Owner paths and a longer preset never becomes a longer response.
- The `Series` select offers `Rank`, `Stake` and `Delegators` and defaults to `Rank`, which stays a position and never a score. The chart (`data-slot="validator-trend-chart"`, `validatorTrendChartGeometry`) breaks its line wherever a day is missing or the selected metric is Unknown instead of interpolating across it, and draws that missing stretch as a band.
- Every disclosure the Server answers with has its own paragraph: coverage (`validator-trend-coverage` — `partial` is read from the answer's own numbers, so a proven silence inside the answered stretch and a stretch that is merely short of the requested window are two different sentences and the second never claims a day is missing), the answered-versus-requested stretch (`validator-trend-stretch`, "the days it does not reach are not silences in this answer"), the clipped page (`validator-trend-truncated`, naming the exclusive continuation instant and stating no day is answered twice), stored rows formed in another timezone (`validator-trend-foreign`), the association-history state (`validator-trend-associations-notice`) and the counter semantics (`validator-trend-counters`) — reward and block values stay labelled cumulative, stake is stated as the balance the Provider reported at that sample, and none of them is ever presented as period earnings or net profit.
- The detail list prints `Configured timezone`, `Coverage`, `Requested`, `Answered`, `Observed / missing`, `First / last observed` (an absent day reads `Unknown`, never a date) and `Association history` (`Partial · <n> deleted Node(s)` when the Server still holds history it can no longer resolve). `Silences in this stretch` lists each gap as a local-day range with its honest wording and reads `No configured local day of the answered stretch is missing a snapshot.` when there is none. `Stored days` is the `data-slot="validator-trend-points"` table with `Local day`, the real `UTC window` and its hour width, `Month`, `Rank`, `Stake`, `Delegators`, `Reward (cumulative)`, `Blocks (cumulative)`, `Sample time` (which instant chose the day — the Provider timestamp or `Server receipt (fallback)` — plus all three named instants `Sample`/`Provider`/`Receipt`, where a Provider timestamp the observation never carried reads `Unknown` instead of borrowing the receipt, alongside the `Delay` cell that reads `Unknown` whenever no delay can be computed) and `Source`. `Configured months` maps each configured month to the UTC instants its boundaries really fall on. Both tables are `data-stack` with `scope="col"`/`scope="row"` headers.
- `Node associations` lists only the intervals that still resolve to a surviving Node, each linking to `/admin/nodes/:nodeId` with its origin, `validFrom → validUntil` (or `open interval`) and an `Open`/`Ended` badge. An empty list states that the deleted Node intervals "are unavailable rather than never having existed" whenever the history is partial, so Story 68's promise stays visible where the trend is read: purging a Node removes the association and never the shared Validator's stored days.
- The card is Owner-only through the existing `/api/admin/v1` guards (real Origin/CSRF, sanitized errors with `Try again`, `role="alert"` on failure, `role="status"` while loading, and a distinct alert when a refresh fails while the last successful answer is still shown). Every control is a 44px touch target, the panel never widens the page at the fixed 360/390/768/1280/1440 viewports in Light and Dark, and the stored-days table scrolls inside its own container. The same five viewports × both themes are also captured as evidence screenshots under `docs/visual-migration/emerald/validator-trend-219` (`platpulse-web/e2e/validator-trend-acceptance.spec.ts`): evidence for review at the fixed matrix, never a gate — no baseline is recorded and no screenshot is compared (ADR 0002).
