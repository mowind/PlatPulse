### 15.12 Backup artifact inspection and verification (issue #209, delivered)

Applies to `PAGE-ADMIN-BACKUPS` and `PAGE-ADMIN-BACKUP-DETAIL`:

- The Admin navigation carries `Backups` → `/admin/backups`, and each artifact is independently linkable at `/admin/backups/:artifactId`. The pages read the recorded artifact row the Server owns: they never create, restore, or delete an artifact, and they offer no scheduling. Creation and restore are offline commands on the Server host (`docs/adr/0008-offline-server-backup.md`), the page says so in its own copy, and no control on it can produce an artifact — an artifact missing from the list is not evidence that no backup exists on the host.
- The list shows the manifest facts the Server recorded (file name, created time, size, schema and Server version, observed data window, creating task) plus each artifact's last recorded verification outcome. A size, window bound, or timestamp the Server did not record reads `Not recorded`/`Unknown` — never `0`, `0 B`, or a fresh observation.
- Verification is requested, never performed by the browser. `Request verification` is one explicit Owner command, queued with a request id through the same CSRF/Origin middleware as every other Admin mutation. `Acceptance is not a result:` is stated plainly, and the page then reads the Server's own Operation record for that task — the one it just accepted, and otherwise the task its recorded `verifyOperationId` names — including its status, progress, recorded issues, and result payload. The recorded artifact state above it changes only when the worker writes an outcome, so an in-flight request is never rendered as a pass or a fail.
- The outcome is Server-owned and rendered verbatim: nothing recorded (`Not verified`), `ok` (`Verified`), or `failed` (`Verification failed`). The Server's recorded reason is shown as the Server wrote it; a known shape (checksum mismatch, unreadable file, snapshot integrity or schema mismatch, unsafe snapshot) also gets a plain-language reading, and an unrecognized reason is shown alone rather than interpreted into a verdict. An absent reason is `Not recorded`, not `Unknown error`.
- `Verified` means the recorded artifact passed the read-only scan the Server ran, and the page states that this is not a restore rehearsal and never proves that a production restore will succeed. Verification success is never presented as a production-restore guarantee, and a failed verification is never presented as a lost backup: the recorded artifact row stays exactly as it was.
- The verified Operation is linked from the artifact through the recorded `verifyOperationId`, and its recorded status and outcome are readable where the artifact is read, with the full record on `PAGE-ADMIN-OPERATION-DETAIL`; a later verification replaces that link, and the earlier outcome stays readable in its own Operation. The card reconciles the artifact with the task instead of assuming the task is still in flight: the task's state is read from the Server rather than on a timer, and it is read again after the command. When the task reaches a terminal state the page re-reads the artifact record, and it presents that task's outcome as the artifact's own only while the recorded `verifyOperationId` still names that task — otherwise it says the artifact record does not point at that task, so that task's result is not attributed to the state above, and that the state above is still the last outcome the Server recorded for it. The page never promises that a link is coming: a newer verification can replace the link before an older task finishes. A cancel the Server honours finalizes the Operation as `cancelled` without touching the recorded artifact, so the last recorded outcome survives a cancelled verification — and the card names that task's own terminal state rather than reporting an in-flight task the Server no longer has.
- A verification task that failed after writing an outcome of its own is read that way: the task record holds the failure, the errors it wrote are listed beside the artifact, and the card says which of the two the artifact state above reflects. A failed task is never read as a failed verification outcome: the Server records the outcome and finalizes the task afterwards, so a restart can fail a running task whose recorded outcome still stands (`crates/platpulse-server/src/backup.rs`, `crates/platpulse-server/src/operations.rs`). The card reads the two together — the outcome the artifact carries and the task's own end — instead of inferring one from the other. A task that failed before writing any artifact outcome — the only case where the Server has no linked outcome — is stated as exactly that, and the page never claims a failure happened before the artifact was touched when the Server's own test surface shows the outcome was written first (`crates/platpulse-server/tests/backup_verification_flow.rs`). A task record the page cannot read is named as unread; the artifact keeps its recorded outcome and the page never reports success, failure, or flight on the task's behalf.
- Accepting a command is remembered per artifact and per session generation: the card is remounted when the artifact or the identity changes, and a completion for an unmounted card writes nothing, so a previous task's state is never shown beside a different artifact or in another session.
- A verification task is an ordinary retained Operation, observed on `PAGE-ADMIN-OPERATION-DETAIL`: it shows the recorded status, issues, and outcome payload, and its cancel control is enabled only while the Server reports the task cancellable. While a task is queued or running, the artifact page labels the visible artifact state as the last one the Server recorded. Nothing on either page deletes an artifact or a task.
- Both pages stay Owner-only behind the existing CSRF/Origin middleware with sanitized errors (no backup-directory path, Server pepper, database path, or password in any DTO, error, or URL), a durable Audit entry per accepted verification, and generation-scoped query caches so an identity change cannot show another session's artifacts. Viewer and Guest sessions reach the Owner-only boundary and never a partial artifact surface.
- They are laid out for the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus, 44x44 touch targets, and local table scroll without primary horizontal page overflow.

### 15.13 Retention policy, safety floors, and bound impact preview (issue #210, delivered)

Applies to `PAGE-ADMIN-RETENTION`:

- The Admin navigation carries `Retention` → `/admin/retention`. The page reads the Server's policy table: family label, current value, its bounds (`minDays`/`maxDays`), the default, whether the family is supported and enabled, and when and by whom it was last written. The per-family minimum already contains that family's safety floor, and the page states the Server's own floor reason (24 hours of raw history, 30 days of investigation history, design §11.4) so a refused value is explained rather than mysterious. The page invents no bound of its own; a value the Server refuses is refused.
- A policy family that is unsupported or disabled is shown as not actionable: the page says the Server declares no cleanup contract for it, and it never renders `0` rows as evidence that nothing is retained. A family whose value means "keep forever" is shown as such and is never stealthily shortened; a longer existing retention is left exactly as recorded until an explicit edit inside that family's own supported contract changes it.
- Editing is one family at a time and never optimistic. The save submits the `policyVersion` the operator read, so a stale tab cannot overwrite a value it never reviewed: a `409 retention_policy_version_conflict` means the recorded value changed since it was read, and the page re-reads the overview, says so, and requires a fresh read and preview before saving again — it never retries blindly. A rejected save leaves the recorded policy exactly as it was, and an accepted save reports the returned policy plus its recorded `auditEventId` as recorded fact, refreshed from the Server. The version submitted is the version the operator read when the draft began, not whatever the latest refetch happens to hold: a background reload of the overview — another Owner's save, or composing a preview, which invalidates it — never re-arms a draft that was already confirmed, so the page keeps the reviewed version, says the family was written again and which value is recorded now, and lets the Server refuse the write instead of overwriting a value the operator never read; after that refusal the draft and its confirmation are dropped and the recorded value is what is shown.
- The per-family read-only impact preview (`retention_impact`) is unchanged and still never audits: it reports a Server estimate, whether the family is unsupported, the bounds, and the Server's notes. The page labels every count as an estimate and never as a count of rows that will certainly be removed.
- Composing a preview creates a Server-owned, expiring record: `previewId`, `createdAt`, `createdBy`, `expiresAt`, an overall `policyVersion`, the requested `scope` (absent means every actionable policy), each family's `cutoff`, `policyVersion` and `estimatedRows`, the `estimatedRows` total, the Server's `notes`, and the `protectedState` it will not touch. The page shows the per-family cutoff, the expiry, and the notes verbatim. Composing a preview changes nothing and therefore records no Audit Event.
- A requested family the Server will not act on appears in `skipped` with the Server's own `code` and `message` (unknown family, unsupported family, disabled policy, or keep-forever policy). The page renders that reason as written and never claims those families were covered.
- The preview is the authority, and the run is bound to it: the run submits only the `previewId`, so the estimates the Owner reviewed are the estimates that execute, with the frozen per-family cutoffs. The overview exposes the newest preview that still binds, so a reloaded page offers the same reviewed plan rather than composing a new one — and the page pins the preview it first restored, replacing it only when the Owner composes a new one here, so a later refresh can never substitute a plan that was never reviewed. If a policy, the scope, or a cutoff changed since the preview — or the preview expired — the Server answers `409 retention_preview_stale` with its reasons (or `404 retention_preview_not_found`) and queues nothing; the page shows the reasons, discards that plan, and requires a new preview.
- The counts are estimates, not a frozen row set, and never a quota: an entry is complete only when a bounded batch comes back short of the batch bound, which proves no expired row is left behind its frozen cutoff. The released rows may therefore exceed the estimate, a batch that releases nothing ends that entry instead of retrying forever, and the page reports the released counts it reads from the recorded Operation rather than presenting the estimate as a promise.
- Two boundary conditions are accepted and stated rather than hidden: the recorded policy version digests the family's recorded value together with its timestamp, so an edit that returns a family to exactly the value that was previewed re-validates (any edit that changes what the plan would release is still refused, and an explicit `retention_days` comparison backs the digest); and re-validating the preview and queueing the run are two statements, so a policy save committed in that window cannot widen or lengthen the queued plan — its cutoffs were already frozen — while every later run must compose a new preview.
- Starting a run is one explicit Owner command behind typed confirmation: the operator types `run ` followed by the opening characters of the preview id as the panel displays it, and only that exact token arms the command, so a bound preview is never executed by a stray click. The confirmation names one preview and is never inherited — binding a different preview clears it, and a replacement preview must be confirmed again — and the command is queued with a request id through the same CSRF/Origin middleware as every other Admin mutation; the page reports the accepted task and links to its recorded Operation on `PAGE-ADMIN-OPERATION-DETAIL`. Nothing on the page deletes data itself, and no effect is shown before the worker writes an outcome.
- Report and receipt identity, Incident evidence, Audit records, and the independent Purge boundary are named as protected state the retention run does not touch, and the page offers no control over them.
- The page is Owner-only behind the existing CSRF/Origin middleware with sanitized errors and a durable Audit entry per accepted policy save and per accepted run; query caches are generation-scoped so an identity change cannot show another session's policies or preview. Viewer and Guest sessions reach the Owner-only boundary and never a partial policy table.
- It is laid out for the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus, 44x44 touch targets, and local table scroll without primary horizontal page overflow.

### 15.14 Retention execution bound to a reviewed plan, one command per confirmation, and honest cancellation (issue #211, delivered)

Applies to `PAGE-ADMIN-RETENTION` and `PAGE-ADMIN-OPERATION-DETAIL`:

- One confirmation is one Owner command carrying a request id the page mints for the preview it bound. Binding a different preview mints a new one, and a refusal meaning "this identity was already used for different work" rotates it, so the next click is a new command rather than a repeat of the refused one. Sending the same command again — a doubled click, a second tab, a retry after a lost response — reconciles to the run the Server already recorded: the page says `no second cleanup was queued`, links to that recorded task, and never presents the replay as a freshly queued cleanup. `409 retention_run_in_progress` (that kind of cleanup is already queued or running) and `409 operation_request_id_conflict` are shown as the Server's own words with the recovery the page can offer, and neither is retried blindly.
- The page reports the recorded task rather than an expectation: nothing is shown as queued, released or cancelled before the Server records an outcome, a deduplicated answer is labelled as a replay of an existing command, and a refused command is reported as queued nothing at all.
- Cancellation is presented from the recorded outcome and never inferred. A cleanup that stopped at a safe checkpoint shows, per family, how many rows it released against the Server's estimate, how many planned targets were not completed, and that released rows are never rolled back; a cleanup cancelled while still queued shows that it released nothing and names the work it stopped short of. A family the Server recorded no counts for is omitted from that summary instead of being rendered as `0`, the raw recorded payload stays available below the summary, and a payload that does not match the Server's recorded shape renders no summary at all rather than a guessed one.
- Status, phase, cancel-requested and terminal time all come from the Server; a cancelled task is never shown as completed, and the page offers no control that could imply a rollback of released data or reach protected state.

### 15.15 Storage capacity and low-space protection visibility (issue #212, delivered)

Applies to `PAGE-ADMIN-OPERATIONS`:

- The Operations page carries a `Storage capacity and low-space protection` panel reading `GET /api/admin/v1/capacity`. Every value is Server-owned: the mount being sampled, the total and available bytes of the last reading, the pause and resume floors, the sampling interval, whether optional history is currently paused, and how old the reading is. A deployment that declares no `[capacity]` policy reads `Disabled` and shows no interval row instead of `0 B` or a fabricated pause. The panel offers no control that edits a threshold, pauses history by hand, or deletes data.
- State comes from the Server's own words: `Protecting` (available space reached the recorded pause floor, so optional metric history is paused until availability reaches the resume level), `Monitoring`, `Disabled` (no policy declared, which is neither a failure nor a pass), and `Unknown` when no usable reading is available. `Unknown` covers both an enabled policy that has never measured the filesystem successfully and one whose latest attempt failed while the last good reading is retained; it never renders as `0`, `false`, or `Healthy`, and it is never shown as `Monitoring`. The panel says why history is paused, names both the pause floor and the resume level, and names which of the two `Unknown` cases applies instead of guessing.
- The recorded interval table shows each protection window the Server wrote: start and end time, the recorded reason it opened or closed (`Low space`, `Resumed`, `Protection disabled`), the volume it recorded, the total and available bytes at both boundaries, and the samples it skipped. A reason the WebUI does not recognize reads `Unknown` rather than an interpreted verdict, and an interval that has not ended shows no end time instead of an invented one.
- Skipped samples are visible evidence rather than a silent loss: for each interval the panel lists the worst skipped series the Server returned (scope, metric, skipped count, first and last skip) and states in its own copy that a skipped sample is counted here instead of being written, that the Server lists only the worst series while naming how many series lost samples in total, and that Report receipts and retry semantics are unchanged.
- Freshness follows the Server: the open page polls every 30 seconds regardless of the current state — a page that only polled while already paused could never show protection starting — refetches on demand, and reports a failed refresh as the last successful reading rather than as current data. Errors are the Server's sanitized reasons. The panel is Owner-only behind the same existing CSRF/Origin middleware as the rest of the Operations page, and no capacity DTO, URL, or error message carries a credential.
- Layout holds the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus, 44x44 touch targets, and local table scroll without primary horizontal page overflow.

### 15.16 Node metric history on the Node detail page: raw samples and aggregate tiers (issues #213 and #214, delivered)

Applies to `PAGE-ADMIN-NODE-DETAIL`:

- `PAGE-ADMIN-NODE-DETAIL` carries a `Metric history` panel reading the Owner-only `GET /api/admin/v1/nodes/{node_id}/metric-history`. The path is demonstrated layer by layer: the Node inventory, the Node detail page, and the panel's own series answer. The panel states the requested range, the answered range after clamping, the retained raw window in days, and the investigation horizon the answer is judged against, so the Operator can tell what the Server did answer rather than what was asked.
- One series is shown at a time, chosen from the five stored Node series (`process_cpu_percent`, `process_memory_percent`, `data_directory_percent`, `peer_inbound_count`, `peer_outbound_count`) with that series' own unit and axis; the range presets are 1 hour, 6 hours, 24 hours, 7 days and 30 days, because the stretches beyond the retained raw window are still answered by the aggregate tiers up to the 30 day investigation horizon. The metric and the requested range are part of the query key, so switching a series or a preset never renders another range's samples under the current one, and `Reload window` re-reads the same preset from the Server's current clock instead of silently sliding the window on every render.
- The plot folds the returned points — stored observations and aggregate buckets alike — into at most 120 time buckets, and every bucket keeps its minimum and maximum, so a spike inside a bucket is never averaged away and an empty stretch is never drawn as a value. A bucket holding a single observation is drawn as a vertical minimum/maximum whisker inside that column next to its point, so an isolated spike is never hidden by one plotted marker and nothing is interpolated across time nobody covered. The line breaks exactly where the Server reported a gap: a protection pause or a collection gap is drawn as an undrawn band and the curve stops at its edge, so no segment is drawn across a stretch nobody observed. It breaks equally where a bucket proved a hole inside its own stretch: the Server returns the widest interval it measured between two consecutive observations of that bucket, and when that interval reaches the threshold the Server's own cadence rule implies (three times the cadence the answer actually showed, floored at 120 seconds) — and for a bucket the answer holds no stored sample of its own for, that cadence is the bucket's grain divided by the observations the bucket counted, truncated to whole seconds exactly as the Server truncates it, so a bucket of seven observations over 300 seconds is judged at 42 seconds and a 126 second hole on the page as well as at the Server rather than at a rounded 43 seconds and 129 while the Server reports the hole the column is drawn as its own marker and the line stops on both sides of it, so the neighbours are never joined across a stretch the Server itself called unproven. The break is data driven rather than geometric: the observations are split at every silence the Server reported *before* they are folded into buckets, so a silence whose bracketing observations both fall inside one bucket cuts the line there instead of being drawn through, and each column is drawn where its own observations really are rather than at the centre of the bucket it fell in — a bucket centre is a position no observation in that column has to support, and a reported silence can cover it. A bucket the window holds no observation for is not plotted at all — the panel never draws `0`, never interpolates, and never extends the curve to the right edge of the window. The panel asks for the largest answer the Server carries (its `limit` is the Server's own sample bound, 20000), so a dense window is narrowed by the Server's own bound and the truncation notice instead of by a request that asked for less than it could have.
- What the tiers mean is said on the answer itself rather than left to the curve: when any returned point came from a bucket the panel prints a tier notice in the Server's own terms — stretches older than the retained raw window are answered by 1 minute and/or 5 minute buckets, each bucket keeps the count, the minimum and the maximum of the observations it summarizes, so a spike inside a bucket is still drawn, and no bucket is presented as a single stored sample. Under it, `Tiers in this answer` lists every stretch the Server reported with the tier that answered it, its point count, whether it was truncated, and its `from → to` bounds, including a tier that was consulted and holds nothing (`consulted, holds nothing`) — a stretch the raw window claims is never shown as an empty aggregate tier. A bucket whose own evidence proved a hole inside its stretch is not drawn as a closed stretch either: its square stands alone, the legend says how many of the drawn buckets measured such a hole, and the row names the interval it measured.
- A point served from a bucket is drawn as a square marker, never as a dot: a circle is one stored observation and a square is a bucket, and the legend under the plot says that ratio for the drawn points while the plot's own description repeats it. The bucket's own minimum and maximum still drive the column it falls in, so a spike the Server preserved survives both the folding into at most 120 columns and the drawing scale.
- A truncated answer and the way out of it are shown together: the notice says the window holds more points than one answer carries, that the newest ones are drawn and the older ones omitted, that the Server spends one budget on the whole answer while keeping the newest points of every tier so the omitted stretch is a seam and never a hole in the middle, and that the plot starts at the oldest point it actually has instead of inventing one at the window edge. `Load older points` asks for the Server's exclusive continuation coordinate; while an older page is shown the panel says the answer ends at that coordinate and that no point is skipped between two pages, and `Return to the newest points` goes back to the newest answer.
- The ledger behind the curve is shown independently of the window: the stored observation count since the first one, the first and last observed instants, the last receipt, the proven coverage against the window (stating that coverage is proven only between stored samples and never assumed across a silence or inside a bucket that measured a hole of its own), the replayed and corrected deliveries counted apart from observations, the points this answer actually carries together with the grain the answer was served at (`raw`, `1 minute` or `5 minutes`), the newest delay, the clock suspicion with the Server's note, the retained raw window with the requested start, and the investigation horizon, which states that older stretches are answered by buckets and never by a recreated sample. A delivery that restated an observation, or a carried last-good value, therefore cannot inflate what the series is claimed to have observed.
- What the Server could not answer is stated rather than filled in, and it is stated against the boundary that actually limits an answer — the 30 day investigation horizon rather than the retained raw window: `partial` (the request started before the horizon, so only the part inside it is answered) and `unavailable` (the request ends at or before the horizon, so no tier keeps evidence for it and only the ledger answers) are shown with the Server's own wording and the originally requested start. A truncated answer says the newest points were returned and the rest is reported, never dropped silently. A series the Node never reported is named as never reported, with no chart and no zero line, and that state is kept distinct from a series that is observed but has no stored sample and no bucket inside the current window; neither is rendered as `0`.
- Silences are listed as evidence: each entry names its kind (`Protection pause` from capacity protection or `Collection gap` when nobody observed), its start and end, its duration, the Server's own reason, and — for a pause — how many observations were skipped, so the pause #212 recorded is visible on the curve instead of being read as an outage.
- The newest observations are listed with a `Grain` column that names what each row is — `Stored sample`, `1 minute bucket` or `5 minute bucket` — beside the observed and received time, value, and the delay that belongs to that very row. A bucket row never passes itself off as one sample: under its grain it says how many observations it counted over how long a stretch — measured between the first and the last observation the bucket really holds rather than from its aligned window start, so a bucket holding one observation reports the count alone and never a span — (`6 observations over 4 minutes`), or, when the bucket's own evidence proved a hole inside it, names the widest interval it measured and says that no line is drawn across it, its own newest reading beneath the observed time, and its minimum-to-maximum envelope beneath the value, so a thin bucket is visible as thin and a spike the Server preserved is visible even where the bucket is drawn as one marker. A delay the Server reports as unknown stays `Unknown` rather than `0`, a clock-suspect observation carries its note, and the table scrolls inside its own region rather than widening the page. A delay that runs the wrong way — an observation stamped after the Server received it — is shown as its magnitude `ahead of receipt` instead of a negative duration or a flattened `0 seconds`, in the ledger and on the sample row alike, because that is a real clock disagreement the Operator has to see.
- The panel offers no control that writes history, edits a retention policy, pauses collection or deletes samples; it links to no raw payload or credential, and a failed read shows the Server's sanitized reason with `Try again` while a failed refresh keeps the last successful samples labelled as such instead of presenting them as current.
- It is Owner-only behind the same existing CSRF/Origin middleware, its query cache is generation-scoped so an identity change cannot show another session's series, and it holds the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus, 44x44 touch targets, and local table scroll without primary horizontal page overflow.

### 15.18 Storage by mount path: the mount list a storage series is read through (issue #216, delivered)

Applies to `PAGE-ADMIN-AGENT-DETAIL`:

- A storage series is named by the mount path the Agent reported, so section 06 `Host resource history` (`data-surface="agent-host"`) opens with a `Storage by mount path` card (`data-slot="storage-mounts-panel"`) reading the Owner-only `GET /api/admin/v1/agents/{agent_id}/storage-mounts`. The list is the Server's stored evidence of which paths this Agent has reported, and the card says so in its own words: every mount path this Agent reported, taken from the stored evidence rather than from a device identity, because a path is the whole name of a storage series, a path that changed is a different series, and two spellings of one filesystem are two series. `PAGE-ADMIN-NODE-DETAIL`'s `Host metric history` carries no list of its own and keeps the typed `Mount path` control of §15.17.
- The card states the Server's own read conditions before the table: the cadence the Server measured, or the fact that no cadence could be measured from the stored evidence and no silence can therefore be declared; the silence threshold that cadence implies; the order the Server answered in; the coverage limit this list carries; and the `answeredAt` instant with the `usedMetric` and `capacityMetric` names it read. The table (`data-slot="storage-mounts-table"`, inside its own `role="region"` `aria-label="Storage mount paths"` horizontal-scroll container) gives each path a row (`data-slot="storage-mount-row"` carrying that path and its state) with `Mount path`, `Observation`, `Used`, `Capacity` and a per-row button labelled `Read the storage series of <path>`; choosing it reads that exact path's `disk_used_bytes` series in the Host history panel below — the panel reads one of the path's two series at a time, the capacity series when the Operator picks `disk_total_bytes`, never both for a read it was not asked for — so the Operator never retypes a path the list already knows and no other path's series is substituted for it.
- The state shown is the Server's word rather than a verdict of the card's own: `Current` for `reported` — still observed at the cadence the Server measured, with the age shown — `Stale` for `silent`, silent for longer than that cadence allows, where the copy states that the readings already stored stay on the series, and `Unknown` for `unknown`, where no cadence could be measured and the card says exactly that instead of showing a duration. Every path of the answer is `unknown` while the Server is holding optional history back, and the card then names the pause the Server is holding — the readings already stored stay on the series — so a path that keeps being reported is never called stale for a pause it did not cause. Unknown is never rendered as `0`: a series never observed, a series with no reading in the retained window, and a series whose newest reading retention released before a boundary the Server names are each said in their own words, per path, out of the ledger the Server answered with.
- What the answer could not include is stated rather than hidden: the coverage bullet repeats the Server's own limit — this list carries at most `<mountLimit>` mount paths, the newest paths are answered and older ones are left out — and only when the Server set `truncated` does a status line add that this Agent holds more mount paths than the list carries, that the oldest of them are not in this answer, and that the paths shown are the newest ones. The card keeps the order the Server answered in (newest observed path first, ties settled by the path) rather than ranking the paths itself.
- The states around the table stay distinct: a `role="status"` line while the list is being read, an `Empty` state saying this Agent has reported no mount path yet so no storage series exists for it, and a `role="alert"` carrying the Server's sanitized reason with `Try again`. A failed refresh keeps the last good answer labelled as such rather than presenting it as current: the rows stay, the card's own tone stops claiming a current reading, and a `role="alert"` line (`data-slot="storage-mounts-refresh-error"`) names the `answeredAt` instant of the answer still on screen and offers `Try again`. Another Agent's mount paths are never rendered under this Agent.
- The card offers no control that writes history, edits a retention policy, deletes a mount path or claims which device a path belongs to. It is Owner-only behind the same existing CSRF/Origin middleware as the rest of the page, its query cache is generation-scoped with no placeholder, and it holds the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus, 44x44 touch targets and local table scroll without primary horizontal page overflow.
