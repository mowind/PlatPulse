## 1. Purpose and non-goals

PlatPulse WebUI presents operational truth from the Server and gives the Owner safe, audited configuration. Home is the read-only, Node-first monitoring surface — readable by anonymous Guests when Site Access Mode is Public and by authenticated Owner or Viewer sessions when Private; Admin is the Owner-only overview and configuration surface. It is a monitoring and administration surface, not a remote-control terminal.

### 1.1 In scope

- Home Dashboard: read-only Public Projections, Node → Node Detail, a compact six-statistic overview following the current Network selection with the Peer country map, and a current block interval derived from the latest two consecutive retained Block Summaries;
- Admin Dashboard: Agent/Node/Network configuration, global history window, Site Access Mode, Sessions, and Audit;
- responsive behavior at 360×800, 390×844, 768×1024, and 1280×800;
- current aggregate Peer Insight and selected-Node Peer History; Peer Snapshot/Presence data is Server-side and redacted, while raw Peer identities are never displayed;
- independent collection, freshness, value, and authorization states;
- REST-authoritative data loading and SSE invalidation;
- accessible forms, tables/cards, confirmations, errors, conflicts, audit links, and session transitions;
- deterministic Playwright-oriented acceptance scenarios.

### 1.2 Out of scope

These are current-surface exclusions. §15.1–§15.3 already route Agent enrollment guidance, editable Agent metadata, Agent Removal, and Agent Attention Acknowledgment; the items below that remain out of the current surface are remote control and the other deferred management pages.

- Agent, Server, SQLite, or evaluation implementation;
- a duplicated full Node Detail inside Admin;
- RPC Endpoint editing, RPC Endpoint failover, remote commands, restart, upgrade, Docker control, or terminal access;
- TUI, arbitrary scripts, SQL/DSL alert rules, or remote-control UI;
- Validator/Restore/Node Transfer/People/Recovery/Rotation management pages (their Server/API operations exist but are not currently routed); Notification test and Event/Delivery history are routed (§15.9); the routed Agent enrollment/metadata/removal/attention surfaces (§15.1–§15.3), the Incident history and detail pages (§15.6), the Operations ledger, Task detail, and Doctor pages (§15.11, issue #208), the Backup artifact surface (§15.12, issue #209), the Retention policy surface (§15.13, issue #210), the retention-execution and cancellation surface (§15.14, issue #211), the storage capacity and low-space protection panel (§15.15, issue #212), the Node metric history surface (§15.16, issues #213 and #214), the shared Host resource history carried by the Node detail and Agent detail pages (§15.17, issue #215), the `Storage by mount path` list on the Agent detail page (§15.18, issue #216), and the recorded sync and consensus state history of the Node detail page (§15.19, issue #217) are the standing exceptions, and Geo provider selection and the global Geo refresh are both routed on Settings;
- raw Peer identity/addresses, complete Peer Snapshot browsing, multi-tenant, HA, PostgreSQL, SSO/OIDC/TOTP/WebAuthn;
- runtime theme/script injection or a second frontend framework.

## 2. Authorities and vocabulary

Use the exact domain terms in `CONTEXT.md`. Current terms include: Host, Agent, PlatON Node, Node ID, RPC Endpoint, Network, Network Identity, Network Registry, Node Inventory, Active Node, Retired Node, Component Observation, Agent Report, Report Receipt, Current Projection, Block Summary, Peer Snapshot, Peer Insight, Peer History, Host Observation, Node Process Observation, Node Chain Observation, Node Observation, Node Health Summary, Validator, Validator Activity, Geo Provider, Geo Database, Geo Location Cache, Geo Insight, Attention Item, Public Projection, Site Access Mode, Invalidation Event, Home Dashboard, Admin Dashboard, Audit Event, Owner, Viewer, and Guest.

The WebUI must not invent synonyms that blur boundaries. In particular:

- Home is not “public admin”;
- Node Health Summary is not a WebUI-computed health color; the two-state Node marker on Home and Node Detail only reflects the Server-owned health word (§5.4);
- an Agent that stops reporting does not retire its Nodes;
- an Agent-level page must not merge independent Node chain observations;
- a successful Peer Snapshot/aggregate with zero peers is authoritative, not Unknown; omitted or unsupported peer capability is not an empty snapshot;
- recent Block History is bounded by the Server window and is best-effort: normal missed blocks remain absent, while explicit bounded Gap Backfill may recover eligible heights; neither path synthesizes zeroes or fabricated summaries.

### Approved Emerald composition refinements

- Home keeps the entire page at the existing **1280px cap** and preserves the Node grid’s `repeat(auto-fill, minmax(300px, 1fr))` column rules. At **1024px and above**, the overview allocates its statistics/map tracks about **4:3**: six equal summary cards in three columns by two rows at left, a complete contained **2:1** map at right. The 4:3 split holds each tile at the width the original four-card 2x2 grid gave it instead of stretching it, and the tiles keep its compact height: a 44px header row carrying the title and either the metric marker or the Breakdown control, then the value over a shared one-line stat slot — no footer row. The two cumulative tiles fill that slot with their own scope, coverage denominator and Partial marker, so all six tiles still share one height and one value baseline. Below 1024px, the map leads the band visually while the statistics keep their three-columns-from-640px / two-on-phones grid and their unchanged six-item DOM order. This human-approved presentation supersedes the earlier 37:61/232px band rather than widening the page or changing Node columns.
- Login displays the PlatPulse brand/Home link and the theme control in the same 56px Emerald header treatment and 1280px content column as Home. It exposes no Admin controls and does not mount the Home data shell. The existing form, authentication and redirect behavior are unchanged.
- Checkbox and radio visuals use 16px indicators inside 44px native input targets. Native grouping, labels, keyboard behavior, form state and disabled fieldsets remain authoritative; the visible indicator carries focus and invalid states. Forced-colors mode restores native rendering instead of relying on decorative colors.

### 2.1 Fixed status vocabulary

Use these terms in labels, accessible text, filters, and tests:

```text
Starting
Current
Stale
Error
Unknown
Disabled
Unsupported
Empty
Peer data current
Connecting to live updates
Live updates paused
You are offline
```

Node Detail uses `Successful` only as the display label for a successful Process collection; it does not assert current process liveness or freshness. The wire Collection State vocabulary is unchanged.

`Peer data current` is a scoped, low-weight healthy summary for Peer Insight; it does not replace the independent Collection, Freshness, or Value terms when those dimensions need explanation. `Online` and `N/A` are not generic replacements. Status communication always includes text and an icon or equivalent explanation; color is supplementary. An open SSE stream renders no transport notice: the positive transport state is deliberately silent because it changes nothing the visitor should do or believe. `Live updates connected` is therefore not part of this vocabulary and must not be reintroduced; only `Connecting to live updates` and `Live updates paused` are rendered and announced.

## 3. Surfaces and authorization

### 3.1 Home Dashboard

Home is a read-only surface for Public Projections. The current Public adapters consume the Network list, Node detail, Node history, metric history, selected-Node Peer History, and the country Geo data behind the Peer country map, where the DTO exposes them:

```text
Home
├── All Networks
│   └── Node list/cards
└── Node Detail
    ├── Shared identity Header, evidence-backed role/Activity, report age and Node ID copy
    ├── Six operational KPIs and Node Peer Country View
    ├── Chain state, Process collection/start/Node Data, and shared Host resources
    ├── Validator performance and diagnostics (confirmed Validator only; stale qualified)
    └── Latest 60 seconds: six shared charts
```

Home is organized Network → PlatON Node, never Agent → Node. Agent and Host topology belongs to Admin.

When Site Access Mode is Public, anonymous Guests can read the allowed Home projection paths; when Private, Home routes require an authenticated Owner or Viewer session. Every Active Node returned by the Public projection appears on Home. The Admin `visibility` field/filter is a legacy compatibility surface and is not used by current Public SQL to hide a Node.

Validator Activity is copied from the Server Public DTO, not inferred in React. `empty`/`not_found` is `observing`; a successful canonical value is `current` or `stale` according to Server freshness; an error with last-good Activity is canonical Activity with `stale`; success without Activity and `unsupported` are `unknown`. Canonical values include `candidate`, `active`, `producing`, `exiting`, `exited`, `verifying`, and `locked`.

For retired, deleted, forbidden, or unknown Nodes, Public routes use non-leaking unavailable semantics such as “This Node is no longer available.” Admin routes may distinguish forbidden from not-found.

### 3.2 Admin Dashboard

Admin requires an authenticated Owner session and is rejected for Viewer sessions. Human roles are Owner and Viewer; Guest is anonymous access, not a role or credential. A Viewer can log in and read Home in Private mode but sees the non-leaking Owner-required Admin outcome.

Admin groups:

1. Overview;
2. Agents;
3. Nodes;
4. Networks;
5. Validators (issue #218);
6. Settings;
7. Incidents (the Alerts group; issue #203);
8. Sessions and Audit.

Admin covers configuration and diagnostics; it must not duplicate Home's full Node Detail card/chart deck. The Admin Node endpoint returns the full administrative `AdminNodeDetail` DTO (health, freshness, process/data/RPC/Sync/Consensus/Peer diagnostics, identity, high-watermark/resync, and transfer context); the current page renders the approved administrative/diagnostic subset and does not turn it into a second Home view.

Every Admin render begins with `Checking access…` when authorization is unresolved. It never flashes data from a previous session.

The Admin shell shares Home's accepted Emerald visual language in both themes: a Slate-50-like canvas with quiet light panels in Light, the near-#141923 canvas with quiet dark panels in Dark, restrained outlines and shadow, high-contrast primary text, quiet secondary copy, and measured Emerald selection accents. It keeps its undecorated workbench background — the public gradient/grid never crosses its reading surface (the no-grid exception is explicit in §8.5.2 and §11.1). The Owner-only shell keeps its management information architecture: a persistent desktop sidebar and an accessible tablet/phone drawer with focus entry, Tab trapping, Escape and scrim close, body scroll lock, and focus restoration. Header and navigation controls remain at least 44×44 CSS pixels.

The first shared-theme proof is `PAGE-ADMIN-OVERVIEW` at `/admin`. It presents the Server-owned attention queue, Node Health Summary, and Agent inventory as independent Admin query/realtime surfaces. Starting, Empty, Error, Stale, last-good, Unknown, never-observed, Disabled, and Unsupported states remain explicit in text plus an icon/shape or equivalent explanation; no intended state is represented only by color or converted to a zero, false, or Healthy value. The implementation caveat in §8.4.5 still applies to database failures that are currently masked by some Admin handlers.

### 3.3 Authorization generation

Authorization changes create a new access generation:

1. stop the old Admin/Public stream as applicable;
2. abort old requests;
3. clear affected sensitive cache;
4. discard responses from older generations;
5. reload authoritative REST state under the new authorization.

Session revoke, expiry, and Site Access Mode changes (Public ↔ Private) all use this sequence. Tokens and business DTOs are never transferred between tabs; tabs synchronize only an access-generation signal.

## 5. Shared state model

The WebUI never reduces component collection, data age, available value, and authorization into one boolean.

### 5.1 Collection state

```text
Starting | Ok | Error | Disabled | Unsupported
```

- `Starting`: no usable observation for the current request yet;
- `Ok`: collection completed, with a value or authoritative empty result;
- `Error`: collection failed; last-good value may remain visible;
- `Disabled`: deliberately not collected/configured;
- `Unsupported`: capability is not available.

### 5.2 Freshness state

```text
Fresh | Stale | Unknown
```

Freshness, `observedAt`, `receivedAt`, `staleSince`, and reason come from Server REST DTOs. The WebUI formats them but never derives business freshness from `Date.now()`.

### 5.3 Value state

```text
Current | LastGood | AuthoritativeEmpty | None
```

- Error + LastGood remains visible with explicit error and age;
- Missing, Unknown, never-observed, and Disabled or Unsupported data without a retained successful value never render as `0`, `false`, or Healthy;
- a retained successful value, including an authoritative `0`, remains visible under collection Error, Starting, Disabled, Unsupported, or Stale freshness with an explicit last-successful qualifier;
- authoritative empty is not Unknown;
- recent Block History is bounded by the Server window and best-effort: absent blocks stay absent, never synthetic zeroes;
- host observation is collected once per Agent and referenced by Node views.

### 5.4 Node Health Summary

Severity and primary reasons are Server-owned. The WebUI presents the Summary and dimension reasons; it does not reimplement health policy or merge Node observations at Agent level.

Where Home or Node Detail mark a Node by name, a two-state marker sits before that name: Healthy is green and every other state - Unhealthy, Unknown, and never-observed - is grey. The marker carries the Server-owned health word as its accessible name, so the compact presentation never drops Healthy, Unhealthy, or Unknown from the accessibility tree; it does not replace the Summary, and an exceptional reason stays visible as text. Admin keeps the full Server-owned severity presentation (§8.4.3).

### 5.5 Server-side state machines without current pages

Alert Rule/Incident/Silence/Maintenance evaluation and long-running Operation states are implemented in the Server and exposed through Admin APIs. The read-side Incident history and detail pages, including the Owner acknowledgment, are routed per §15.6 (issue #203), and Alert Rule read/edit/preview with Network/Node overrides is routed per §15.7 (issue #204), with Silence and Maintenance Window management routed per §15.8 (issue #205), and the Operations ledger/Task detail plus Doctor pages consuming the recorded Operation DTOs per §15.11 (issue #208); storage capacity and low-space protection is likewise a Server-owned state machine surfaced read-only on the routed Operations page per §15.15 (issue #212), the mount list a storage series is read through is likewise read from the stored coverage ledger on the Agent detail page per §15.18 (issue #216), and the recorded state history the Node detail page reads is the Server's own state log with its per-series ledger per §15.19 (issue #217); no page resolves or suppresses the underlying state machines. They remain independent of the WebUI's Node Health Summary; a future page must consume the typed DTOs rather than recreate those state machines in the browser.

## 6. REST, query cache, and SSE

### 6.1 Production seam

```text
Generated OpenAPI client
  → typed API adapter
  → query/mutation and SSE invalidation layer
  → page/view components
```

The generated client is imported through the project client singleton. Its `{data, error}` result is handled explicitly; bodyless 204 responses are treated according to generated types and do not assume `null`.

The adapter owns:

- request ID propagation;
- session/CSRF handling;
- typed error-envelope normalization;
- access generation tagging;
- response revision comparison;
- transport versus domain error distinction.

### 6.2 Query namespaces

Public and Admin caches must not share query keys or cache objects:

```text
public:<resource>:<scope>
admin:<resource>:<scope>
```

The exact implementation key format may vary, but the namespace boundary is mandatory. Site Access Mode and session transitions clear affected keys before new responses are rendered.

### 6.3 Realtime flow

```text
route open
  → REST query
  → connect surface-specific EventSource
  → receive invalidation/reset
  → discard older revision
  → invalidate exact query key
  → REST refetch
```

SSE contains invalidation/resource identity or collection reset, not authoritative business DTOs. One stream exists per surface shell per browser tab. High-frequency invalidations are coalesced. Hidden tabs reduce non-critical refetch while visible critical changes remain prompt.

The Public/Admin event endpoints accept cursor recovery through the `after` query parameter or the `Last-Event-ID` header (the reconnect header takes precedence when both are supplied). Responses are `text/event-stream`; each emitted event uses the `invalidation` event name, a numeric event id/cursor, and JSON `data` with `version`, `eventId`, `resource`, optional `resourceId`, `revision`, and optional `reset`. A first connection without a cursor starts after the current buffered sequence because REST has already supplied the snapshot; the browser should send the last received cursor when reconnecting and discard/reconcile events older than its current authorization generation.

SSE connection status is visible but does not cover valid content. Public Home and Node Detail surfaces show `Connecting to live updates` while connecting and `Live updates paused` after disconnect; an open stream renders no transport notice at all, because a connected stream changes nothing the visitor should do or believe. Browser/network loss additionally uses `You are offline` when the browser signal is authoritative. The compact Admin header retains its existing `Starting`/`Current` transport labels so public transport wording does not increase Admin information density. These transport labels never certify REST refresh success, observation freshness, Agent liveness, or Node Health. The current generated OpenAPI records the stream operation but does not fully describe every cursor/header/event field; runtime `realtime` behavior is the authority for replay.

SSE updates must preserve filters, sorting, scroll, expansion, and ordinary drafts. They do not reorder a list merely because a timestamp changed.

### 6.4 Mutation flow

- no optimistic business state;
- no automatic mutation retry or replay;
- success immediately invalidates and refetches authoritative REST;
- failure preserves drafts and shows field/page errors;
- conflicts refetch current authoritative state without overwriting drafts;
- access changes abort old requests and discard old responses.

### 8.3 Settings (`PAGE-ADMIN-SETTINGS`)

- renders one Settings heading with an ordered History Window, Site Access Mode, then Geo provider module inside one left-aligned constrained surface (see §8.6);

A typed phrase, if displayed, is client-side friction only; it is not a Server security field;

- Geo provider offers only the providers this Server actually implements: Disabled, Local MMDB, IPinfo, and GeoJS. Disabled schedules no lookups at all; Local MMDB resolves countries from the operator-provided GeoLite2 Country database on the Server; IPinfo sends each observed Peer public IP to the fixed third-party endpoint `https://ipinfo.io/{ip}/json` and keeps only the returned country code; GeoJS sends it to the fixed third-party endpoint `https://get.geojs.io/v1/ip/geo/{ip}.json` and likewise keeps only the returned two-letter code. The option list, the disclosure, and the availability reason all come from the Server rather than from a hardcoded client list;

The browser composes no disclosure of its own, so the destination the Owner is shown and the endpoint a request is really sent to come from the same Server constant and cannot drift apart;
- Geo provider shows the effective state (Disabled/Current/Stale/Error), where the current provider sends Peer addresses, whether a local database is configured, the cached country count, the pending lookup count (not scheduled while Disabled), the last success time, and the Server-owned rate-limit window while an external provider is backing off; an option the Server reports unavailable is rendered disabled with the Server-provided reason and cannot be submitted; success reports the Audit Event identifier;
- the Geo provider card carries the Owner-only global refresh (issue #136): the button submits the Server-owned mutation and the card then renders the Server's real per-address progress rather than treating the accepted request as success. It states that the action re-resolves every public Peer IP any Network currently references even when a cached result is still valid, that lookups are counted per distinct IP address, and that the Peer country map counts Peer records per Node. While the Server reports the run `running` the button is disabled and the counts advance; a terminal run renders `completed` or `stopped early` with the Server-owned `abort_reason`, the resolved / without-a-country / failed counts, the rate-limited count when non-zero, and the number of Peer records referencing those addresses. An empty scope is rendered as having nothing to re-resolve, and a run made under a different provider than the current selection says so instead of appearing as the new provider's result. Disabled or otherwise unavailable Geo renders the refresh disabled with the Server's `refresh_unavailable_reason` instead of a fake success. Progress stays truthful without a live SSE stream because the diagnostic query polls only while a run is running;
- the Settings cards stack on narrow viewports, preserve 44×44 CSS pixel targets, and never cause primary horizontal page overflow.

The retired `/admin/history-window` and `/admin/site-access` routes are not redirected; they resolve through the Admin Section not found fallback. This is a page-level SPA outcome and does not guarantee an HTTP 404 response from the Server.

### 8.4 Overview (`PAGE-ADMIN-OVERVIEW`)

The Overview is the Owner's triage surface, not a second copy of the Nodes or Agents inventory and not a remote-control console. It borrows Komari's compact scanning density, light operational canvas, restrained borders, strong primary numbers, and quiet secondary copy without importing Komari's database, subscription, traffic-ranking, pricing, latency-probe, or remote-operation model. The accepted order is `Attention -> Summary -> Node Health -> Agent inventory`.

#### 8.4.1 Composition and navigation

1. `Attention queue` is the first full-width panel. It presents current Server-derived Attention Items and their safe next actions.
2. Four compact summary cards follow: `Agents`, `Active Nodes`, `Retired Nodes`, and `Networks`. The cards use explicit counts and text legends, optionally with an accessible segmented bar; they do not use a single online/healthy percentage or circular score that can hide Unknown or Retired state.
3. `Node Health Summary` presents at most the ten highest-priority Active Nodes. The complete inventory remains at `/admin/nodes`.
4. `Agent inventory` presents at most the six highest-priority Agents. The complete inventory remains at `/admin/agents`.

Each summary card is one semantic link with a visible focus state and no nested action:

```text
Agents        -> /admin/agents
Active Nodes  -> /admin/nodes?lifecycle=active
Retired Nodes -> /admin/nodes?lifecycle=retired
Networks      -> /admin/networks
```

The primary values are:

```text
Agents:       total; online / offline / unknown
Active Nodes: active; healthy / unhealthy / unknown
Retired Nodes: retired
Networks:     total; with Network Identity Mismatch
```

`Active Nodes = healthy + unhealthy + unknown` and `total Nodes = active + retired`. Retired Nodes are excluded from live health buckets and Attention Items. `AdminOverviewSummary` has no `published` metric. Node list/detail DTOs and the Nodes page retain `visibility` as a legacy compatibility/diagnostic field and filter; current Public SQL does not use it to hide Home Nodes, so Site Access Mode remains the effective site-wide anonymous-access authority.

#### 8.4.2 Attention queue

**Baseline versus target:** the current kind + subject IDs and unacknowledged queue below are implemented behavior. §15.3 adds durable Agent Attention Acknowledgment and occurrence/evidence boundaries; the current IDs alone cannot permanently dismiss a type without also swallowing future occurrences.

An Attention Item is a current Server-derived prompt, not an Alert Incident, Notification, Audit Event, or browser-computed warning. The REST DTO keeps each problem independent with a stable `kind + subject` identity. The typed kinds are:

```text
agent_offline
agent_spool_fatal
agent_spool_overflow
agent_report_gap
agent_security_event
agent_shutdown_incomplete
agent_inventory_rejected
node_unhealthy
node_health_unknown
node_resync
node_identity_mismatch
```

Typed severities are `critical` and `warning`. Critical means a confirmed availability, data-integrity, or security risk:

```text
agent_spool_fatal
agent_spool_overflow
agent_security_event
agent_inventory_rejected
node_unhealthy
node_identity_mismatch
```

Warning means investigation is required without a confirmed critical loss:

```text
agent_offline
agent_report_gap
agent_shutdown_incomplete
node_health_unknown
node_resync
```

A new Agent with no accepted report is Unknown rather than Offline. A new Active Node remains Starting during the Server-owned first-observation grace period and does not produce `node_health_unknown` until that grace period expires. Unsupported, Disabled, stale, never-observed, and other incomplete states do not automatically become Critical. Network Identity Mismatch remains distinct from RPC Error and produces its own critical item because mismatched Block History must not merge into the registered Network.

The Server orders individual items by severity (`critical`, then `warning`), most recent authoritative `observed_at`, stable subject label, and stable identity. The WebUI groups items visually by `subject_kind + subject_id` without discarding or recomputing any item. A group uses its highest severity, exposes its primary issue, and offers expansion for additional issues. The panel reports both counts, for example `6 issues across 3 subjects`. Group order is highest severity, latest authoritative observation, subject label, and stable subject identity.

The first six subject groups are visible by default. `Show N more` and `Collapse` reveal or hide the remainder without losing the current items. Safe navigation is derived only from typed subject kinds and known same-origin Admin routes; the Server does not supply arbitrary URLs. Unknown future kinds remain visible with an Unknown fallback and no guessed link.

Each row/card is exactly one Active Node and preserves Node scope. An Agent monitoring multiple Nodes produces separate Node rows/cards; block, transaction, consensus, peer, and error observations never merge into an Agent-level chain view.

View Node

Boot IDs, complete credential state, shutdown evidence, complete Host observations, and detailed diagnostics belong to Agent Detail.

The default priority is Agents with critical diagnostics, then offline, unknown, and online Agents, with stable Agent ID tie-breaking. At most six cards are shown, followed by `View all Agents`.

#### 8.4.5 Data, time, and partial states

The page retains three independent Admin query surfaces:

```text
GET /api/admin/v1/overview -> Attention and summary response
GET /api/admin/v1/nodes    -> Node Health Summary
GET /api/admin/v1/agents   -> Agent inventory and Host diagnostics
```

Failure of one surface never hides successful data from another. Attention and summary are returned together by the Overview handler, but the current handler builds them with independent database reads and provides no cross-resource point-in-time/transaction snapshot guarantee. Initial loading uses explicit `Starting` text, optionally accompanied by static skeleton shapes. A refetch failure can preserve LastGood content and says that the last successful values remain visible. Each failed surface owns its own `Try again`. SSE carries only invalidation/reset; `Live updates paused` or `You are offline` never clears valid REST content.

Implementation caveat: the current `GET /api/admin/v1/agents` handler maps its initial list-query failure to `200 []`, and Agent Detail maps some nested query failures to `0`, `[]`, or `None`. These are degraded implementation behaviors, not authoritative Empty/zero values; the UI must avoid presenting them as healthy or complete, and Server-side error propagation remains follow-up work. Runtime Public/Admin handlers can also return typed 503/500 errors not yet enumerated in every generated OpenAPI operation; clients must handle generic non-2xx responses.

Visible timestamps are relative, such as `2 minutes ago`, with an accessible absolute UTC value. Agent reports may show `Report #128 - 5 seconds ago`. The WebUI formats Server timestamps but never uses browser time to derive Freshness, liveness, grace periods, Health, or Attention severity.

The current Settings link only manages Server-wide History Window/Site Access Mode; it does not edit an Agent's local inventory. The page cannot configure an RPC Endpoint, start an Agent, create a local Node Inventory, expose an Enrollment workflow, enable fake data, or offer one-click initialization.

#### 8.5.4 Diagnostic evidence semantics

§15.3 refines prominence after explicit Owner acknowledgment: acknowledged Agent evidence leaves the prominent warning area, but actual liveness/health and expandable evidence remain available. Being online alone still never dismisses recorded evidence or implies recovery.

- `sequence_gap_count` counts recorded sequence-gap intervals, not missing reports, currently unresolved gaps, or active failures. Label the historical interval count explicitly.
- `security_event_count` is an accumulated recorded-event count without per-event resolution/timestamps in this summary. It does not prove an ongoing incident or credential failure.
- Queue, in-flight, fatal, dropped-range, and delivery-error evidence remain distinguishable. The latest Host snapshot can retain a last error or historical dropped range; that alone does not prove a current failure. Use available observation metadata without inventing per-field recovery/freshness or client severity rules.
- No Host observation, spool not yet observed, and an authoritative zero queued count are different states. Unknown is never converted to zero or normal.
- Keep concise indications of important diagnostic evidence in the summary; move long safe error text and secondary details to the existing detail route. Do not suppress critical evidence because reporting status is `Current`.

## 9. Content, privacy, and redaction

### State and realtime acceptance

The UI keeps collection state, freshness state, value state, and authorization state independent. It renders the fixed user-facing vocabulary from this document: Starting, Current, Stale, Error, Unknown, Disabled, Unsupported, Empty, Connecting to live updates, Live updates paused, and You are offline.

- Initial route loads show a meaningful Starting/loading state and do not fabricate values.
- A successful observation may show Current or an authoritative empty value. A successful Peer Snapshot/aggregate of zero is displayed as zero, not Unknown; omitted/unsupported peer collection remains distinct.
- An Error or Stale observation may retain LastGood data, but the UI must show the error/stale reason and age/freshness supplied by the Server. It must never convert Unknown, stale, never-observed, Disabled, or Unsupported into 0, false, or Healthy.
- Node, history, metric-history, and validator requests fail independently. A failed optional module does not erase the Node summary or unrelated successful modules.
- A normal SSE invalidation preserves the currently displayed Node and view context while the exact Public resource is refetched. A reset, authorization transition, Node ID change, or access recheck clears affected sensitive projection state before the next render and may show a revalidation state.
- SSE carries invalidation/reset signals only. REST remains authoritative for all displayed business values. A disconnected stream announces Live updates paused; an open stream announces nothing, because the positive transport state is silent; browser-offline state may additionally announce You are offline.
- Retired, deleted, forbidden, or unknown public Nodes use non-leaking unavailable copy and never reveal whether a protected record exists.

### 15.1 Agent enrollment and metadata

Applies to `PAGE-ADMIN-AGENTS` and `PAGE-ADMIN-AGENT-DETAIL`:

- Provide an Add Agent entry that creates a short-lived, single-use Enrollment Token and presents local enrollment instructions. Generating a token does not create an offline placeholder Agent; the list gains the Agent only after successful enrollment.
- Present the secret only in the authorized enrollment interaction; do not place it in URLs, logs, persistent browser storage, generic query caches, Audit payloads, or Public state. No remote installation/start/stop command is executed by the UI.
- Support Server-backed display name and notes editing. Keep the stable Agent ID visible/copyable; do not make the ID, actual Host identity, receipt-derived liveness, or local collection configuration editable. A name is not inferred from a Node or diagnostic field.
- Keep credential revocation separate from Delete Agent. This scope does not restore dedicated Recovery/Rotation or other deferred pages. Exact added API shapes and form placement remain implementation work, not fabricated extensions of today's DTO.

### 15.2 Permanent removal and clear consequences

Applies to Agent Detail and the Nodes inventory/Node Detail management surfaces (`PAGE-ADMIN-AGENT-DETAIL`, `PAGE-ADMIN-NODES`, `PAGE-ADMIN-NODE-DETAIL`):

- Agent deletion confirms the specific Agent and Server-authoritative list of owned Nodes, revocation of all credentials, and permanent removal of those Nodes' monitoring history. Pending Transfer blocks removal until handled. A changed ownership/impact set requires refetch and confirmation, not deletion of unseen newly assigned Nodes.
- Node deletion is explicit Owner judgment, available for invalid Active as well as Retired Nodes; do not invent an automatic offline threshold or label failure itself as a lifecycle. Retain existing rename; add no Admin create-Node or Endpoint editor.
- Use explicit destructive copy such as `Permanently delete Node`. Explain that the Node leaves Home/current monitoring, its observations/history/Links are deleted, the same Node ID cannot return, and re-monitoring requires a new locally configured Node ID. Minimal deletion identity, necessary Audit and existing Incident evidence remain; independent Validator history is not erased.
- Explain what will not happen: the remote Agent/Node process is not stopped, local configuration is not changed, shared Node/Host/Network/Validator data is not cleared, and no recovery is asserted. Agent removal includes the stated credential revocation and owned-Node purge; it is not merely hiding a row.
- Confirm/Cancel, busy guards, field/page errors, conflict recovery and authoritative completion are required. Do not optimistically remove records or call a queued/incomplete purge a completed deletion. On completion, invalidate/refetch affected Admin lists, overview and summaries; an open Public view must stop displaying the removed Node and use the existing non-leaking unavailable outcome for its detail URL.
- Preserve context for unaffected rows and filters. Failure leaves an actionable error and authoritative state, not an empty success screen. Server permission checks and Audit are mandatory; a typed phrase, if used for friction, is not the authorization boundary.

### 15.3 Shared confirmation of Agent Attention Items

Applies to `PAGE-ADMIN-OVERVIEW` and `PAGE-ADMIN-AGENT-DETAIL`:

- The product action is `Acknowledge` (确认提示), not `Resolve alert`, `Clear history`, or `Silence`. Production copy remains consistently English; the Chinese wording here identifies the confirmed intent, not a localization feature.
- Overview provides per-item acknowledgment for Agent subjects. Agent Detail provides individual acknowledgment and `Acknowledge current Agent items`. No Node acknowledgment or permanent type-disable action is added.
- A bulk action covers only the Agent items/evidence boundaries explicitly shown for that action, not all hidden diagnostics, child Node items, or new evidence arriving after the displayed snapshot. Server confirmation is shared across Owners, both surfaces, sessions and restarts; browser local storage is not the authority.
- On authoritative success, that occurrence leaves the prominent attention/warning area. Evidence remains available through deliberate diagnostic disclosure; actual liveness, health, freshness and component failures remain truthful. Even a continuing fault may be acknowledged without making an offline Agent look online or changing Incident/notification policy.
- Ordinary refreshes, unchanged reports, re-login and restarts never resurrect an acknowledged occurrence. New evidence or a genuinely recovered-then-recurring fault requires fresh attention. Unknown/stale data is not recovery. The Server must distinguish occurrences/evidence; the current `kind + subject` ID and presentation timestamp alone are insufficient.
- A failed acknowledgment keeps the item actionable. A stale request must not swallow newer unseen evidence. Successful concurrent acknowledgments must converge after authoritative refetch; don't replay stale responses into the queue or transfer business DTOs between tabs.
- Existing Agent Detail warning predicates include historical and current evidence outside the Overview queue. These surfaces must converge on Server-owned acknowledgment eligibility/evidence boundaries rather than independently recreating acknowledged warnings from cumulative counters. Raw safe diagnostics remain available but are not re-promoted as unacknowledged prompts.
- Audit exposes who acknowledged which Agent evidence and when, not secret-bearing raw diagnostics. The acknowledgment operation does not disable Alert Rules, change Incident state, delete evidence, pause notifications or create a recovery event.

### 15.4 Validator presentation and deleted-subject history

- Remove manual Validator selection, role editing and manual-link fallback from the target design. Validator detail and statistics remain independently meaningful; Public rendering consumes Server-projected automatic correspondence rather than guessing in React.
- Show Current Validator Status separately from Node Health and consensus participation. Preserve locked/exiting qualifiers when validity is confirmed, explicit non-current status after completed exit/authoritative absence, and Unknown/Stale when evidence cannot establish a fresh conclusion. Do not reintroduce manual role badges. Activity placement follows existing page composition; this does not authorize an unrelated Home redesign.
- The one-time model migration clears old Validator Link/history/snapshot/daily/monthly data, not Node monitoring history. A temporarily Unknown or lower selection total is legitimate; no client fallback to old manual results, fabricated full-month coverage, or forced zero lifetime totals. See [Provider](validator-provider.md) and [metrics](validator-metrics.md) for the target evidence contract and pending primary-source verification.
- Daily Node deletion does not clear independent Validator history, even after its last monitored Node is removed. Existing Incident evidence is retained and marked with deleted-subject context, excluded from current actionable problems, not relabeled as known recovery. Cancel unsent subject notifications; delivered messages cannot be recalled.
- Current problems disappear from Attention when their predicates genuinely clear; historical prompts can remain until acknowledgment. Sustained known recovery resolves a durable Incident without deleting it. The routed Incident history page is delivered by §15.6 (issue #203); deleting a subject keeps the original Incident facts and open/resolved state, annotated rather than relabeled as recovery.

### 15.6 Incident history and durable acknowledgment (issue #203, delivered)

Applies to `PAGE-ADMIN-INCIDENTS` and `PAGE-ADMIN-INCIDENT-DETAIL`:

- The routed Incidents page lists one row per Incident occurrence with its Server-owned state, severity, subject, Rule key/version, sequence, opened/resolved/subject-deleted times, and durable acknowledgment; the row's disclosure shows that occurrence's durable acknowledgment and a link to inspect it, and the detail shows the full opened/resolved evidence plus the current Rule evaluation and the matching Silence/Maintenance suppressions. The WebUI rewrites no evidence, infers no cause, and never fabricates recovery for Unknown, Stale, disabled, or deleted subjects.
- The list answers one occurrence range and can walk further back inside it (issue #203 review C3, delivered with issue #220). `?from=&to=` is the range the Server applies — an Incident is in it when it opened inside it or was still open when the range started — and both ends travel together, so one end alone is refused with `alert_validation`; with no range the answer is the newest occurrences the filters match. A range wider than 30 days is refused (`MAX_INCIDENT_RANGE_SECS`, crates/platpulse-server/src/http/alerts_admin.rs:1956). `INCIDENT_PAGE_LIMIT = 200` (platpulse-web/src/pages/AdminIncidents.tsx:90) is now a page size rather than a ceiling: the Server counts `total` without the cursor and `returned` with it, and a truncated answer carries its own exclusive cursor `<opened_at>|<incident_id>` (`alert_incidents`, crates/platpulse-server/src/http/alerts_admin.rs:2015). `Load older occurrences` follows that coordinate and `Back to the newest occurrences` gives it up (platpulse-web/src/pages/AdminIncidents.tsx:515 `setCursor`); a changed filter or window drops the cursor instead of carrying it across a count it was not taken under. The cursor is the Server's coordinate and is never re-derived from this browser clock (`IncidentFilters`, platpulse-web/src/api/admin.ts:2331, forwards `from`/`to`/`before`). The page states what it holds in the Server's terms (`data-slot="incident-page-facts"`, platpulse-web/src/pages/AdminIncidents.tsx:750): "The Server answered this page without an occurrence range, so it holds the newest occurrences the filters match." or "Occurrences of the range <from> to <to>: an Incident is in it when it opened inside that range or was still open when the range started.", then "Every occurrence the filters match is in this answer." (or "… from this coordinate onward is in this answer."), "The filters match <total> occurrence(s) and this page carries <n> of them, newest first.", or, for a page that matches nothing, "The filters match no occurrence here, which is an empty answer rather than a zero value." The Node investigation page enters this list with the window it read (`/admin/alerts/incidents?subject=node&subject_key=<node_id>&from=<window.from>&to=<window.to>`, platpulse-web/src/pages/AdminNodeInvestigation.tsx `incidentsHref`, labelled `Incidents for this Node in this window`), so the occurrence predicate the investigation was answered under is the one the list applies rather than a clock the reader's browser supplies (issue #220).
- The list accepts an exact `subject_key` (paired with `subject_kind`) narrowing. Node and Agent detail carry a contextual "Incidents for this Node/Agent" shortcut into `/admin/alerts/incidents?subject=<kind>&subject_key=<id>`, and the page shows the active Subject key as a clearable chip, so an Owner can move from an observed problem to that subject's Incident history (parent #202 Story 2; issue #203 review B2).
- A long unbroken Owner username wraps inside its own list cell and detail paragraph rather than overflowing the page, verified at the 360/390 viewports (issue #203 review B1).
- `Acknowledge` records the first successful Owner request as the durable, shared confirmation of that occurrence: who confirmed it and when. It does not resolve the Incident, mark the subject healthy, change recovery, or suppress notifications, and it stays separate from Agent Attention Acknowledgment.
- The confirmation is reachable from the list and the detail, always behind an explicit confirmation step. Refresh, a second Owner, and a Server restart show the same authoritative identity and time; a repeat or concurrent request reports the first identity instead of replacing it, and the winner is visible to every Owner client.
- A resolved occurrence keeps its acknowledgment. A genuinely recurring fault opens a new unacknowledged occurrence with its own sequence; Rule edits/disabling and subject deletion never silently resolve or acknowledge an Incident.
- Only Owner authorization applies, through the existing CSRF/Origin boundary, with Audit; the confirmation is never stored in browser local storage.

### 15.7 Alert Rule management and inherited overrides (issue #204, delivered)

- /admin/alerts/rules lists the typed Alert Rule catalog and /admin/alerts/rules/:ruleKey reads one Rule: the baseline enabled flag, severity, and schema-declared condition parameters, the immutable version history in alert_rule_versions, the per-scope overrides, and the current evaluation state per subject. The catalog is fixed: the pages read and edit existing keys and never create, delete, or accept a free-form DSL.
- The detail page shows the effective resolution explicitly instead of flattening it: the baseline applies to every subject, a Network override narrows it for that network, and a Node override narrows it for that node, with the most specific value winning. Only Network and Node scopes are supported; there is no arbitrary Agent or Host override. An override row renders an unset field as Inherited rather than repeating the baseline value, so inheritance stays visible as inheritance.
- Editing writes enabled, severity, and the condition parameters the Rule schema declares (threshold only where the schema declares one). Every save carries the composed expectedVersion the page was read at: the baseline version for a baseline edit, and the same composed version for an override save. The composed version is the concurrency token for the whole aggregate: a baseline edit and an override upsert or removal each append an immutable composed revision in alert_rule_versions and advance alert_rules.version, and the page adopts the revision its own write produced before offering the next save.
- The Server rejects a save whose expectedVersion no longer matches the stored composed version with 409 and alert_rule_version_conflict. The page then shows "This Rule changed since you read it", disables saving, and requires the Owner to reload the current configuration and review before saving again. A background refetch never silently promotes the stored version into the open draft, so a genuine stale write is always surfaced rather than smuggled through. Because an override change advances the same version as a baseline edit, two Owners editing different overrides of one Rule cannot silently overwrite each other either.
- Preview evaluates the unsaved draft against every eligible subject and reports each subject current state, projected state, whether it would fire, and the note. It is not a save: it creates, resolves, and acknowledges nothing, and it does not promise that an Incident will open immediately.
- Rule edits and disabling never rewrite an Incident opening rule version or opened evidence and never clear an acknowledgment. The Incident detail keeps the opening facts and projects the current effective Rule configuration separately; an unresolvable current configuration is shown as unknown, never as a disabled Rule, a recovered subject, or a healthy one.

- Every disclosure the Server answers with has its own paragraph: coverage (`validator-trend-coverage` — `partial` is read from the answer's own numbers, so a proven silence inside the answered stretch and a stretch that is merely short of the requested window are two different sentences and the second never claims a day is missing), the answered-versus-requested stretch (`validator-trend-stretch`, "the days it does not reach are not silences in this answer"), the clipped page (`validator-trend-truncated`, naming the exclusive continuation instant and stating no day is answered twice), stored rows formed in another timezone (`validator-trend-foreign`), the association-history state (`validator-trend-associations-notice`) and the counter semantics (`validator-trend-counters`) — reward and block values stay labelled cumulative, stake is stated as the balance the Provider reported at that sample, and none of them is ever presented as period earnings or net profit.
- The detail list prints `Configured timezone`, `Coverage`, `Requested`, `Answered`, `Observed / missing`, `First / last observed` (an absent day reads `Unknown`, never a date) and `Association history` (`Partial · <n> deleted Node(s)` when the Server still holds history it can no longer resolve). `Silences in this stretch` lists each gap as a local-day range with its honest wording and reads `No configured local day of the answered stretch is missing a snapshot.` when there is none. `Stored days` is the `data-slot="validator-trend-points"` table with `Local day`, the real `UTC window` and its hour width, `Month`, `Rank`, `Stake`, `Delegators`, `Reward (cumulative)`, `Blocks (cumulative)`, `Sample time` (which instant chose the day — the Provider timestamp or `Server receipt (fallback)` — plus all three named instants `Sample`/`Provider`/`Receipt`, where a Provider timestamp the observation never carried reads `Unknown` instead of borrowing the receipt, alongside the `Delay` cell that reads `Unknown` whenever no delay can be computed) and `Source`. `Configured months` maps each configured month to the UTC instants its boundaries really fall on. Both tables are `data-stack` with `scope="col"`/`scope="row"` headers.
- `Node associations` lists only the intervals that still resolve to a surviving Node, each linking to `/admin/nodes/:nodeId` with its origin, `validFrom → validUntil` (or `open interval`) and an `Open`/`Ended` badge. An empty list states that the deleted Node intervals "are unavailable rather than never having existed" whenever the history is partial, so Story 68's promise stays visible where the trend is read: purging a Node removes the association and never the shared Validator's stored days.
- The card is Owner-only through the existing `/api/admin/v1` guards (real Origin/CSRF, sanitized errors with `Try again`, `role="alert"` on failure, `role="status"` while loading, and a distinct alert when a refresh fails while the last successful answer is still shown). Every control is a 44px touch target, the panel never widens the page at the fixed 360/390/768/1280/1440 viewports in Light and Dark, and the stored-days table scrolls inside its own container. The same five viewports × both themes are also captured as evidence screenshots under `docs/visual-migration/emerald/validator-trend-219` (`platpulse-web/e2e/validator-trend-acceptance.spec.ts`): evidence for review at the fixed matrix, never a gate — no baseline is recorded and no screenshot is compared (ADR 0002).

### 15.22 Node investigation over one UTC window (issues #220, #221)

Applies to the new `PAGE-ADMIN-NODE-INVESTIGATION` (`/admin/nodes/:nodeId/investigation`) and to the entry into it from `PAGE-ADMIN-INCIDENT-DETAIL`:

- The Server half is `GET /api/admin/v1/nodes/{node_id}/investigation` (crates/platpulse-server/src/http/admin.rs:2942 `admin_node_investigation`, query `AdminInvestigationQuery { window, from, to }` at crates/platpulse-server/src/http/admin.rs:2888, route registered at crates/platpulse-server/src/http/admin.rs:8261-8267 as "The one UTC window every evidence route above is read inside (#220)"), its module crates/platpulse-server/src/investigation.rs, its test crates/platpulse-server/tests/node_investigation.rs, and the regenerated client (platpulse-web/src/api/generated/sdk.gen.ts:495 `adminNodeInvestigation`, types at platpulse-web/src/api/generated/types.gen.ts:2537-2968). The Web half is delivered too: the page platpulse-web/src/pages/AdminNodeInvestigation.tsx, routed at platpulse-web/src/App.tsx:180 and entered from the `Investigate this Node` link on the Node Detail header (platpulse-web/src/pages/AdminNodes.tsx:615) and from the occurrence card of the Incident detail (platpulse-web/src/pages/AdminIncidents.tsx:964), its pure-logic module platpulse-web/src/nodeInvestigation.ts, its unit tests platpulse-web/src/pages/AdminNodeInvestigation.test.tsx and platpulse-web/src/nodeInvestigation.test.ts, and its browser acceptance platpulse-web/e2e/node-investigation-acceptance.spec.ts. The selectors named below are the ones the page really renders, and this section is the contract it is held to.
- The page is one UTC window and nothing else. The window control is a `role="group" aria-label="Investigation window"` of the presets the Server itself travels with every answer (`supported_presets`: `1h`/`Last hour`, `6h`/`Last 6 hours`, `24h`/`Last 24 hours`, `7d`/`Last 7 days`, `30d`/`Last 30 days`, from `WINDOW_PRESETS` at crates/platpulse-server/src/investigation.rs:71) with `aria-pressed` on the selected one, plus `Reload window` — which re-reads the same preset from the Server's current clock instead of silently sliding the window on every render — and an explicit `From`/`To` pair. The client hardcodes no preset list and no default: the answer carries `supported_presets` and the page presses the one the answer itself resolved. The client repeats no width, no default and no preset list of its own: the preset list, the resolved window and the widest window it states all arrive in the answer (the 30 day horizon is the answer's own `window.horizonDays`), and the two widths the Server states (`MIN_WINDOW_HOURS = 1`, `MAX_WINDOW_HOURS = 720`, crates/platpulse-server/src/investigation.rs:103-106) stay the Server's to enforce, so the page cannot drift from a limit it never repeated. `DEFAULT_WINDOW_PRESET = "24h"` (crates/platpulse-server/src/investigation.rs:100) is the window the page opens on and the one an empty query resolves to, so `?window=24h`, a bare deep link and a refresh all answer the same window.
- The window lives in the URL and only there. `?window=<key>` or `?from=<utc instant>&to=<utc instant>` is what the Server reads: a link that names a preset together with `from`/`to` is sent as it is written and refused by the Server ("choose either a preset window or an explicit from/to range, not both") instead of one of the two being chosen here on its behalf, so copying the address, reloading the tab or sharing it from an Incident occurrence reproduces the window — and reproduces its refusal — instead of quietly returning to the default. `window.custom` is true only on the explicit path, `window.preset` reads `custom` there (`CUSTOM_WINDOW_PRESET`, crates/platpulse-server/src/investigation.rs:99), and the control must show the custom pair as the selected state rather than leaving a preset pressed.
- The asked window is answered as asked, and a clamp is said out loud. Every answer carries `window.preset`, `presetLabel`, `custom`, `requestedFrom`, `requestedTo`, `from`, `to`, `durationSeconds`, `answeredAt`, `clampedToNow`, `horizonDays` (30) and `rawRetentionDays` (1). The Server never widens, narrows or clips the window to what retention happens to hold — retention is reported as a boundary inside the window instead — and the only shortening it performs is to the current instant, which it discloses in its own words in `notes` ("the requested window ended in the future and was clipped to <t>"). The page must show the requested range and the answered range whenever they differ, with that sentence, and must never render the answered range as if it had been requested.
- Window errors are the Server's reasons, never a generic failure. `resolve_window` (crates/platpulse-server/src/investigation.rs:242) answers 400 with code `invalid_investigation_window` (`INVALID_WINDOW_CODE`, crates/platpulse-server/src/investigation.rs:112), and the form must surface the reason it carried: an unknown preset ("<key> is not a supported window; supported windows are 1h (last hour), 6h (last 6 hours), 24h (last 24 hours), 7d (last 7 days), 30d (last 30 days)"), a half-specified range ("an explicit window needs both from and to: one end alone does not describe a range"), a non-canonical instant ("<field>=<value> is not a canonical RFC 3339 instant; pass a UTC instant such as 2030-01-01T00:00:00Z"), a reversed range ("the window ends at or before it starts: from must be an earlier instant than to"), a range below the 1 hour minimum (`MIN_WINDOW_HOURS = 1`, crates/platpulse-server/src/investigation.rs:103) or above the 720 hour maximum (`MAX_WINDOW_HOURS = 720`, crates/platpulse-server/src/investigation.rs:106) ("the window is <width> seconds wide; the supported minimum is 1 hour" / "… the supported maximum is 720 hours"), and a window wholly in the future ("the window lies in the future, so the Server cannot have observed any of it"). The same route answers a query the Server cannot read with the code `invalid_investigation_window` and "the investigation window could not be read; name a preset, or pass from and to together". The window a link names is sent to the Server exactly as the link writes it, and the Server's own reason is what the page renders: which windows the Server reads — a preset arriving with a range, one end of a range, an instant no reader can parse, a range that ends at or before it starts, a width outside the minimum and the maximum, a preset key it does not support — is its rule and not the page's, so a refused window is named where it was asked for (`readInvestigationLink` normalizes and judges nothing, platpulse-web/src/nodeInvestigation.ts:96-143; the reason is rendered on `[data-slot="investigation-window-refused"]`, platpulse-web/src/pages/AdminNodeInvestigation.tsx:274-284, in a `role="alert"` that begins "The Server refused the window this link names:") beside the controls that ask for another one, and never as a window substituted for the one the reader followed. No page wording of its own stands in for the Server's reason, and the Client holds no window policy to state.
- Every answer carries all seven sources, in a fixed order, whether or not each holds evidence: `relationships`, `node_metrics`, `node_state`, `host_metrics`, `peers`, `incidents`, `validator` (`SOURCE_ORDER`, crates/platpulse-server/src/investigation.rs:508). The first family is the Server's own record of the Node's relations, read before the collected evidence because it is what every other family's attribution rests on; it is described in its own bullet below. The coverage vocabulary is `complete`/`Complete`, `partial`/`Partial`, `empty`/`Empty window`, `unavailable`/`Unavailable` and `unsupported`/`Not applicable` (crates/platpulse-server/src/investigation.rs:341), and each source states its time basis with the Server's word and label: `metric_observation`/`Metric observation time`, `state_observation`/`State observation time`, `peer_receipt_bucket`/`Peer receipt bucket`, `incident_evaluation`/`Incident occurrence time`, `validator_snapshot_source`/`Validator source time`, `server_record`/`Server record time` (crates/platpulse-server/src/investigation.rs:385). A source card also states its own `sourceState`/`errorCode` — the state of that source's own collector, never borrowed from another collector that succeeded — its `subjectKind`/`subject`, `firstObservedAt`, `lastObservedAt`, `lastReceivedAt`, `releasedBefore`, `retainedFrom`, `retentionDays`, `truncated` and its `notes` verbatim. It also carries `relatedSubjects`: the subjects this family's evidence is attributed to, each with its `subjectKind`/`subject`, its `role` (`source` for the subject the family answers about, `related` for another recorded subject), its `basis`/`basisLabel`, the `from`/`to` stretch it rests on and the Server's `detail`. The list is empty when the Server recorded no subject as related to the family's own subject, and an empty list never means every point is the family's own subject — a family can also carry a `relationship_unknown` boundary over the stretch it cannot attribute.
- Unknown is never a zero, and an absence is never a measurement. A source whose coverage is `empty` states an absence of evidence inside the window; it never renders `0`, an empty chart drawn as a flat line at zero, or a "0 samples" tile, and no absent value may be substituted by `0` anywhere in the panel. `expectedPoints`, `missingPoints`, `grainSeconds`, `cadenceSeconds`, `longestGapSeconds` and `seconds` may be null because the Server does not count that grain (see below) — a null must read `Not counted for this grain`, never `0` or `0 gaps`, and the page must not invent the number the Server declined to prove. Coverage is rendered from the boundary the Server answered with, in its own words: "the Server has never stored an observation for this source on this subject", "the first observation of this source is <t>, which is after the window ends", "cleanup has released this source's evidence before <t>, so none of the window is still stored", "the earliest observation of this source is <t>, so the window opens before the Agent reported any of it", "evidence older than <t> was released by cleanup", "the newest observation of this source is <t>, <n>s before the window ends".
- The grain table names the grain before it shows a number. Grains on the wire are `raw`, `1m`, `5m` (the metric tiers), `state_entry`, `receipt_bucket_5m`, `receipt_bucket_1h`, `occurrence`, `validator_day` and `recorded_interval` (crates/platpulse-server/src/investigation.rs:474-490). Columns: `grain`, `grainSeconds`, `available`, `pointCount`/`sampleCount`, `expectedPoints`, `missingPoints`, `firstObservedAt`/`lastObservedAt`, `cadenceSeconds`, `longestGapSeconds` and each grain's own `note`. `available` is `span.is_some() && point_count > 0` (crates/platpulse-server/src/investigation.rs:786): a grain that serves the window and stored nothing reads as not available with "this grain serves this window and holds no point inside it", and a grain that does not serve the window at all reads "this tier does not serve this window: <account>" — the raw tier answers only the newest 24 hours, the `1m` tier the newest 7 days and the `5m` tier 7 to 30 days back. `expectedPoints` exists only where the Server counts a grid, and it is counted per series from that series' own first observation, so a Node enabled yesterday is not drawn as a hole the size of the window; the two peer receipt tiers carry neither `expectedPoints` nor `missingPoints`, so the page must not offer a missing-bucket count from a table that does not prove one.
- Interruptions are listed as evidence, with their kind. `holes` carry `series`, `from`, `to` and `seconds`, and the Server fetches only the widest one per grain, disclosing that in the grain's note ("the longest interruption is listed; the tier's statistics carry any shorter ones" for a raw grain, "… the buckets this tier does not hold are counted in missing_points" for a bucket grain). Boundary kinds and labels are `pre_enablement`/`Before this evidence started`, `retention_cleanup`/`Released by retention cleanup`, `low_space_pause`/`Optional history paused for low space`, `collection_failure`/`Collection gap`, `never_observed`/`Never observed`, `stale_tail`/`Newest evidence is older than the window end` and `relationship_unknown`/`No recorded relationship` (crates/platpulse-server/src/investigation.rs:428), each carrying the Server's `detail` where it sent one. A low-space pause is never shown as a collection failure — "an interruption inside a refused stretch is the pause, not a failure" (crates/platpulse-server/src/investigation.rs:1168-1179) — and the boundary list is rendered in the order the Server sent (sorted by instant, then kind, deduplicated) rather than regrouped by the client.
- The Peer receipt evidence panel reads the range endpoint, not the window endpoint: `GET /api/admin/v1/nodes/{node_id}/peer-history?grain=5m|1h&from=&to=` (crates/platpulse-server/src/http/admin.rs:2798 `admin_node_peer_history`, query `AdminPeerHistoryQuery` at crates/platpulse-server/src/http/admin.rs:2675, module crates/platpulse-server/src/peer_history.rs). It presents the semantics the Server really records: a bucket start is the instant the Server accepted the Report — the receipt — and not the instant the Agent counted its peers, so it says when the evidence arrived; a bucket is stored only when a Report carries Peer evidence, so a stretch with no bucket means no Report arrived rather than the peer set being unchanged; and the grid starts at the oldest bucket the grain ever recorded, so the era before a Node's first successful snapshot is never counted against it. Columns: the half-open `from`/`to` it answered, `returned`, `matching`, `firstBucket`/`lastBucket`, `missingBuckets`, `coverage`, `truncated` and `continuation`; its `coverage` uses the same vocabulary as the investigation window (`complete`, `partial`, `empty`, `unavailable`). A gap inside the record is receipts that never arrived and must not be re-labelled an empty window just because the answered page holds no row, and `missingBuckets` is proved by the aligned grid (`max(expected_buckets(grid_from, to, grain_seconds) - matching, 0)`, crates/platpulse-server/src/peer_history.rs:791), never by an expected-point count. A ranged read leaves the endpoint's fixed tails empty, so one response never means two things. `continuation` is the exclusive `before` coordinate: `Load older buckets` is enabled only while `truncated`, and `Return to the newest buckets` returns to the window the panel opened on.
- The Incident source is an occurrence source and says so. Incidents have no cadence: a quiet stretch between two Incidents is never a missing observation, so this source carries no hole and no stale tail and the panel must not draw one. Its own note is "Incidents are evaluated by the Server from its own history, so no Agent collector reports on them and none is named here". The list it links to applies the same predicate the investigation used — an Incident that opened before the window and had not closed when it started is inside the window — under a 30-day ceiling, with the cursor `<opened_at>|<incident_id>`, `total` counted without the cursor while the page is counted with it, and `coverage` (`complete`/`partial`/`empty`) derived from `total`/`truncated`; the panel states the Server's rule in its own words: "an occurrence is never averaged into a value, so a window with no Incident is empty and not zero". It also counts the Incidents of a subject the Server recorded as related to this Node, but only inside the stretches the Server held that relation for (crates/platpulse-server/src/investigation.rs:2957), and says the count in the grain's own note ("<n> of these Incidents are on subjects recorded as related to this Node, inside the stretches the Server held that relation for", crates/platpulse-server/src/investigation.rs:3041): each such subject is listed in `relatedSubjects` with basis `recorded_relationship`, and the family carries one answer path per related subject whose note is "only the stretch the Server recorded this relation for is asked, not the whole window" (crates/platpulse-server/src/investigation.rs:3085). An Incident on the Node itself is always counted, and the Alert catalog holds no rule on a Network subject, so a recorded Network relation can never appear here and the family says so in its note instead of drawing a row the catalog cannot produce. When the family counts no Incident on a related subject while the relation record does not cover the whole window, it says why in its own note: "no Incident on a related subject is counted for this window: the record of this Node's relations does not cover all of it, and a stretch with no recorded relation is a gap in the record rather than an absence of Incidents" (crates/platpulse-server/src/investigation.rs:3053). A gap in the record is named as a gap and is never read as an absence of Incidents, while the family's own subject — the Node — is still counted over the whole window from the Server's own history, because that count does not rest on the relation record at all.
- The Validator source is day-grained and may be `unsupported`. Its day grid is the Server's configured local calendar, the Validator trend engine remains the day-level authority, and each link is described by the Server as what it is — a correspondence the Server itself wrote down rather than an on-chain key change ("the Server recorded <validator> (<role|unassigned>, <origin>) as linked from <t> to <until>", or "… as linked from <t> and still holds it", crates/platpulse-server/src/investigation.rs:3196), with the Server's own note "a Validator link is the Server's own record of when it began and stopped reading a Validator for this Node: its edges are correspondence times rather than key-change times, and it proves no continuous protection between them" (crates/platpulse-server/src/investigation.rs:3314) and its own `relatedSubjects` entry with basis `recorded_validator_link`/`Recorded Validator Link`. A stored day is counted for a link only while the Server held that link: the snapshot read is bounded by the link's own correspondence through the Server's receipt clock — the clock the edges of the link itself are written from — so a day recorded under an earlier link, or before any link existed, is not credited to this one, and two links to the same Validator inside one window cannot each claim the same stored day (crates/platpulse-server/src/investigation.rs:3146 and :3160). Each link's trend answer path is asked for that link's own recorded stretch rather than for the whole window, and the path carries that in its note ("only the stretch the Server recorded this link for is asked, not the whole window", crates/platpulse-server/src/investigation.rs:3345), because the days outside the correspondence were read under another link, or under none. When no Validator overlaps the window at all the source is `unsupported` with the reason "no Validator is linked to this Node for any part of this window, so the Server holds no Validator snapshots for it" — an unsupported source has notes and no grains and no answer paths, so the panel shows the reason, must not draw an empty trend chart, a zero or a bare "No data", and must not offer an answer path for a source the Server says is not applicable. Holding no record of a link is likewise not evidence that the Node had none, and the source says so in its own words: "the Server holds no link interval for this Node inside this window, and holding no record of a link is not evidence that the Node had none: this family states what the Server recorded and never what the current link implies about the past" (crates/platpulse-server/src/investigation.rs:3257).
- Every conclusion carries its answer path, and only the paths the Server sent. Each `answerPaths` entry is rendered as its `label`, its `path` as a link into the existing page, and its `note` where the Server attached one ("an Incident that opened before the window and had not closed when it started is listed too"; "one read per component; the entries carry the collection state and value source of each write"). The paths are real requests that accept the window they carry: metric history `?metric=<key>[&dimension=<mount path>]&from=<a>&to=<b>` (crates/platpulse-server/src/http/admin.rs:4748), state history `?component=sync|consensus&from=<a>&to=<b>` (crates/platpulse-server/src/http/admin.rs:5153), peer history `?grain=5m|1h&from=<a>&to=<b>` (crates/platpulse-server/src/http/admin.rs:2675), incidents `?subject_kind=node|agent&subject_key=<id>&from=<a>&to=<b>` (crates/platpulse-server/src/http/alerts_admin.rs:2015) and the Validator trend `/api/admin/v1/validators/{validator_id}/trend?from=<a>&to=<b>`. The panel must not invent a link, must not turn the investigation itself into a second answer surface, and a source that sent no answer path reads as a Server statement rather than as a broken link. The one family that sends no answer path by design is the recorded-relationships family, and it says so in its own note — the record is the Server's own writing, read inside this answer, "which is the only place the Server serves them, so this family points at no other path" (crates/platpulse-server/src/investigation.rs:2791) — so its empty `answerPaths` is a statement the panel renders as one — the card shows `data-slot="investigation-no-answer-path"` in place of the endpoint list rather than heading a list of links that does not exist (platpulse-web/src/pages/AdminNodeInvestigation.tsx) — and no second endpoint is invented for it.
- The seventh family is the Server's own record, and it never back-fills the past from the present (issue #221; stories 60, 61, 65, 66 and 68). `relationships`/`Recorded relationships` answers about `subjectKind` `node` from the table `node_relationship_intervals` (crates/platpulse-server/migrations/0071_node_relationship_intervals.sql, `SERVER_SCHEMA_VERSION = 71`, crates/platpulse-server/src/database.rs), which the Server writes as it accepts a Report or completes a Node Transfer (crates/platpulse-server/src/relationships.rs, called from crates/platpulse-server/src/http/report_ingestion.rs). The table is created empty and is prospective only: nothing is back-filled from the Agent or Network key a Node carries now, so a window that opens before the record began carries a `relationship_unknown` boundary — "the Server has never recorded which Agent or Network this Node belonged to, and recording is prospective, so this stretch is not attributed to the relations the Node has now", or "the Server recorded nothing about which Agent or Network this Node belonged to from <a> to <b>, so this stretch is not attributed to the relations it had before or after it" (crates/platpulse-server/src/investigation.rs:1274-1294) — instead of an attribution, and its coverage degrades to `partial` honestly. Each recorded stretch is one `relatedSubjects` entry with basis `recorded_relationship`/`Recorded relationship`: an interval the record gave to another subject is read as that subject, and the node's own current key is never applied backwards. The family states the record's own ledger — the first instant it holds, the furthest instant it reaches and the last time the Server wrote an interval down — and its only grain is `recorded_interval`/`Recorded relationship intervals`: one point per recorded interval over the window, no `cadenceSeconds` and no `longestGapSeconds`, because the distance between two records is not a missing observation and no interruption can be proved from it. A family whose evidence rests on a recorded relation says which subject it is about: `host_metrics` carries the Agent whose records its evidence came from (`role` `source`), the Incident family and the Validator family carry theirs with basis `recorded_relationship` and `recorded_validator_link` respectively, and where the record gives a stretch to another subject the family names that stretch as unknown rather than crediting it to its own ("the Server recorded <relation> <key> for this stretch, so this family holds no evidence attributed to <subject> it answers about", crates/platpulse-server/src/investigation.rs:1253-1265). The page renders the list as the `data-slot="investigation-related-subjects"` table (Subject, Read as, Recorded basis, Stretch, What the record says) directly under the boundary table, shows `data-slot="investigation-no-related-subject"` when the list is empty, and reads these boundaries from the Server's own `kindLabel` like every other family, so `relationship_unknown` displays as `No recorded relationship` with no client vocabulary and no client-side kind list (platpulse-web/src/pages/AdminNodeInvestigation.tsx, helper `relatedSubjectKindLabel` at platpulse-web/src/nodeInvestigation.ts). Story 68 holds at the purge boundary: purging a Node deletes the intervals the Server recorded for it — they are counted in the purge preview's `relationship_intervals` and removed with the Node (crates/platpulse-server/src/node_purge.rs) — while the Agent, Host, Network, Validator and Incident history those records point at survives, so the deleted association stays clearly unavailable instead of reading as never having existed.
- The Incident detail page gains one entry into it. `PAGE-ADMIN-INCIDENT-DETAIL` offers `Investigate this Node in this window`, which opens `PAGE-ADMIN-NODE-INVESTIGATION` for the occurrence's subject Node with the window opened at that occurrence's own instant — an explicit `from`/`to` window, so the opened page reads as custom and never claims a preset it did not ask for. The entry is offered for an occurrence whose `subjectKind` is `node`; an Agent-subject occurrence must not be opened as a Node investigation and no Node may be guessed for it. The occurrence's instant is carried as the window start, and the page states that the window was opened from that occurrence rather than chosen by the reader (platpulse-web/src/pages/AdminIncidents.tsx:56 `nodeInvestigationLink`: `from` is the occurrence and `to` is the later of now and the narrowest window the Server answers, so an occurrence minutes old is still a range the Server accepts and a window that would end in the future is clipped by the Server rather than filled by the client).
- State handling and acceptance match the rest of section 15. A `role="status"` line while the window's first read is in flight; a `role="alert"` carrying the Server's sanitized reason with `Try again` when the read fails; and, when a refresh fails, a `role="alert"` that keeps the last successful answer on screen labelled as what it is (`Failed to refresh; showing the last successful investigation.`) instead of presenting it as current — each evidence panel says the same about its own read, so a Peer receipt range that could not be refreshed is named as the last successful read of that window while the hard failure alert is reserved for a read that has no answer at all. A missing Node answers 404 `not_found`; a purged Node answers 404 `node_purged` with "this Node was purged at <t>; its evidence was deleted by design and cannot be reconstructed", which the page renders as that fact rather than as an empty investigation; a database failure answers 503 `unavailable`. The page is Owner-only behind the same existing CSRF/Origin middleware, its query cache is generation-scoped with no placeholder, and it holds the fixed 360/390/768/1280/1440 viewports, Light/Dark, keyboard focus, 44x44 touch targets, and local table scroll without primary horizontal page overflow. The URL ends up with the same text; only fast typing is kept whole. ### 15.25 Same-tab return to the Home reading and the Node it was left from (issue #224, delivered)

Applies to `PAGE-HOME-NETWORKS` (`/`), on top of §15.23 and §15.24, and to the return links of `PAGE-HOME-NODE` (`/nodes/:nodeId`):

- The departure is neither a Home parameter nor a scroll offset: it rides in the tab's own react-router navigation state under the key `homeReturn` (`HOME_RETURN_STATE_KEY`, platpulse-web/src/homeReturn.ts), written by the two Node links of Home and read by the `Back to Home` links of the Node detail page (platpulse-web/src/pages/HomePages.tsx). Nothing about a reading position enters the URL: the arrival's address bar carries exactly the Home reading the reader left, in Home's own parameter order (`network`, `q`, `health`, `validator`, `sort`, `view`), and no offset, no place and no second position parameter is ever written to it. Navigation state is chosen over a URL ticket because it dies with the tab: a middle-click, a new tab, a copied link, another session or a later visit cannot inherit it. It is also refused to another document: the departure carries the reading token of the document that wrote it (`tab`, one `crypto.randomUUID()` per loaded document, `homeReturnTab()`), so a reload of the Node page, a new tab and a browser session the browser restored from disk are all a different document and are handed nothing. That is stated as the cost it is: reloading the Node page loses the return context, and the `Back to Home` links of that page then read as ordinary links to `/`. Browser-native history scroll restoration keeps owning Back and Forward; this return owns the one tab-local journey Home → Node Detail → Home.
- What the document remembers is small and closed: `HomeReturn { nodeId; search; position: { index; count } | null; tab }`, where the place is the 0-based index the Node held when the reader left (the state stores `index + 1`) and is `null` unless `0 <= index < count`, and `tab` is the reading token of the document that wrote the departure. `readHomeReturn(state, tab)` accepts it only when that token is this document's own and the Node ID matches `NODE_ID_PATTERN` (`/^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$/`), the search is a string no longer than `MAX_RETURN_SEARCH` (4096), which `homeReturnHref` reads back into Home's own vocabulary, and the place is a whole number in `1 <= index <= count`; a state that is not a departure at all (the login flow's `{ from, sessionExpired }`, an older deploy, a hand-written `history.state`) is refused whole, and a bad place drops only the place, so a wrong place can never displace the Node identity it travels with.
- The Node ID decides where the reader lands, and the place only decides the fallback. `landHomeReturn(scoped, matching, target)` looks the Node up by ID in the in-scope projection first and then in the filtered result, so a refetch that reordered the list changes the row's index and never the Node the reader is put back on — the whole point of remembering an identity beside a position instead of a pixel offset, which would land on whatever now happens to be at that offset. Three outcomes: the Node is in `matching` → no notice at all, the reader simply continues where they were; the Node is in `scoped` but not in `matching` → `filtered`, and the notice names the Node the way the reader reads Nodes, by display name; the Node is in neither → `missing`, and the notice names the Node ID it was left from. The fallback place is `homeReturnFallbackIndex(count, position) = min(position.index - 1, count - 1)`, `null` when there is no place and no list, so a list that shrank never leaves the reader on blank space and a search that matches nothing keeps §15.23's own empty statements instead of inventing a row.
- The notice is one sentence the reader can act on, in the Home filter notice's own audited tone: `<label> is no longer shown by these filters.` or `<label> is no longer in this view.`, followed by ` Showing the nearest matching Active Node instead.` or ` Showing the nearest Active Node instead.` It renders as `data-slot="home-return-notice"` with `role="status"` on the amber `bg-amber-400/10` surface with `text-amber-600 dark:text-amber-400`, in a `px-4 pt-4` wrapper beside `data-slot="home-filter-notice"`, so the two refusals of one link — a value this deployment does not offer and a Node it can no longer show — are both readable on the same paint. The notice is dropped the moment the reader asks for another reading (any toolbar action) and on a `popstate` takeover, so a sentence about a Node never sits over a view the reader has just changed.
- The departure is consumed exactly once. The first render that can place it re-writes the same URL with `setSearch(search, { replace: true, state: null })`: the address bar is unchanged, the departure is gone from the history entry, and no history step is added, so an arrival entry can never be re-inherited by a refresh or by back/forward and the URL the reader could copy carries no reading position. It is consumed only once the reading on screen is really the one the departure names: while a refetch of the Public reset that followed the departure is still in flight, the projection can still be the cached one, and a landing computed from it would put the reader beside a Node the fresh reading still holds. The departure and its search therefore wait in `pendingReturn` until the settled projection answers the search the URL carries, and the landing of a reading that is still being refetched is provisional. `landedReturn` holds the place the arrival reached together with whether it is still provisional (`{ index, notice, provisional }`, where `provisional` is the `refreshing` prop, `networks.isFetching` in the routed Home): the first landing places the reader in the reading on screen, and when the settled projection puts their Node somewhere else the arrival places them again — once, and silently, because a sentence here would say nothing the reader cannot see — while a Node the settled reading did not move is never re-placed and a live reorder the reader is watching never moves them at all. A toolbar action and a `popstate` takeover clear the pending departure, the landed place and the notice together (`finishReturn`), because nothing is owed to a reading the reader left by another door. The reveal itself runs once per arrival, through React callback refs keyed by Node ID (`Map<string, HTMLElement>` held in a ref, attached to `data-slot="node-list-row"` and `data-slot="node-card-frame"`) rather than by querying the DOM: the located row is scrolled with `scrollIntoView?.({ block: 'center' })` and the Node link inside it is focused with `{ preventScroll: true }`, so a keyboard reader continues from the row they returned to and a touch reader is not moved twice; a `null` ref, or a Home whose projection is not available yet, is handled without touching geometry.
- No scroll offset is stored anywhere — not in the URL, not in navigation state, not in `sessionStorage` — so a fresh, direct or bookmarked Home entry (a new tab, a typed URL, a link from anywhere else) renders exactly the reading its URL names and inherits no place of its own: one arrival has exactly one owner. A PUSH arrival at `/` that no departure of this document claims is moved to the top (`document.scrollingElement?.scrollTo({ top: 0 })`, platpulse-web/src/layouts/HomeLayout.tsx), while an arrival that is this document's own return is left where it is, so the reveal that places the reader on their Node is the only thing that moves them; the guard is the departure itself (`readHomeReturn(here.state, homeReturnTab()) !== null`) rather than the render order of two effects. The departure also cannot cross an identity change, and the boundary that catches one is the boundary that outlives every shell: `syncHomeReturnReader(reader)` runs in the authentication provider (platpulse-web/src/auth/AuthContext.tsx) with the reader as `role + ':' + userId`, or the authentication state itself — not in `HomeLayout`, because signing out and signing in as somebody else happens while no Home shell is mounted, so a rotation kept in Home would never see the reader change. The first reader a document observes adopts the token that document already holds, so a reader whose own identity is re-established (a session re-check republishing the same principal at a new authorization generation) keeps the entry they wrote; any other reader rotates the token, so a sign-out, a sign-in as another reader or an expiry starts from a Home with nothing inherited. A Public cache reset alone does not rotate it — republishing the projection does not change who is reading — so a reader who never signed out keeps their own departure through the reset a Purge triggers.
- The contract is held to the routed Public surface and never to private internals: the departure and the reveal are exercised through the Node links' `data-slot="node-link"`, the `homeNodeLabel` accessible names of the row and card links, the `role="status"` notices and the address bar. No React state, CSS class, private DOM attribute or hand-edited `history.state` is read by the acceptance, because the departure and the reveal are driven entirely through the links, the accessible names, the notices and the address bar. A story whose subject is the world changing under the reader is aged with a real Admin write — a Node rename through `PUT /api/admin/v1/nodes/{node_id}/metadata` — instead of by editing the history state react-router wrote. This ticket adds no schema, no endpoint, no DTO, no OpenAPI change and no regenerated client: where a reader was reading is browser-side navigation state the Server neither stores nor needs to observe, and the reading a return restores is still `GET /api/public/v1/networks` through the generated client of §15.23. The browser acceptance does write to the Server, through the Admin routes that already exist — it renames a Node and, on a Server of its own (§6), purges one, because a Purge is irreversible — and the reading it comes back to is that Server's own answer over the fixture database, not a private client cache.
- Acceptance. The pure seam and its unit tests are platpulse-web/src/homeReturn.test.ts (19 cases: building a departure, refusing a hand-written state, another document's departure and a rotated token, one token per reader with the first reader adopting the document's own, rebuilding the return link into Home's own vocabulary without writing a place to a URL, and the three landing outcomes with the notice copy) and the arrival behaviour in platpulse-web/src/components/HomeDashboard.test.tsx (`Public Home same-tab return`, 8 cases, including a place a reordered list has moved past, a Node the restored filters hide, a landing re-computed and re-noticed when the refetch settles without the Node, and a reader placed again when the settled reading has moved their Node); the reader boundary in platpulse-web/src/auth/AuthContext.test.tsx (1 case: the entry a reader wrote survives their own session re-check, and a sign-in as somebody else starts a new reading); the production-router round trip in platpulse-web/src/App.test.tsx (45 tests) follows the `Back to Home` link back to a bare Home and holds the two arrivals apart: a fresh arrival at Home gets the top of the page, the reader's own return does not. The browser acceptance is platpulse-web/e2e/home-return.spec.ts (10 cases) over the production WebUI, a real Server HTTP surface and a temporary SQLite database (§6), at the five fixed viewports: a list return whose address bar is exactly the departure reading with no place in it, a Node ID that wins over a place a rename has moved past (the rename is a real Admin write), a Node a restored filter now hides under the name it now has, a card-view return taken with the keyboard, a touch tap on the two touch projects, a reloaded Node page that has no reading to come back to, a fresh Home that inherits no reading position (`window.scrollY === 0`, no notice, no focused Node link), a fresh arrival at Home that starts at the top of the page, the Dark surface where the return notice and the filter notice are painted together in the same tone, and — on a disposable Server of its own, so it runs on one project — a Node really purged through `POST /api/admin/v1/nodes/{node_id}/purge`, after which the reader's return lands beside the row that took its place and says, by Node ID, that the Node is no longer in this view. Screenshots may be recorded as review evidence at that matrix and are never compared (ADR 0002).

### 15.26 Home latest-60-second charts drawn from the Server's own coverage, never across a silence (issue #225, delivered)

Applies to `PAGE-HOME-NODE` (`/nodes/:nodeId`), on top of the accepted six-chart deck of §11.1 (issue #150) and of the gap doctrine the Admin long-history panel reads in §15.16, and to the Public latest-60-second response those charts draw from:

- The chart's question is answered by the Server, not guessed by the browser: `GET /api/public/v1/nodes/{node_id}/metrics` now carries `series`, one `PublicMetricSeriesCoverage` per plotted direction, in the same order as the nine arrays it judges (`PUBLIC_METRIC_SERIES`, crates/platpulse-server/src/http/public.rs:1440, whose entries are the camelCase response field names the nine arrays do not carry themselves). The change is additive: `from`, `to`, `windowSeconds` and the nine arrays are untouched, the window stays 60 seconds (`PUBLIC_NODE_METRIC_WINDOW_SECONDS`, crates/platpulse-server/src/http/public.rs:1185), no Admin route or panel changes, and no Audit entry is written, because this answer observes nothing and commands nothing.
- What one series can vouch for, as `PublicMetricSeriesCoverage` (crates/platpulse-server/src/http/public.rs:1234-1285): `observed` (whether this answer carries any observation of the series at all, including the last-good point that precedes the window), `observationCount` (window only, so a series that is observed but counted zero has not been seen recently and the tail dates that rather than a zero), `firstObservedAt`/`lastObservedAt`, `cadenceSeconds`, `gapThresholdSeconds`, `coveredSeconds`, `unobservedTailSeconds`, and `gaps` — `PublicMetricGap { from, to, seconds, kind }` (:1215-1232), `from` the newest instant before the silence, `to` the first observation after it, which is exactly where a chart may start drawing again, and `kind` today always `collection_gap` from the shared `GapKind::as_str` vocabulary, because a 60-second answer holds no protection pause to name. `coveredSeconds` never counts the stretch after the newest observation, because nobody observed how long it is, and `unobservedTailSeconds` measures from the newest observation to the end of the window and may exceed the window when that observation is an older last-good point: the series really has been quiet that long. A series whose raw samples retention has already removed is still a series somebody observed, so the Server dates it from the series ledger (`node_metric_series_state`/`host_metric_series_state`, migrations/0066_node_metric_history.sql:42-54 and migrations/0068_host_metric_history.sql:83-97), which holds the first and last observation instant of every metric and no value at all: the Public answer gains an age without gaining a fabricated point, and only a metric the ledger never saw answers `observed` false — which is exactly what the two block series (`blockIntervalMs`, `transactionCount`) get — a limit this contract states instead of hiding: they live in `block_summaries`, which has no ledger, so once retention removes their rows the Server cannot date that expiry and answers them as never observed; dating them would need a block-series ledger, that is new schema outside this ticket, while nothing is invented either way (no zero, no line, `Unknown` rather than 0).
- An unknown cadence is never read as silence. `cadenceSeconds` is the cadence currently in force — the newest interval between two consecutive observations, trusted only while the interval before it agrees with it — and `gapThresholdSeconds` is three times it, capped at five minutes of cadence. Zero cadence means the Server holds no rhythm verdict for that series and it then answers `gapThresholdSeconds` 0 with no gaps, so a series with no known rhythm is answered as unknown instead of as silent — the same rule §15.16 states for a series with no self-measured cadence. Zero is also the honest answer immediately after an interruption: the newest interval on its own cannot tell an interrupted collection from a cadence that legitimately changed, so the answer names no silence and `coveredSeconds` stays 0 until the next observation settles the rhythm — a series observed every 5 seconds, silent for 30 seconds and then resumed for two intervals answers cadence 5 with the gap, because by then the interval before the newest one agrees with it.
- The Server did not write a second gap rule: the metric-history machinery was reused with its silence floor made a parameter (`gap_threshold_seconds_with_floor`, crates/platpulse-server/src/metric_history.rs:766, and `continuity_with_floor`, :819, both feeding `silence_threshold_seconds`, :927). The Admin surfaces keep `gap_threshold_seconds`/`continuity` with `MIN_GAP_SECONDS = 120` (:360), so the Admin long-history panel and its assertions are unchanged; the Public 60-second answer passes a floor of 0, because a two-minute floor sits above the whole window and no silence inside it could ever be named. The cadence behind the verdict is the current-cadence rule (the newest interval) rather than the fastest-gap rule the Admin aggregate tiers use, so ordinary jitter is not read as silence. The last-good point that precedes the window still rides as element 0 of its array and still informs the value, the cadence and the age shown, but it never enters the continuity computation: a silence that begins before the window is not a gap in it.
- The client seam is platpulse-web/src/metricCoverage.ts, a thin reader of that contract rather than a second chart framework: `metricCoverage(history, metric)` finds one series' own verdict, `coverageRuns(points, from, to, max, gaps)` turns raw observations into drawable runs at the deck's own geometry (`x = (sampledAt - from) / (to - from) * 600`, `y = 142 - (clamped value / ceiling) * 134`, the ceiling falling back to 1 when the maximum is 0), and `coverageNote`/`coverageNotes` write the sentence. - The card says what the curve cannot. Each of the six cards renders `data-slot="node-metric-coverage"` (`m-0 text-[11px] leading-4 text-muted-foreground`) in the card's detail area above its chart, beside the other absence notes: `No samples reported yet` for a series nobody observed, `Last observation 2 minutes ago` for one whose window holds nothing while the series has been seen before it (which is also how a series reads once retention removed its samples: dated by the ledger, so an age, never `No samples reported yet`), `1 gap in this window` / `3 gaps in this window` for silences the Server counted, and — only when the tail is at least as long as the decided threshold, so the age is a named silence rather than ordinary waiting — `No samples for the last 4 minutes` joined to it with ` · `. Durations reuse the metric-history wording (`formatHistoryDuration`: `1 minute`, `20 seconds`), so one age is spelled one way on both surfaces. The same sentence is appended to the chart's `<desc>` (`svg[role="img"]`), so a reader using a screen reader is told what the curve cannot show, and the notice is text, never a colour or a symbol alone.
