# ADR 0010: Read the Home counters and Peer country map over the current list selection

**Status:** Accepted; implemented by issue #233 (Server slice in crates/platpulse-server/src/http/public.rs, Web slice in platpulse-web/src/homeGeo.ts and platpulse-web/src/components/). This revises the Home scope rule settled for issue #222 (Story 71), which had made the whole overview band and the Peer country map follow only the Network selection while the search, Health and Validator status filters narrowed the Node list.

## Context

A Home reader who types a search term, or picks a Health or Validator status, is looking at a specific set of Nodes. Until this decision the band above that list kept reporting the whole Network selection: four attributable counters (Active Nodes, Healthy Nodes, Attention, Networks) and the Peer country map described Nodes the reader had just filtered out, with a sentence explaining that the overview covered the whole Network selection. The list said one thing and the readings above it another.

Two constraints shaped the fix. First, the Server is the trust boundary: the browser may sum Server facts but must not parse a country, deduplicate by IP or Peer identity, or infer an Unknown bucket by subtraction. Second, the Server had to keep exactly one source of truth for country data, so a Network reading and the sum of its Nodes' readings can never drift.

## Decision

The four attributable counters and the Peer country map read the current list selection. The two cumulative Validator cards keep the Network selection and say so.

- **Scope follows what the reader sees.** Active Nodes counts the matched Active Nodes, Healthy Nodes the matched Nodes whose Server-owned `health` is healthy, Attention the remaining matched Nodes including Unknown, and Networks the Public Network groups that still hold a matched Node. The Peer country map, its country list, its corner chip and its Known/Unknown/Unknown-reason counts read the same matched set. While nothing narrows the list the matched set equals the Network selection, so the readings are unchanged from the earlier contract, field for field.
- **The two cumulative cards are deliberately out of scope, and state it.** `Cumulative blocks` and `Cumulative rewards` are Cross-Network Validator Overview totals the Server publishes per Network over already-deduplicated Network summaries. Re-summing them onto a subset of Nodes would invent a smaller "total" out of the same Nodes, so they keep the whole Network selection and each draws its scope note ("Whole Network selection, never the filtered list") in its caption and in its Breakdown as soon as a filter makes the difference visible. A visibly inconsistent scope, explained on the card, is preferable to a silently wrong total.
- **No new request, route or query parameter.** The one existing `GET /api/public/v1/networks` response gains a compact per-Node bucket (`PublicNode.peerCountries`, type `PublicNodePeerCountries`: scope, Available Peer records, Known and Unknown country counts, the two Unknown reasons, and the per-country counts with their Server representative points) alongside the unchanged Network-level `geo` insight. The browser sums the matched Nodes' buckets and nothing else, so a Node selection is a reading of Server facts, not a client-side projection.
- **Both readings come from one Server batch.** `PublicGeoReadings::load` reads the per-Node Geo rows once and `load_node_geo` builds one distribution per Active Node; the Network-level insight is the sum of those distributions. The per-Network repeat read the earlier implementation performed for each Network is gone. This is what makes "Network read == sum of its Active Node buckets" true by construction, and what makes "Node Detail read == Home read with only that Node selected" true for one selected Node. The batch is then restricted to exactly the Nodes the same response lists, each with its Network (`PublicGeoReadings::restrict_to_listed_nodes`): the listed rows and the Geo rows are two separate reads, so a Node activated after the list read cannot enter a Network reading that carries no listed bucket for it, and a listed Node the Geo read lost keeps its place in the denominator — that Network can then only read `partial`, never `complete` over the Nodes that remain.
- **A never-observed Node contributes no count, never a zero.** A Node whose Peer snapshot was never accepted has an `unobserved` scope, and the projection reports no counts at its own scope (`has_basis = scope != "unobserved"`). The aggregate therefore leaves it out of the counts while keeping it in the denominator, which can only make a selection partial, never complete. Counting its rows as Unknown would report a Node that was never observed as a Node whose countries are unknown.
- **Provider and database state stay Network-level.** `state`, `attribution`, `errorReason`, `lastGoodAt`, `staleSince` and `databaseAgeSeconds` describe the provider and its database; a list filter cannot make them fresh or stale. They read from the Networks the selection lands in. Visible staleness still follows the selection through each summed country's `staleCount`. Peer collection freshness is the one dimension that does follow the selected Nodes, by the rule the Server already applies to one scope (`PublicNode.peers.freshness`): a selection holding one Node reads exactly as that Node's Detail page, never as the Network set's `mixed`.
- **An empty selection is an empty reading, not a failure, and the whole band says so.** The four counters that follow the list read no figure at all — `No match` (`SummaryCard`'s `emptyLabel`) instead of a zero, and with no failure tone — while the list keeps its own "Showing 0 of N", the map states that no Active Nodes match these filters with no country list and no chip, and the two cumulative cards keep the Network selection's totals and their scope note. Without a projection the counters keep reading `Unknown`, a different statement from "no Node matches", so no cell in the band adopts failure styling or a fabricated zero.
- **The basis is stated on the region.** The map root carries `data-scope-basis="network" | "node-selection"` and the cumulative cards carry their note, so a reader, a test or a screenshot can tell which selection a reading stands on.

## Consequences

- **The response grows, and that is the accepted price.** Every listed Node now carries a compact bucket. The per-Node shape is deliberately a bucket and not a full `PublicGeoInsight` (no per-Node attribution, no per-Node provider status, no per-Node freshness object), because those are Network-level facts a Node cannot have independently. The measured magnitude case is 256 Active Nodes across 10 countries in one Network; no payload size budget was set, so a future growth in Nodes × countries is a payload question to revisit, not a correctness one.
- **One accepted reference edge case.** If a Node retained Peer rows while its accepted Peer snapshot has `value_revision = 0`, that Node reads `unobserved` and the Network reading no longer counts those rows. The state is not production-reachable: crates/platpulse-server/src/http/report_ingestion.rs `upsert_peer_snapshot` returns early unless the component status is `Ok` with a latest value, and the DELETE + INSERT of `current_node_peers` happens in the same transaction that records the accepted snapshot. Fixtures that had modelled the unreachable state were corrected by seeding the snapshot the Server would have required, not by weakening the expectations.
- **The two cumulative cards are the one deliberate scope inconsistency** in the band. It is absorbed by the on-card note and by docs/design/webui.md §15.28; if a future issue wants them to follow too, that is a new decision record, because the totals are Network-level by construction.
- **The Home scope rule now reads once**, in docs/design/webui.md §15.23 as revised by §15.28, and in the Attention tooltip; docs/design/platpulse.md:513-515 and the Home scenario rows carry the same rule.
- **Vocabulary.** The reading is a Node Selection Geo Aggregate (节点选择国家聚合) in CONTEXT.md — a set of Nodes, distinct from a Network's Geo Insight and from one Node's Node Peer Country View. "Filtered Geo Insight" stays forbidden for both.

## Alternatives considered

- **A separate per-Node geo endpoint or query parameter.** Rejected: a second request and a second route for data the same response can carry, and it would let the Network reading and the sum of its Nodes drift.
- **Summing full `PublicGeoInsight` objects per listed Node.** Rejected: the per-Node projection costs more than the browser needs, and it would duplicate Network-level provider state on every Node.
- **Deriving Unknown, or the per-country Known counts, in the browser by subtraction or deduplication.** Rejected by the trust boundary: the browser would be inventing counts and could disagree with the Node Detail page.
- **Keeping the whole map on the Network selection and explaining it in copy.** Rejected: that is the behaviour being replaced — the reading would keep describing Nodes the reader filtered out, and a reader comparing the map with the list would still see two answers.
- **Making the two cumulative cards follow the selection to remove the inconsistency.** Rejected: it would report a "cumulative" total over a subset of the Nodes it was accumulated over.
