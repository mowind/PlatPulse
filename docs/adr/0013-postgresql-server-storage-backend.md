# ADR 0013: PostgreSQL as an opt-in second Server storage backend

**Status:** Accepted (design interview for [issue #226](https://github.com/mowind/PlatPulse/issues/226); 0.3.0 target, implementation in progress — PostgreSQL support is not yet implemented). It supersedes the "PostgreSQL" mention in the non-goals of `docs/design/platpulse.md` (§3.3), `docs/design/webui.md` (§1) and `README.md` (Non-goals), and amends the former AGENTS.md convention "SQLite via SQLx with typed SQL" (now "SQLx with typed SQL") for the Server only.

## Context

The Server was designed and built SQLite-only: a single-connection pool carries every read and write, `locking_mode = EXCLUSIVE` plus an `flock` guard the database file, and Report Ingestion's read-then-write invariants rely on that implicit global serialization rather than on row locks. Offline backup/restore (ADR 0008) and the coordinated upgrade checkpoint (issues #190–#192) copy, hash and rename one database file. Deployers that already operate PostgreSQL want the Server to live in that infrastructure — its backups, monitoring and access control — instead of a separately maintained SQLite file; relief from single-file size and lock pain is a secondary benefit. HA, multi-instance and multi-tenant operation are not the goal.

## Decision

- **Two permanent, first-class Server backends.** SQLite remains the default, zero-dependency single-host deployment; PostgreSQL is selected explicitly by configuration. Both backends run the full Server test suite in CI; neither is a smoke-tested afterthought. This is not a transition toward removing SQLite.
- **The Agent is untouched.** The Agent Store stays local SQLite, `platpulse-core` and the wire protocol do not change, and an Agent cannot tell which backend its Server uses.
- **One Server owns one database.** On PostgreSQL the Server and every offline CLI command take a session-level advisory lock before doing any work; a second holder fails closed at startup. PostgreSQL does not make the Server HA or multi-instance.
- **Minimum PostgreSQL 15.** CI covers 15 and the current major release; the Server refuses to start against an older server with an explicit diagnostic.
- **Single-connection serialization on both backends (0.3.0).** The PostgreSQL backend keeps one work connection, so Report Ingestion's read-then-write invariants hold exactly as on SQLite. External read-only tools may still connect alongside the Server, which SQLite's exclusive mode cannot offer. Real in-process concurrency is a separate later change whose acceptance requires those invariants to hold under concurrency.
- **A PostgreSQL baseline, not a replay of SQLite history.** PostgreSQL has its own migration set starting from one baseline equivalent to the SQLite schema version current at release. Both backends share one logical schema version; every later schema change ships both migrations in the same change, and CI checks that tables, columns, constraints and indexes stay logically equivalent. Migrations run at startup after the ownership lock is held; the role must own the target schema, and missing privileges fail startup with a clear message.
- **Mirrored logical column types.** PostgreSQL columns mirror the SQLite logical types — RFC3339 text times, 0/1 integer or boolean flags, `bytea` digests, text JSON — so SQL stays largely shared and a Storage Backend Migration is a byte-faithful copy. Every text column uses `COLLATE "C"`, verified at startup, because time ordering relies on byte-wise string comparison that locale collations can break. Native `timestamptz`/`jsonb` are a possible later optimization.
- **Storage Backend Migration ships in 0.3.0** (`platpulse-server storage migrate`). It is offline and one-way (SQLite → PostgreSQL only) and requires a source that passes `integrity_check`, matches the binary's schema version, and is either past the v1→v2 cutover or never on v1. It copies the whole database unsanitized — Agent identity, credential digests, Report Receipts and Purge barriers must survive exactly — into an empty target, then verifies per-table row counts and content digests; any mismatch fails. The source file is left untouched as the fallback point.
- **ADR 0008 backups are SQLite-only.** On PostgreSQL, `backup`, `restore` and `verify-integrity` refuse with a pointer to PostgreSQL's own tooling. Those dumps, PITR and managed snapshots are Storage Snapshots, which ADR 0008 already accepts as unsanitized, so this is no new privacy concession; the deployment documentation states that they contain raw Peer addresses, Endpoints and credential digests. No sanitized logical backup is invented for PostgreSQL. Doctor reports backup age and residue as NOT_APPLICABLE and replaces the integrity check with connection, version, collation, ownership-lock and schema-version checks. The Admin Backup artifact surface states that this backend has no Backup Artifacts rather than showing an empty list.
- **Checkpoint and cutover are SQLite-only.** The `checkpoint *` and `cutover *` upgrade-bridge commands (issues #190–#192) refuse on PostgreSQL. A future coordinated-upgrade checkpoint will be designed for both backends.

- **Portable SQL first, then a `sqlx::Any` seam.** A behaviour-preserving slice on SQLite alone rewrites the SQLite-only forms into shared ones: `INSERT OR IGNORE` becomes `ON CONFLICT DO NOTHING` with its `rows_affected` dedup meaning kept, `last_insert_rowid()` becomes `RETURNING`, `rowid` batching becomes primary-key/keyset batching, scalar `MIN`/`MAX` become `CASE`, `julianday` arithmetic moves to Rust or bound parameters, and `?` becomes `$N` (which sqlx-sqlite accepts). The domain query layer then runs on one `AnyPool` with one SQL text. Ownership, integrity checks, PRAGMAs, progress interruption, error classification, backup, checkpoint and Storage Backend Migration stay concrete per backend. A Report Ingestion spike gates the seam: `Any` decodes `bool` only from a Bool value, so the flag mapping is decided there together with BLOB, `rows_affected`, `RETURNING`, error codes and performance. A failed spike reopens the seam decision. This is still typed SQL, not an ORM.
- **Configuration without inline secrets.** `[storage] backend = "postgres"` selects the backend, and its absence means SQLite with today's `db_path`. `[storage.postgres]` takes `host` (or a unix-socket directory), `port`, `database` and `user`, plus a `password_file` that gets the same owner-only, no-symlink checks as `pepper_file`. `sslmode` defaults to `verify-full` and allows only `verify-ca` otherwise; `disable` is accepted only over a unix socket. `ssl_root_cert_file` and `connect_timeout_secs` complete the section. No URL/DSN form exists. `db_path` with the PostgreSQL backend is rejected. `PG*` environment variables and `.pgpass` are ignored, so connection options are built explicitly rather than with `PgConnectOptions::new()`. Host, port, database and user may appear in logs, but the password never does, and the options' `Debug` output is redacted.
- **Losing ownership ends the process.** A dedicated ownership connection holds the advisory lock under a heartbeat and TCP keepalive. If it is lost, readiness turns 503 and the Server shuts down in order with a non-zero exit; it never re-acquires and continues in-process. A work connection lost mid-transaction rolls back, and Ingestion answers with a retryable 503 that the Agent's identical-bytes retry resolves through the existing idempotency. The work connection may reconnect only while ownership is held. Connection errors never latch corruption; only SQLSTATE `XX001`/`XX002` do.
- **Readiness and metrics.** SQLite deployments are unchanged. On PostgreSQL the `/health/ready` storage component is reported as `postgres`, and SQLite page/freelist metrics are not exposed. `platpulse_storage_database_bytes` comes from `pg_database_size` and is omitted, never zero, when unreadable.
- **No capacity protection on PostgreSQL.** `[capacity]` with the PostgreSQL backend is rejected at startup with a dedicated message, because the database's disk belongs to the database operator. Doctor reports the storage check as NOT_APPLICABLE and the Admin capacity surface says it does not apply. A full PostgreSQL disk fails writes, and Ingestion answers with a retryable 503 rather than losing data silently.
- **Tests on both backends.** One shared test-database helper selected by `PLATPULSE_TEST_STORAGE=sqlite|postgres` replaces the per-file helpers. On PostgreSQL each test gets a fresh database cloned from a migrated template. CI runs the full `cargo test --workspace` on SQLite, PostgreSQL 15 and the latest major. SQLite-only tests carry an explicit reason and show as skipped, never passed, in PostgreSQL mode. An unreachable PostgreSQL fails the run instead of falling back to SQLite. An end-to-end Storage Backend Migration test ingests into SQLite, migrates, and serves from PostgreSQL. It checks that Public and Admin answers are unchanged, that an exact replay neither re-accumulates nor conflicts, and that same-identity different bytes still conflict.
- **Owner-only visibility.** The Admin Doctor and Settings surfaces show the Storage Backend, the PostgreSQL server version, and host, database and user. Public Projections, Public DTOs and SSE carry nothing about storage. The backend changes only through configuration and a restart; the Admin offers no switch.

- **No silent return to a stale SQLite.** Once the PostgreSQL Server has accepted a report, Agents have applied Receipts, emptied their Durable Spool, and advanced sequence and Inventory Declaration Records, so starting again on the old SQLite file would break ordering, Receipt and Purge-barrier evidence. `storage migrate` therefore writes a sibling marker (`platpulse.db.migrated`) without touching the database file. While the marker exists, the SQLite backend refuses to start and refuses every writing CLI command. Rollback goes only through `storage migrate abort`, and only while the target has accepted no write since the migration baseline recorded at commit: no report, Admin mutation or background write. A successful abort removes the marker. After any business write on PostgreSQL, abort is refused and the fix is forward on PostgreSQL, matching the cutover rollback rule.
- **One target transaction, bounded downtime.** Copy and verification run inside a single target transaction that commits only when every check passes. Any failure leaves the target empty and the command retryable. The command holds ownership on both sides (source flock + EXCLUSIVE, target advisory lock) and reports per-table progress and an estimate. During the offline window Agents keep spooling, and a full spool drops its oldest historical reports into History Gaps, as it already does. The window must therefore stay shorter than the spool's capacity, and release qualification measures migration time on production-sized data.

## Consequences

- Documentation changes before code. The first slice accepts this ADR, removes PostgreSQL from the non-goals in `docs/design/platpulse.md`, `docs/design/webui.md` and `README.md`, and amends AGENTS.md. The amendment covers SQLx typed SQL on SQLite or PostgreSQL for the Server and SQLite only for the Agent, tests against real temp SQLite and real PostgreSQL, PostgreSQL test commands, and every schema change shipping both backends' migrations together. The PostgreSQL chapter of `docs/deployment.md` follows the feature slices. It covers role and schema ownership, a `C`-collation database, TLS, the warning that Storage Snapshots carry raw sensitive data, and the Storage Backend Migration runbook with its downtime, abort and forward-fix steps.
- Delivery order, tracked as child issues of #226:
  - S0 documentation sync.
  - S1 portable SQL on SQLite.
  - S2 `Any` spike on Report Ingestion.
  - S3 storage seam with SQLite as the only backend and the shared test helper.
  - S4 PostgreSQL core: configuration, ownership connection, version/collation checks, baseline migration, schema-equivalence check, and CI on 15 and the latest major.
  - S5 operations boundary: refusals, Doctor, readiness/metrics, capacity rejection, and the Admin surfaces.
  - S6 `storage migrate` and `abort`, with the end-to-end test.
  - S7 deployment documentation and release qualification.

  S5 and S6 may proceed in parallel after S4.

- The seam is `sqlx::Any` (S2), which hides the native SQLite handle. An interruptible SQLite integrity check (startup `integrity_check`, Doctor `quick_check`, issue #194) therefore runs as a maintenance session (S3). The session closes the pool's only connection and holds a gate so that no replacement can configure itself. It opens a native connection with a progress handler, closes it, and then reopens the gate. At no point are two connections open, so the session cannot meet the two-connection precondition of the WAL-reset bug (docs/research/server-db-corruption-investigation.md). What we accept: closing the last connection checkpoints the WAL the way a clean shutdown does. Between the close and the native open there is a brief window in which another process could take the file lock. If it holds the lock past the busy timeout, the check fails and the pool reconnects on the next request. This is the issue #137 exposure, limited to an operator-triggered Doctor run or startup. It does not apply to the serving path.

## Considered options

- **PostgreSQL replaces SQLite.** Rejected: SQLite stays the zero-dependency single-host deployment.
- **Translate all SQLite migrations to PostgreSQL.** Rejected: PostgreSQL has no deployed history to replay, and the SQLite table-rebuild idiom does not carry over.
- **Native `timestamptz`/`jsonb` from the start.** Deferred: it splits the SQL and turns migration into a type conversion.
- **A pooled, concurrent PostgreSQL backend in 0.3.0.** Deferred: Ingestion invariants rely on serialization, not row locks.
- **A sanitized PostgreSQL logical backup.** Rejected: it would be a third privacy boundary to maintain. PostgreSQL's own backups are Storage Snapshots under ADR 0008's existing terms.
