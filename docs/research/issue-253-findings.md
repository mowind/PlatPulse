# Issue #253 findings — 以 Report Ingestion 验证 \`sqlx::Any\` 存储接缝 (the \`sqlx::Any\` storage seam, proven on Report Ingestion)

**#253** is S2 of the PostgreSQL roadmap (#226, ADR 0013), the gate between S1 (#252, portable SQL, merged as 7569663) and S3 (#254, the storage seam). ADR 0013 chose "portable SQL first, then one \`sqlx::Any\` seam" and made this spike the gate: an unacceptable limit reopens the decision. This document records what the spike ran, what it proved, and what S3 must do because of it.

**Verdict: the gate passes.** No limit found is unacceptable. Every incompatibility is either already avoided by S1's portable SQL, or is a bounded, enumerable rewrite with a test-enforceable rule. Two findings are correctness hazards that S3 must fix *before* PostgreSQL is offered to anyone (§Q7 aborted-transaction semantics, §Q5 the error classifier), and one is a configuration decision ADR 0013's config rules force (§Options, \`PG*\` environment leakage).

The spike code lives on the throwaway branch \`spike/253-sqlx-any\` (not merged, as the ticket allows): \`crates/platpulse-server/tests/any_spike.rs\`, the schema translator \`crates/platpulse-server/tests/any_spike/translate_schema.py\` and its output \`pg_schema.sql\`. The Cargo change there (\`sqlx\` features \`any\`, \`postgres\`) is spike-only.

## Method

1. **Real schema, both backends.** The final SQLite schema (82 tables, 176 indexes, 4 triggers, built by applying every Server migration) was mechanically translated to PostgreSQL: \`INTEGER PRIMARY KEY\` → \`BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY\`, \`INTEGER\` → \`BIGINT\`, \`REAL\` → \`DOUBLE PRECISION\`, \`BLOB\` → \`BYTEA\`, \`TEXT\` → \`TEXT COLLATE "C"\`, \`GLOB '[A-Z][A-Z]'\` → \`~ '^[A-Z][A-Z]$'\`, tables ordered by FK dependency; triggers were left out (they become PL/pgSQL in S3). All 82 tables and indexes applied cleanly. This is a probe, not the S3 baseline.
2. **Real SQL.** The "accepted Report" slice of \`ingest_report\` (crates/platpulse-server/src/http/report_ingestion.rs) was copied **verbatim** — receipt lookup (\`ReceiptRow\` via \`FromRow\`), \`AgentRow\`, boot / inventory / sequence checks, the \`nodes\` and \`component_status\` upserts, \`block_history_state\`, \`block_summaries ... ON CONFLICT DO NOTHING\` with \`rows_affected\` dedup, the identity window, the BLOB receipt insert, \`agent_boots\`, the 27-parameter \`agents\` UPDATE, and the audit insert with \`RETURNING\`. One macro generates the slice twice, over \`AnyConnection\` and over the native \`SqliteConnection\`, so both run byte-identical SQL.
3. **Real servers.** Every test runs against temp-file SQLite and against PostgreSQL 15, 17 and 18 (Docker, one database per test). All 10 tests pass on all four; the two \`#[ignore]\` tests (environment leak, benchmark) were run by hand.

## Q1 — Boolean mapping (recommendation: keep \`INTEGER\`/\`BIGINT CHECK (x IN (0,1))\`, decode and bind \`i64\`)

- The \`Any\` driver decodes \`bool\` **only** from an \`AnyValueKind::Bool\` value. An integer flag decoded as \`bool\` fails on **both** backends with \`mismatched types; Rust type \`bool\` is not compatible with SQL type \`BIGINT\`\` — this is a SQLite regression too, not only a PostgreSQL one. Decoding as \`i64\` works on both.
- Binding a Rust \`bool\` into a PostgreSQL \`BIGINT\` is worse than a type error: the server rejects the Bind message with \`08P01\` "insufficient data left in message" (protocol violation). SQLite accepts it silently (Any binds bool as int there), so a SQLite-only test suite would never see it.
- A native \`BOOLEAN\` column does not help: \`flag = 1\` fails on PostgreSQL with \`42883\`, a \`BOOLEAN\` does not decode as \`i64\`, and SQLite has no boolean type, so the two schemas would diverge in every predicate.
- Predicates are values too: \`EXISTS(...)\` yields an integer on SQLite and a \`boolean\` on PostgreSQL. \`CASE WHEN EXISTS(...) THEN 1 ELSE 0 END\` yields \`i64\` on both.
- **Rule for S3:** mirror every flag as \`BIGINT NOT NULL CHECK (x IN (0,1))\` on PostgreSQL, decode and bind \`i64\` only, never \`bool\` in domain SQL, and wrap any selected predicate in \`CASE ... THEN 1 ELSE 0 END\`. Report Ingestion already binds flags as \`i64\`. **Known rewrites:** 7 \`bool\` decodes — crates/platpulse-server/src/http/alerts_admin.rs:683, :793, :1375, :1392 and crates/platpulse-server/src/alerts/mod.rs:803, :831, :851. 10 SQL \`EXISTS(\` sites must be checked for whether they are selected (as opposed to used in \`WHERE\`).

## Q2 — BLOB / \`bytea\` round-trip: identical

A 34-byte digest containing \`0x00\` and \`0xff\` round-trips and is found again by equality lookup; a 300,000-byte \`receipt_body\` round-trips byte-identical; \`length()\` counts bytes on both; a \`UNIQUE\` BLOB column raises a unique violation on both. \`credential_digest\`, \`csrf_token_digest\`, \`token_digest\` and \`receipt_body\` need nothing beyond \`BLOB\` → \`BYTEA\`.

## Q3 / Q4 — \`rows_affected\` and \`RETURNING\`: identical

\`ON CONFLICT DO NOTHING\` reports 1 then 0; \`DO UPDATE\` 1 and 1; \`DO UPDATE ... WHERE false\` 0; an \`UPDATE\` writing the same values still reports 1 on both; \`RETURNING\` ids are consecutive; \`ON CONFLICT DO NOTHING RETURNING\` on a conflict returns no row on both. Block-history dedup (which keys off \`rows_affected\`) is therefore portable as written by S1.

## Q5 — Error classification: \`code()\` works, the current classifier does not

- SQLite through Any keeps its extended codes in \`DatabaseError::code()\`: primary-key \`1555\`, FK \`787\`, \`BUSY\` (\`code & 0xff == 5\`, reproduced with a \`BEGIN IMMEDIATE\` holder and a 50 ms busy timeout), \`NOTADB\` \`26\`, \`CORRUPT\` (\`code & 0xff == 11\`); \`kind()\` is populated and \`downcast_ref::<SqliteError>()\` works.
- PostgreSQL gives SQLSTATEs: \`23505\` (with the constraint name, e.g. \`agents_pkey\`, via \`PgDatabaseError\`), \`23503\`; \`XX001\` / \`XX002\` reach \`code()\` unchanged.
- **Hazard:** crates/platpulse-server/src/http/health.rs:23 \`is_corruption_error\` parses \`code()\` as an integer and tests \`code & 0xff\` against \`11 | 26\`. On PostgreSQL it misses \`XX001\`/\`XX002\` (not numeric) **and misclassifies \`22027\`** (\`trim_error\`; \`22027 & 0xff == 11\`) as corruption. **Rule for S3:** the classifier dispatches on the backend (\`AnyConnection::backend_name()\` / the error's concrete type) — numeric extended codes for SQLite, SQLSTATE strings (\`XX001\`, \`XX002\`, class \`23\`) for PostgreSQL. Unique/FK checks should prefer \`kind()\`, which is portable.

## Q6 — Performance: Any over SQLite costs about 4–8 % per Report

Release build, the verbatim slice, 2,000 Reports of 4 blocks each, single connection, native and Any alternated over two rounds:

| connection | synchronous | mean | p50 | p95 |
| --- | --- | --- | --- | --- |
| native \`SqliteConnection\` | FULL | 555.5–555.9 µs | 541.9–543.7 µs | 668.7–671.9 µs |
| \`AnyConnection\` over SQLite | FULL | 576.3–584.0 µs | 552.0–560.0 µs | 675.9–823.4 µs |
| native \`SqliteConnection\` | OFF | 550.0–550.4 µs | 535.4–535.9 µs | 636.1–689.2 µs |
| \`AnyConnection\` over SQLite | OFF | 574.7–597.9 µs | 550.9–556.2 µs | 780.2–919.8 µs |
| \`AnyConnection\` over PostgreSQL 17 (Docker, localhost) | default | 4,600.5 µs | 4,453.3 µs | 5,189.7 µs |

The Any overhead is ~20–50 µs mean / ~10–20 µs p50 per Report (value boxing into \`AnyArguments\` / \`AnyRow\`), with a fatter p95 tail. Against the Report cadence this is noise; it is not a reason to keep two code paths. The PostgreSQL figure is per-statement network round-trips plus a durable commit on a Docker volume — it is a sanity number, not a benchmark of PostgreSQL, and it says nothing against the seam.

## Q7 — \`FromRow\`, \`Transaction<Any>\`, and the \`defer_foreign_keys\` replacement

- \`#[derive(FromRow)]\` structs (\`AgentRow\`, \`ReceiptRow\`) decode from \`AnyRow\` unchanged; commit, rollback and nested savepoints behave identically.
- **Hazard — an ignored failure aborts a PostgreSQL transaction silently.** SQLite lets a transaction continue after a failed statement. PostgreSQL puts it into the aborted state: the next statement fails with \`25P02\`, and \`commit()\` **returns \`Ok\`** while the server turns the \`COMMIT\` into a \`ROLLBACK\` — measured: SQLite persisted 1 row, PostgreSQL persisted 0, no error surfaced. Wrapping the optional statement in a savepoint (\`tx.begin()\` → statement → commit / rollback) restores SQLite's behaviour (2 rows persisted on both). The Server has exactly this pattern in the ingestion transaction: \`let _ =\` on \`insert_audit_event\` at crates/platpulse-server/src/http/report_ingestion.rs:2025, :2064, :2113, :2166, on \`record_security_event\` at :2610, :2627, :2905, on the \`report_sequence_gaps\` insert at :2669, plus \`.map_err(|_| ()).ok()\` on the boot-close \`UPDATE agents\` / \`UPDATE agent_boots\` at :3503-3518 and the swallowed results at :2458 and :2913; and crates/platpulse-server/src/http/admin.rs:7089, :7127. On PostgreSQL any one of these failing would discard an accepted Report while answering 200. **Rule for S3:** no ignored statement inside a transaction — either propagate the error or run the optional statement in a savepoint; add a PostgreSQL test that forces one to fail.
- **\`PRAGMA defer_foreign_keys\` replacement.** Node Transfer (crates/platpulse-server/src/http/report_ingestion.rs:2140) moves \`nodes.agent_id\` and the composite FK \`component_status (agent_id, node_id)\` in one transaction. \`PRAGMA\` on PostgreSQL is \`42601\`; \`SET CONSTRAINTS ... DEFERRED\` on a non-deferrable FK is \`42809\` "constraint ... is not deferrable". With the PostgreSQL FK declared \`DEFERRABLE INITIALLY IMMEDIATE\` and \`SET CONSTRAINTS component_status_agent_id_node_id_fkey DEFERRED\` issued when \`backend_name()\` is \`"PostgreSQL"\` (\`"SQLite"\` keeps the PRAGMA), the transfer commits on both. **Rule for S3:** that FK is \`DEFERRABLE INITIALLY IMMEDIATE\` in the PostgreSQL baseline, and the deferral is a seam function, not inline SQL.

## Connection options through \`AnyConnectOptions\`

- \`AnyConnectOptions\` is URL-only. SQLite's URL accepts only \`mode\` / \`cache\` / \`immutable\` / \`vfs\`; \`foreign_keys\` is on by default and \`journal_mode=WAL\` persists in the file, but \`synchronous\` and \`busy_timeout\` must be set in \`after_connect\` (verified: \`foreign_keys=1\`, \`wal\`, \`synchronous=2\`, \`busy_timeout=5000\`).
- **PostgreSQL environment leaks through a URL.** \`PgConnectOptions::parse_from_url\` starts from the environment (\`PGHOST\`, \`PGPORT\`, \`PGUSER\`, \`PGPASSWORD\`, \`PGSSLMODE\`, \`PGSSLROOTCERT\`/\`PGSSLCERT\`/\`PGSSLKEY\`, \`PGAPPNAME\`, \`PGOPTIONS\`) and falls back to \`.pgpass\` when no password is given. Measured: \`PGAPPNAME=leaked\` became \`application_name = leaked\`, and \`PGOPTIONS='-c statement_timeout=4321'\` became \`statement_timeout = 4321ms\` on a URL that named neither. This contradicts ADR 0013's config rule (no URL/DSN; \`PG*\` and \`.pgpass\` ignored). The process cannot unset them (\`unsafe_code = "forbid"\` rules out \`std::env::remove_var\`), and \`AnyConnection\`'s backend field is crate-private, so a hand-built \`PgConnectOptions\` cannot be wrapped into an \`AnyConnection\`. \`AnyConnectOptions\`' \`Debug\` did **not** contain the password.
- **Decision for S3 (one of):** (a) fail closed at startup when any \`PG*\` variable is set while the PostgreSQL backend is configured, set every leakable option explicitly in the generated URL, and always supply the password (from \`password_file\`) so \`.pgpass\` is never consulted; or (b) keep the seam's own enum over concrete \`PgPool\` / \`SqlitePool\` and give up \`Any\`. The spike's evidence favours (a): it keeps one query path and the leak is closable at the boundary.

## What S3 (#254) inherits

1. Flags are \`BIGINT CHECK (0,1)\`, decoded and bound as \`i64\`; rewrite the 7 \`bool\` decodes; selected predicates go through \`CASE\`.
2. No ignored statement inside a transaction (the 15 sites above), with a PostgreSQL test that forces one to fail.
3. Backend-dispatched error classification replacing \`code & 0xff\`.
4. \`DEFERRABLE INITIALLY IMMEDIATE\` on \`component_status (agent_id, node_id)\` and a seam function for the deferral.
5. \`CAST\` around \`SUM\`/\`AVG\`; replace \`json_*\` and \`INDEXED BY\` in domain SQL.
6. \`PG*\` / \`.pgpass\` closed at startup; SQLite pragmas in \`after_connect\`.
7. Triggers (\`node_validator_links_no_overlap_*\`, \`node_relationship_intervals_no_overlap_*\`) become PL/pgSQL with the same \`RAISE\` messages, and \`GLOB\` checks become regex checks, in the PostgreSQL baseline.
