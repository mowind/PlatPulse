# Issue #218 findings — automatic Validator identity and current status on the Admin surfaces

**#218** ("feat: 自动 Validator 身份与当前状态", parent #202, stories 62, 63 and 68) asks for two things that the design keeps apart on purpose. The first is an **identification**: which chain identity a Node's own Agent evidence proves, resolved from the Node's Network plus the *full* P2P public key its Agent observed — "PlatPulse Node UUID、短 fingerprint、显示名、IP、当前共识成员标志都不是替代查找键" (docs/design/platpulse.md:806). The second is a **current staking verdict**: whether that identity is currently a valid, staking Validator, which is Provider evidence and therefore a different question with a different owner (docs/design/platpulse.md:809-817). The ticket's job was to make both visible on the Admin surfaces without ever turning missing evidence into a negative answer: "缺少可信公钥、Network Identity 不匹配或 Network 未配置可用 Provider 时，不能猜测关联" and "普通 HTTP 失败不是无质押的证据" (docs/design/platpulse.md:819).

Everything below is the working tree as it stands, read at the line references given. It is not a plan, and it makes no claim about a run this pass did not perform (see VERIFICATION).

## SERVER — what already existed, and the two real gaps

1. **The automatic model existed; nothing read it back out to Admin.** `node_validator_identity_status` and the automatic Link interval were already written by one function only — `pub async fn discover_automatic_links(db: &ServerDatabase) -> Result<IdentityDiscoverySummary, ValidatorError>` (crates/platpulse-server/src/validator.rs:2467) — and the Public projection already consumed them (crates/platpulse-server/src/http/public.rs:2238 for the reason and :1053-1070 `associate_node_validators` for the association). Admin had no endpoint that returned the same facts, so an Owner had to read Public to answer "which Node belongs to which Validator".
2. **The Admin Node detail deliberately answered `validator: None`.** The Admin projection for one Node carried no identity block at all, so the one page an Owner uses for Node diagnosis said nothing about whether the Server had identified that Node's chain identity, and nothing about why it had not.
3. **The Admin Validator DTO had no current-status evidence to render.** `AdminValidatorInsight` (crates/platpulse-server/src/http/validators_admin.rs:36) carried the Provider fields, but the *derived* answers — the canonical status, its qualifier, its state, the activity series and the age of the retained last-good value — were only computed inside the Public projection. Two projections of the same evidence can drift; the design fix was to move the derivation down into `validator.rs` and let every surface call it.
4. **A Provider that is unconfigured had no disclosure path on Admin.** With no `[validator_provider]`, `validator_dto` (crates/platpulse-server/src/http/validators_admin.rs:399) synthesizes an insight. The gap was `source`: the synthesized answer carried `Some("disabled")`, which the WebUI rendered as the literal string "disabled" — a value that reads like a measurement instead of "no Provider is configured".

## What was added

### The identity projection: one query, one helper set, in `validator.rs`

- `pub struct NodeValidatorIdentityRecord` (crates/platpulse-server/src/validator.rs:2226) is the row shape: `node_id`, `node_display_name`, `network_key`, `lifecycle`, `state`, `observed_node_key`, `evaluated_at`, `validator_id`, `validator_node_key`, with `pub fn association_effective(&self) -> bool { self.validator_id.is_some() && self.lifecycle == "active" }` — the same rule the Public association uses, so Admin cannot claim a link Public does not project.
- `pub async fn list_node_validator_identities(db: &ServerDatabase, node_id: Option<&str>) -> Result<Vec<NodeValidatorIdentityRecord>, ValidatorError>` (:2257) is one query: `nodes` LEFT JOIN `node_validator_identity_status` LEFT JOIN the newest OPEN `origin='automatic'` link LEFT JOIN `validators`. The LEFT JOINs are load-bearing: a Node the discovery pass has never examined still comes back with `state = 'not_evaluated'` rather than disappearing, so the coverage table can say "not evaluated yet" instead of silently omitting the Node. Ordering is `network_key, node_id`.
- `pub fn project_activity(outcome, activity: Option<&str>, freshness) -> (String, String)` (:525) and `pub fn automatic_identity_reason(state: Option<&str>) -> Option<String>` (:562) moved down from `http/public.rs`; `public_validator_activity` (crates/platpulse-server/src/http/public.rs:882) now delegates to the first, and the private `validator_identity_reason` was deleted. One copy of each rule, two callers.
- `pub fn last_good_age_seconds(last_good_received_at: Option<&str>, now: OffsetDateTime) -> Option<i64>` (:2213) replaces per-surface arithmetic, so a surface can only render an age the Server itself computed, and `None` stays "unknown" rather than becoming `0`.
- `associate`: `automatic_identity_reason` returns `None` exactly for `identified` and for an absent state, and otherwise a sentence per unresolved state — `not_evaluated`, `missing_public_key`, `invalid_public_key`, `network_identity_missing`, `network_identity_mismatch`, and a fallback. The reason text is part of the contract the e2e spec asserts by substring (`toContain`), so re-wording a sentence means updating the spec with it.
- Unit tests cover each helper directly: `project_activity_follows_the_evidence_predicates`, `automatic_identity_reason_explains_every_unresolved_state`, `last_good_age_is_absent_without_a_last_good_value`, `association_effectiveness_requires_an_open_interval_and_an_active_node`.

### The Admin DTOs and the one new endpoint

- `pub struct AdminNodeValidatorIdentity` (crates/platpulse-server/src/http/validators_admin.rs:353) is the browser-facing identity block: `nodeId`, `nodeDisplayName`, `networkKey`, `lifecycle`, `state` (defaults `not_evaluated`), `reason`, `observedValidatorNodeKey`, `validatorId`, `validatorNodeKey`, `associationEffective`, `evaluatedAt`. It is **camelCase even when nested inside the snake_case `AdminNodeDetail`** (crates/platpulse-server/src/http/admin.rs:2403): every DTO in `validators_admin.rs` is camelCase, the choice is pinned by the repository's own `validator_api_dtos_use_browser_camel_case`, and a mixed casing was judged worse than a nesting seam. The e2e spec asserts `validatorNodeKey` / `validatorId` / `associationEffective` on the Node answer and `validator_identity` on the envelope.
- `pub(crate) async fn admin_validator_identities` (:955), routed in `router()` (:971) at `/validator-identities` in the Admin validator group, answers **a bare JSON array** (utoipa `body = [AdminNodeValidatorIdentity]`). It reads through the same `list_node_validator_identities` the Node detail uses, so the coverage table and the per-Node panel cannot disagree.
- `AdminNodeDetail` gained `pub validator_identity: Option<super::validators_admin::AdminNodeValidatorIdentity>` (crates/platpulse-server/src/http/admin.rs:2403), resolved at :2471 and returned through `error_response` on failure. The neighbouring transfer query deliberately swallows its error; this one does not, because a database failure must not be presented as "this Node has no identity".
- `AdminValidatorInsight` (:36) gained `activity`, `activity_state`, `current_validator_status`, `current_validator_status_state`, `current_validator_status_qualifier`, `last_good_age_seconds`, and `validator_dto` (:399) now derives them with the shared helpers. The synthesized no-insight branch (no Provider configured) answers `state 'not_configured'`, `freshness 'unknown'`, `outcome 'not_configured'`, `source Some("disabled")`, `counterState 'normal'`, `activity Some('unknown')`, `currentValidatorStatus 'unknown'`, qualifier `None`, `lastGoodAgeSeconds None` and every other field `null` — i.e. an unreadable Provider is Unknown across the board and never `not_validator`.
- `docs/openapi/openapi.json` was regenerated from the Server itself: 107 paths, pure additions.

### Interval semantics this ticket relies on (unchanged, now surfaced)

- A key change **closes** the open automatic interval and opens a new one, with the boundary chosen by `close_interval_boundary(now, valid_from)` — `now` when `now > valid_from`, otherwise `valid_from + 1 second` — so a same-instant re-identification still produces an ordering the history can explain.
- `network_identity_mismatch` and `invalid_public_key` close the open interval; `network_identity_missing` and `missing_public_key` do **not**. An absence of a key is not evidence that the identity changed, so it must not quietly end an interval the Server cannot disprove.
- `discover_automatic_links` reads `nodes n JOIN networks r ON r.network_key = n.network_key LEFT JOIN current_node_chain_observations c ON c.node_id = n.node_id WHERE n.lifecycle = 'active'` (crates/platpulse-server/src/validator.rs:2473), so a retired Node stops being re-evaluated but keeps its last recorded state.
- Node Purge removes `node_validator_identity_status`, `node_validator_links` and `node_transfers` for that Node (crates/platpulse-server/src/node_purge.rs:368-371) and records only `deleted_nodes` (:397). The **Validator** identity itself and its retained Provider evidence survive, and so does the interval of every Node that still exists — but the purged Node's own interval is deleted with it, so the Admin Validator detail's "Node associations" table no longer shows that Node and `linkCount` falls by that Node's intervals — it reads 0 only when the purged Node held this identity's only association, which is the case the integration test covers. The deleted association reads back as unavailable instead of being reconstructed. Shared identity is not collateral damage of a Node deletion (the 数据所有权 row of docs/design/platpulse.md:868); Node-owned association history is.

### How discovery is triggered (why the e2e spec restarts the Server)

`serve` spawns the discovery worker unconditionally (crates/platpulse-server/src/cli.rs:1336-1361): `refresh_seconds = config.validator_provider.as_ref().map(|p| p.refresh_seconds).unwrap_or(60)`, the tokio interval's first tick fires immediately, so the first pass runs at startup even with no Provider, and only then does `if !provider_configured { continue; }` turn the loop into a no-op. Failures log `Validator identity discovery deferred: {redacted}` and never touch Node health or readiness. There is no `validator discover` CLI subcommand, so the only way to make a deterministic test observe a discovery pass is to restart the Server — which is why `platpulse-web/e2e/validators-admin-acceptance.spec.ts` seeds the observations, restarts, and only then reads the surfaces in three of its four tests. The pass is no longer silent, though: when `IdentityDiscoverySummary::changed_associations()` is true (an association was opened or closed — crates/platpulse-server/src/validator.rs) the worker publishes a `validator` invalidation on both the Admin and Public realtime channels (crates/platpulse-server/src/cli.rs), which `applyAdminInvalidation` maps to the Validators, Validator-Link, identity-coverage and Node keys (platpulse-web/src/api/admin.ts:1777-1779). The fourth acceptance test states that live: the page is already open, the Server is never restarted, and the listener proves zero main-frame navigations. A pass that only re-writes a Node's `state`/`reason` without opening or closing an interval still publishes nothing and surfaces on the next navigation or refetch.

### Two defects the acceptance run found

1. **A label printed three times is not a locator.** `ValidatorIdentityPanel` renders the same notice label in the header badge, the paragraph badge and the `State` value, so a bare `getByText('Identified', { exact: true })` resolved to three elements and Playwright failed with a strict-mode violation. The fix reads the value through its own `dt`: `panel.locator('dl > div:has(> dt:text-is("State")) > dd')`. No page markup was changed to make a test pass.
2. **One Report id names one immutable body.** Stating the contradiction as an *edit* of the fixture's Report was refused: `report_ingestion` keys the receipt on `report_id` and answers 409 `report_identity_conflict` "Report identity conflicts with a stored report" when the same id arrives with a different body hash (crates/platpulse-server/src/http/report_ingestion.rs:2023-2049). The corrected premise is the one the design actually states — a later Report from the same Agent is a later Report — so the spec submits it under its own id (`SECOND_REPORT_ID`). The Server-side path the test then relies on is confirmed: the Node-level observation upsert replaces the stored genesis (`network_genesis_hash=COALESCE(excluded.network_genesis_hash, ...)`, crates/platpulse-server/src/http/report_ingestion.rs:1609-1610), and `block_network_identity_mismatches` (:696-731) only inspects `report.block_summaries`, which the fixture leaves empty, so nothing else perturbs the Node-level mismatch.

## What this ticket does not claim

- No live PlatScan run and no new Provider field mapping: the authoritative-negative conditions for `locked`/`exiting`/`verifying` still rest on the evidence already recorded in docs/research/platscan-current-validator-status-evidence.md, and docs/design/platpulse.md:819 keeps its "仍需主源证据验证" caveat.
- No manual identity or role fallback was reintroduced, and no manual entry point exists: the automatic Link remains the only association model (docs/design/platpulse.md:807).
- The Public/Home projection is unchanged (#173); #218 extends the Admin surfaces and reuses the same helpers so the two cannot drift.
- The ageing of an authoritative absence is inherited, not re-decided. `project_activity` (crates/platpulse-server/src/validator.rs:531) and `current_validator_status` (:695-699) treat a strictly validated 200/code 0/empty-node-id/status-0 answer as Observing/`current` and NotValidator/`current`, and the `empty` outcome updates neither `activity` nor `last_good_received_at` (the non-success branch of `apply_provider_result`, crates/platpulse-server/src/validator.rs:2781-2810). A Server that stops refreshing therefore keeps presenting the last authoritative absence as current, and `success(active) → empty → error` presents the older `active` as the retained last-good. This is #168's rule shared with the Public surface (#173), the authoritative-negative conditions are still pending primary-source evidence, and #218 does not fork the projection to change it — the Admin detail does print `Attempted at` and `Observed at`, so the age of the last authoritative attempt stays visible beside the verdict. Review pushed back on this disclosure, and the pushback is recorded rather than argued away: a permanently `current` absence does contravene the design's own "Provider 失败或信息过期不产生新的结论，保留 last-good 并标 Stale" row (docs/design/platpulse.md:817), so it is an **inherited defect** of the projection with an Admin symptom, not an accepted rule — see F1 below.
- A Node Purge deletes the purged Node's own Link intervals (crates/platpulse-server/src/node_purge.rs:368-371), so the Admin Validator detail's association table drops that Node (`linkCount` 0) and the identity coverage list no longer lists it (crates/platpulse-server/tests/validator_admin_identity.rs:648-707). Only the shared `validators` identity row and its retained Provider evidence and history survive; Node-owned association history is deleted with the Node and is never reconstructed. The count reads 0 in that test because the purged Node held this identity's only association; with a second surviving Node the row survives with the remaining intervals.
## Reviewer findings and disposition

The change was reviewed by a subagent with `cliproxyapi/gpt-6.1-sol` at high reasoning effort, against the working tree (diff plus the new feature files, tests, spec and docs). Its verdict was **request changes**, with six findings. Three were fixed, one was fixed in code after the review pushed back on an earlier disclosure-only disposition, and two are disclosed as follow-ups with the reason. The finding ids below (F1-F6) are stable and are the ones the closing comment refers to.

- **F1 - an authoritative absence never ages (MUST FIX, disclosed).** `project_activity` (crates/platpulse-server/src/validator.rs:531) and `current_validator_status` (:695-699) project a strictly validated empty answer as Observing/`current` and NotValidator/`current` regardless of freshness, and the `empty` outcome updates neither `activity` nor `last_good_received_at` (the non-success branch of `apply_provider_result`, :2781-2810). So a Server that stops refreshing keeps presenting the last authoritative absence as current, and `success(active)` -> `empty` -> `error` presents the *older* `active` verdict as the retained last-good. The correct fix is to persist the latest confirmed verdict including an absence, with its own confirmation timestamp, and then apply freshness to that verdict - which changes `project_activity`, `current_validator_status` and `apply_provider_result` and therefore the Public projection #173 shares. This ticket keeps the inherited rule (no primary-source evidence justifies re-deciding it here) and RELABELS it as an inherited defect contradicting docs/design/platpulse.md:817 rather than as a rule this ticket endorses (docs/design/platpulse.md:821, :69-70 of this document). A follow-up must state the transition the fix has to satisfy: `active -> empty -> error` retains the *absence*, and a first `empty` followed by `error` retains that absence instead of degrading to Unknown.
- **F2 - the purge claim was wrong (FIXED).** The docs and a page intro claimed a purged Node's ended Link interval stays visible. It does not: crates/platpulse-server/src/node_purge.rs:368-371 deletes that Node's `node_validator_identity_status`, `node_validator_links` and `node_transfers` rows, and crates/platpulse-server/tests/validator_admin_identity.rs asserts `link_rows == 0` (:648-654), the shared Validator surviving with `linkCount == 0` (:674) and `links` empty (:687), and the purged Node absent from the coverage list (:699-707). Corrected in docs/design/webui.md:203 and :1294, docs/design/platpulse.md:821 and both bullets of this document. What survives is the shared `validators` identity row, its retained Provider evidence and its history on other Nodes.
- **F3 - the Public-association cell read the discovery state instead of the Server's association (FIXED).** The cell decided whether Public shows an association from the resolution of the identity state, so a Node whose key rotation closed nothing but whose latest evidence disagrees would have read `No Link to project` while the Server still held an open interval. `validatorPublicAssociation` (platpulse-web/src/validators.ts:73) now returns null without a `validatorId` and otherwise decides from `associationEffective` (the same facts `validatorIdentityNotice` uses), and the Node detail's `Automatic Link` item branches on `identity?.validatorId` (platpulse-web/src/pages/AdminNodes.tsx:1271-1343). Honest scope note: the disagreement is not reachable through Report ingestion, because the observation upsert retains the identity columns with `COALESCE(excluded..., current...)` (crates/platpulse-server/src/http/report_ingestion.rs:1609-1610) so only a Node that never reported a key reads `missing_public_key`, and such a Node has no open interval; the reachable case is a **retired** Node, because discovery only examines `WHERE n.lifecycle = 'active'` (crates/platpulse-server/src/validator.rs:2473). For that case the pre-fix and post-fix renderings coincide, so this is a contract hardening with a reachable case proven by test 3 (below), not a production defect the change repairs.
- **F4 - a failed ranking refresh can read as an apparently current rank (MUST FIX, disclosed).** Ranking collection is independent of detail collection and `apply_ranking_result` (crates/platpulse-server/src/validator.rs:2928-2951) deliberately retains the last confirmed rank on failure - the existing scenario at :3477-3484 demonstrates fresh detail evidence beside `rankState = error`/`rankFreshness = stale`. But `AdminValidatorInsight` carries only `rank: Option<i64>` (crates/platpulse-server/src/http/validators_admin.rs:47) with no outcome, freshness, timestamp or diagnostic; the mapper takes freshness from the detail call (:412-415) and copies the retained rank (:443), so the page can print a current-looking Provider freshness beside an old rank. The correction is a DTO change (rank outcome + freshness + observed-at + diagnostic) with the OpenAPI and generated-client ripple, which is outside the stories this ticket implements, so it is disclosed here and in the closing comment rather than half-landed.
- **F5 - the Server serialized a never-observed counter state as `normal` (FIXED at the presentation layer, Server-side follow-up).** The coverage of this defect: the synthetic no-insight branch sets `counter_state: "normal"` (crates/platpulse-server/src/http/validators_admin.rs:469-484), the migration default supplies `normal` (crates/platpulse-server/migrations/0060_validator_activity_candidate.sql:22), and the first error insert lets that default stand (crates/platpulse-server/src/validator.rs:2800). `validatorCounterStateLabel` (platpulse-web/src/validators.ts:273) now prints the Server's value only for a read that succeeded (`success`/`empty`), prints `<state> (retained)` when the latest refresh failed but an earlier good answer exists, and otherwise prints `Not observed`, so the Admin page can no longer fabricate a normal counter state. The Server still serializes the default, so a consumer that reads the DTO directly still needs the presentation rule: the follow-up is an explicit `NotObserved`/null counter state in the DTO.
