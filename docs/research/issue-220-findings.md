# Issue #220 findings — one UTC investigation window over a Node's own evidence

**#220** is the investigation ticket of the #202 roadmap — the tree records it as "One UTC investigation window over a Node's own evidence at the HTTP boundary" (crates/platpulse-server/tests/node_investigation.rs:1-2, stories 54 to 59, design §11.4 to §11.7) — and the design it reads against is §11.4 "数据边界" (docs/design/platpulse.md:589), §11.5 "低空间保护（issue #212）" (:610), §11.6 "可信的指标历史：24 小时原始样本、30 天聚合层与共享 Host 系列" (:621) and §11.7 "同步与共识的证据" (:669). What the module fixes is a **coordinate** rather than a new store: one UTC window, plus, per evidence family, how much of that window that family can actually answer. crates/platpulse-server/src/investigation.rs owns no evidence — the metric, state, Peer, Incident and Validator reads stay where they already were — and the module reads them into one answer. Two rules govern every judgement below: **Unknown is never zero**, and **the window is answered as asked** (never widened, narrowed or clamped to what retention happens to hold).

Everything below is the working tree as it stands, read at the line references given. It is not a plan. This pass read code and wrote documents only: no cargo command, no npm command and no browser run happened here, and the ticket text itself was not read — which is why nothing below quotes the ticket's own wording (see VERIFICATION).

> **Superseded in part by issue #221.** `docs/research/issue-221-findings.md` records the seventh family (the Server's own record of the Node's relations), which now leads `SOURCE_ORDER`, and the additions to `TimeBasis`, `BoundaryKind` and the grain list. Both changes shifted the line references into `crates/platpulse-server/src/investigation.rs` that this document cites, so every `investigation.rs:<line>` below reads as of #220's merge (commit `76e91a2`) rather than as of the tree it is read in today; the behaviour it describes is otherwise unchanged.

## SERVER — one window, and how a request becomes one

1. **The window is a first-class value.** `pub fn resolve_window(window: Option<&str>, from: Option<&str>, to: Option<&str>, now: OffsetDateTime) -> Result<ResolvedWindow, String>` (crates/platpulse-server/src/investigation.rs:232) trims every value and turns an empty string into `None`, so `(None, None, None)` resolves to `DEFAULT_WINDOW_PRESET` = `"24h"` (crates/platpulse-server/src/investigation.rs:90 and :246-249) — a bare deep link, an empty query and a refresh are all the same window rather than an error. The preset path sets `from = now - hours` and `to = now` with `clamped_to_now` false; the explicit path needs both ends and parses them through `canonical_instant`.
2. **The presets travel with the answer.** `WINDOW_PRESETS` (crates/platpulse-server/src/investigation.rs:51-88) is 1h/"Last hour", 6h/"Last 6 hours", 24h/"Last 24 hours", 7d/168/"Last 7 days", 30d/720/"Last 30 days", and `ResolvedWindow::to_response` (:170) publishes `preset`, `presetLabel`, `custom`, `requestedFrom`, `requestedTo`, `from`, `to`, `durationSeconds`, `answeredAt`, `clampedToNow`, `horizonDays` = `MAX_WINDOW_HOURS / 24` and `rawRetentionDays`, plus `supported_presets`. A client therefore never hardcodes the preset list, the horizon or the retention window; `CUSTOM_WINDOW_PRESET` = `"custom"` (:99) names the explicit path.
3. **The bounds are named constants, and each refusal carries its own reason.** `MIN_WINDOW_HOURS` = 1 (:93) and `MAX_WINDOW_HOURS` = 720 (:96) bound the width; the strings a caller sees are the module's own: `"choose either a preset window or an explicit from/to range, not both"`, `"<key> is not a supported window; supported windows are …"`, `"an explicit window needs both from and to: one end alone does not describe a range"`, `"<field>=<value> is not a canonical RFC 3339 instant; pass a UTC instant such as 2030-01-01T00:00:00Z"`, `"the window ends at or before it starts: from must be an earlier instant than to"`, `"the window is <width> seconds wide; the supported minimum is 1 hour"`, `"… the supported maximum is 720 hours"` and `"the window lies in the future, so the Server cannot have observed any of it"`. `INVALID_WINDOW_CODE` = `"invalid_investigation_window"` (:102) is the one code all of them answer with (crates/platpulse-server/src/http/admin.rs:2932, :2883 for the query struct).
4. **The future is clipped once, visibly, and never silently.** A `to` beyond `now` becomes `to = min(requested_to, now)` with `clamped_to_now = true`, and the whole-answer `notes` say `"the requested window ended in the future and was clipped to <t>"` (crates/platpulse-server/src/investigation.rs:2971-2986). Two further standing notes ride on every answer: `"<n> optional series were refused while the Server protected a nearly full disk; those stretches are reported as pauses rather than as collection failures"` and `"each source answers as of its own time basis and reports its own boundaries; a source that holds nothing says so instead of reporting zero"`.

## SERVER — six sources, one fixed order, one vocabulary

5. **Every answer carries all six sources whether or not each holds evidence.** `SOURCE_ORDER` (crates/platpulse-server/src/investigation.rs:486) is exactly `node_metrics`, `node_state`, `host_metrics`, `peers`, `incidents`, `validator`, the sources are pushed in that order with `debug_assert_eq!(sources.len(), SOURCE_ORDER.len())` (:2969), and a source that holds nothing says so instead of being omitted.
6. **The vocabulary is closed and each word has a label.** `Coverage` (:331) is `complete`/`Complete`, `partial`/`Partial`, `empty`/`"Empty window"`, `unavailable`/`Unavailable`, `unsupported`/`"Not applicable"`; `TimeBasis` (:375) is `metric_observation`/"Metric observation time", `state_observation`/"State observation time", `peer_receipt_bucket`/"Peer receipt bucket", `incident_evaluation`/"Incident occurrence time", `validator_snapshot_source`/"Validator source time". `BoundaryKind` (:414) is `pre_enablement`/"Before this evidence started", `retention_cleanup`/"Released by retention cleanup", `low_space_pause`/"Optional history paused for low space", `collection_failure`/"Collection gap", `never_observed`/"Never observed", `stale_tail`/"Newest evidence is older than the window end".
7. **A grain is available only when it both serves the window and stored something.** Grain keys are `raw`, `1m`, `5m`, `state_entry`, `receipt_bucket_5m`, `receipt_bucket_1h`, `occurrence`, `validator_day` (crates/platpulse-server/src/investigation.rs:456-470). `GrainEvidence::to_response` (:782) sets `available: self.span.is_some() && self.point_count > 0` (:786) — a tier that serves the window and holds no point is not available, and it says why ("this grain serves this window and holds no point inside it", :1591) — and `missing_points = expected_points.map(|e| (e - point_count).max(0))` (:777), so `expectedPoints`/`missingPoints` are `null` wherever the Server does not count a grid rather than `0`. A tier that does not serve the window at all reads "this tier does not serve this window: <account>".
8. **The ledger is a per-source coordinate, and the newest release floor wins.** `struct Ledger { first_observed_at, last_observed_at, last_received_at, released_before }` (:815) with `Ledger::reduce` (:828) folding per-series rows by taking the min of `first_observed_at` and the max of the other three; the newest `released_before` is the honest floor for the whole source. `retained_from(now, released_before, retention_days)` (:1267) returns the later of the recorded floor and `now - retention_days`, and `retention_detail` (:1281) words which of the two produced a boundary so a declared policy is never reported as a cleanup that happened. `source_state(rows, keys)` (:891) makes an error in any of that source's own collectors the source's state — a source is never healthy merely because another collector succeeded.
9. **A low-space pause is its own kind of evidence.** `struct Pause` (:922, `covers` `Pause::boundary` :951) turns a refused stretch into `BoundaryKind::LowSpacePause` with its own sentence ("<n> optional <series> sample(s) were not stored while the Server protected a nearly full disk, from <a> to <b> …"), and `SourceBuilder::finish` drops any `CollectionFailure` boundary lying inside a refused stretch (:1926-1937, "An interruption inside a refused stretch is the pause, not a failure") so one outage is never reported twice under two names.
10. **An unsupported source is an answer, not an omission.** `SourceBuilder::finish` pushes the reason into `notes` (:1966-1968) and the source ends with empty grains and empty `answer_paths`; `judge_coverage` returns `Coverage::Unsupported` immediately (:1004-1009) and attaches no boundary, because "this source cannot speak" is not a finding about the window. `validator_source` is the one source that does this today (:2685-2691, "no Validator is linked to this Node for any part of this window, so the Server holds no Validator snapshots for it").

## SERVER — the coverage judgement, in order, and why each test is written that way

11. **`judge_coverage` (crates/platpulse-server/src/investigation.rs:1002) runs a strict order** and returns at the first one that fires:
    - `unsupported` → `Coverage::Unsupported` (:1004).
    - no `ledger.first_observed_at` → `NeverObserved` over the window, `Unavailable` ("the Server has never stored an observation for this source on this subject", :1010-1022).
    - `first_observed_at > window.to` → `PreEnablement` over the whole window, `Unavailable` ("the first observation of this source is <t>, which is after the window ends", :1027-1041). The comparison is strict on purpose: the comment at :1023-1026 reads "A window that ends in the same second as the source's first observation still overlaps the source's history … Reading the tie as 'after the window ends' would let a millisecond decide the verdict."
    - `retained_from >= window.to` → `RetentionCleanup` over the whole window, `Unavailable` ("cleanup has released this source's evidence before <t>, so none of the window is still stored", :1042-1058). The `>=` is the mirror of the strict `>` above: a retention floor exactly at the window end released everything the window could hold.
    - `first_observed_at > window.from` → a `PreEnablement` boundary over `[window.from, first_observed_at]` ("the earliest observation of this source is <t>, so the window opens before the Agent reported any of it", :1060-1070) — partial, because the rest of the window is answerable.
    - `retained_from > window.from` → a `RetentionCleanup` boundary over `[window.from, retained_from]` ("evidence older than <t> was released by cleanup", :1071-1080).
    - every grain hole becomes a `CollectionFailure` boundary (:1137, "the <grain> grain holds no observation[ on <series>] for <n>s, from <a> to <b>").
    - unless `facts.event_source`, a tail silence longer than `grace_seconds` becomes `StaleTail` ("the newest observation of this source is <t>, <n>s before the window ends").
    - Boundaries are sorted by `at` then `kind` and deduplicated by `(kind, at)`; `coverage` is `Partial` when any boundary exists **or** `truncated` **or** any `grain.missing_points() > 0`, `Empty` when the source stored `0` points, and `Complete` only when nothing above fired.
12. **The grace constants are derived, not chosen.** `METRIC_GRACE_SECONDS = 3 * crate::metric_history::MIN_GAP_SECONDS` (:1201) = 360, and it deliberately reuses `MIN_GAP_SECONDS` = 120 (crates/platpulse-server/src/metric_history.rs:360) so one silence cannot be a gap on metric history and continuity on the investigation. `STATE_GRACE_SECONDS = 2 * crate::state_history::STATE_ANCHOR_SECONDS` (:1206) = 7200, because state rows are written when a component changes and as hourly anchors, so two anchor intervals is the widest stretch an unchanged component can legitimately leave (`STATE_ANCHOR_SECONDS` = 3600, crates/platpulse-server/src/state_history.rs:91). `PEER_GRACE_SECONDS = 3 * 3600` (:1209) = 3 hours, three hourly buckets. `VALIDATOR_GRACE_SECONDS = 36 * 3600` (:1213) = 36 hours, one local day plus lateness. Incidents pass **0** (:2527) and set `event_source = true`, so no stale-tail boundary is ever minted for an occurrence source.
13. **The metric tiers, and the grace that keeps a Node from looking dead.** `metric_source` (:1645) measures three tiers declared at :1695-1717: `raw` (oldest `= window.from.max(raw_window_cutoff)`, newest `= window.to`; `RAW_WINDOW_HOURS` = 24, crates/platpulse-server/src/metric_history.rs:387), `1m` (oldest `= max(window.from, now - 7d)`, newest `= min(window.to, raw_cutoff)`; `ONE_MINUTE_MAX_AGE_DAYS` = 7, crates/platpulse-server/src/metric_history.rs:401) and `5m` (oldest `= max(window.from, now - 30d)`, newest `= min(window.to, now - 7d)`; `FIVE_MINUTE_MAX_AGE_DAYS` = 30, crates/platpulse-server/src/metric_history.rs:410). Expected points are counted per series from that series' own first observation (`grid_expected_points`, :1621) — "a Node that was enabled yesterday" must not be drawn as a hole the size of the window — and only the widest hole per grain is fetched (`fetch_worst_gap`, :1790) with the grain saying so.

## SERVER — Peers: receipt-aligned buckets, and a grid that proves its own holes

14. **A bucket means "the Server accepted a Report carrying Peer evidence then", and nothing else.** `peers_source` (:2280) reads `peer_aggregate_5m`/`peer_aggregate_1h` and states both facts in the source's own notes: "a bucket is aligned to the instant the Server accepted the Report (the receipt), not to the instant the Agent counted the peers: it says when the evidence arrived" and "the Server stores a bucket only when a Report carries Peer evidence, so a stretch with no bucket means none arrived rather than the peer set being unchanged". The 5m ledger is built from that table's own bounds — `first_observed_at = MIN(bucket_start)`, `last_observed_at = last_received_at = MAX(bucket_start) + 300s` ("a bucket stands for the receipt instants of the five minutes it opens") — with retention family `FAMILY_PEER_AGGREGATE_1H` and `released_before = None`.
15. **The two tiers are fixed windows with fixed limits.** 5m covers the newest `HISTORY_FIVE_MINUTE_LIMIT` = 288 buckets (24 hours) and 1h covers `HISTORY_HOURLY_LIMIT` = 168 buckets (7 days) up to the 5m horizon (crates/platpulse-server/src/peer_history.rs:19-20); a tier whose count exceeds its limit sets `truncated` and says "the <grain> tier keeps <limit> buckets, fewer than this window holds, so it answers with the newest of them". Because a bucket is only written when `peers.status == Ok`, **there is no `expected_points` for either tier** — the DTO carries neither `expectedPoints` nor `missingPoints` — and a missing run is proved by the aligned grid instead: `peer_gap_sql` (:2264) computes `(epoch_of(bucket_start) - epoch_of(previous)) / grain_seconds - 1` as the number missing and the hole runs from `previous + grain_seconds` to `bucket_start`. The measured silence is reported one bucket wider than the count missing (`longest_gap_seconds: hole.seconds + tier.grain_seconds`, :2429) so the seam between "one bucket late" and "one bucket absent" is never rounded away.
16. **The bounded range read (crates/platpulse-server/src/peer_history.rs) answers a range without pretending it is a tail.** `load_range` (:727) counts `matching`/`first_bucket`/`last_bucket` over the half-open range, takes `ever_min`/`ever_max`/`latest` from an unbounded read of the same table, pages `ORDER BY bucket_start DESC LIMIT limit + 1` and cuts back to `limit` with `truncated` and `continuation = <last returned bucket_start>`. Then, in this order (:757-818): `grid_from` = `ever_min > request.from ? ever_min : request.from` (:787); `missing_buckets` = `0` when there is no `ever_min`, else `max(expected_buckets(grid_from, to, grain_seconds) - matching, 0)` (:791); `held_whole_range` only when `request.from >= ever_min` **and** `expected_buckets(ever_max, to, grain_seconds) <= 1` (:804) — the left edge and the right edge are checked separately so a range that starts before the record and a range that runs past its newest bucket are both `partial`; and `coverage` (:818): `unavailable` when there is no `ever_min`, `empty` when `request.to <= ever_min`, then `partial` when `missing_buckets > 0` or the range is not held whole, then `empty` when `matching == 0`, else `complete`. The last two steps are the point of the whole design: **a gap inside the record is receipts that never arrived**, so a page that holds no row inside a documented record is `partial`+missing, and it is never re-labelled an empty window.
17. **The range endpoint's refusals are separate codes.** `peer_range_request` (crates/platpulse-server/src/http/admin.rs:2706) answers `invalid_query` for a range without a grain ("a Peer range needs a grain: pass grain=5m or grain=1h"), `invalid_grain` for an unknown grain ("grain is not a Peer receipt grain (5m or 1h)"), and `invalid_history_range` ("history range is invalid") for a range that is not canonical, is reversed, is wider than `MAX_PEER_RANGE_SECONDS`, or names only one end ("a Peer range needs both from and to"). `before` must satisfy `from < before <= to`, and `limit` defaults to the grain's tail limit and clamps to `1..=MAX_PEER_RANGE_LIMIT`. A ranged read leaves the fixed tails empty so one response never means both a range and a tail.

## SERVER — Node state, Incidents and the Validator source

18. **Node state is entry-grained, never value-grained.** `state_source` (:2114) reads `node_state_series_state` per component of `crate::state_history::STATE_COMPONENTS` under the `Sync`/`Consensus` collectors, retention family `FAMILY_OBSERVATION_STATE`, and produces **one** grain: `state_entry` with no `grain_seconds`, `sample_count = point_count`, `expected_points = None` and the `STATE_GRACE_SECONDS` threshold. Its hole wording is state-specific ("the state grain holds no entry across two hourly anchors, so this component's state is unknown for that stretch", :2109) and its note is the one that keeps a quiet component from reading as a dead one: "entries are stored when the component changes and as hourly anchors, so the count is entries rather than changes, and a quiet stretch means an unchanged component" (:2176). Its answer path is per component: `/api/admin/v1/nodes/{node}/state-history?component=sync&from=<a>&to=<b>` (:2194-2201), "one read per component; the entries carry the collection state and value source of each write".
19. **Incidents are an occurrence source with the same window predicate the list route uses.** `INCIDENT_WINDOW_PREDICATE` = `"i.opened_at < ? AND (i.resolved_at IS NULL OR i.resolved_at > ?)"` (:2466, bound end-then-start) so an Incident that opened before the window and had not closed when it started is inside it, and `INCIDENT_SUBJECT_PREDICATE` (:2470) matches `subject_kind='node'` with the Node id **or** `subject_kind='agent'` with the Agent id. The ledger's `first_observed_at` is the Node's `first_seen_at` (:2889, `canonical_instant(...).unwrap_or(window.from)`), so a window with no Incident is `Empty` rather than `Unobserved` and a window ending before the Node existed is not answered as "an empty list". The source is built with grace `0` and `event_source = true` (:2527) and one `occurrence` grain whose hole threshold is `i64::MAX`: an occurrence source has no cadence, so a quiet stretch between two Incidents is never a missing observation. Its note is "Incidents are evaluated by the Server from its own history, so no Agent collector reports on them and none is named here", and it emits two answer paths, for the Node subject and for the Agent subject (:2551-2566).
20. **The Incident list route grew a paired range, a ceiling and a two-part cursor.** `MAX_INCIDENT_RANGE_SECS` = `30 * 24 * 60 * 60` (crates/platpulse-server/src/http/alerts_admin.rs:1956, "matching the widest investigation window (issue #220)"); a range must be given as a pair ("an incident range needs both from and to: one end alone does not describe it"), must not end at or before it starts, and must not exceed 30 days ("the incident range is wider than the supported 30 days"); malformed instants answer `alert_validation` with `"incident range <field>=<value> is not a canonical RFC 3339 UTC instant with second precision"` (:1961). The cursor is `<opened_at>|<incident_id>` parsed by `split_once('|')` into the predicate `(i.opened_at < ? OR (i.opened_at = ? AND i.incident_id > ?))` (:2015 and after) — **a single instant is not a coordinate**: two Incidents sharing an `opened_at` would make a page that pages on the instant alone repeat or skip rows, which is exactly what the message says ("an incident continuation must be the <opened_at>|<incident_id> coordinate a truncated answer returned"). `total` is counted from the conditions **without** the cursor while the page count and the rows use them **with** it, so the second page does not shrink the total; `truncated = page_total > returned`; `continuation` is emitted only when truncated; `coverage` (:2235) is `empty` when `total == 0`, `partial` when truncated, else `complete` — documented in the DTO as "An occurrence is never averaged into a value, so a window with no Incident is empty and not zero (design 11.4; issue #220)".
21. **The Validator source is day-grained on the configured calendar, and it is the one that can be unsupported.** `validator_source` (:2663) reads `VALIDATOR_LINK_SQL` (:2599, links overlapping the window), `VALIDATOR_HORIZON_SQL` (:2606) and `VALIDATOR_GRID_SQL` (:2615), all filtered to the configured zone; with no link at all it sets `builder.unsupported` and returns before adding any grain or answer path (:2685-2691). Otherwise the grid is built from `crate::validator::local_date_at` — "the day grid is the <tz> calendar the Server is configured with, from <a> to <b>; the Validator trend engine is the day-level authority and also discloses rows recorded in other timezones" — as one `validator_day` grain with `grain_seconds = 86400`, `cadence_seconds = 86400`, `expected_points` = the inclusive count of local days, and no hole. Its ledger's `first_observed_at` is the **earliest link's `valid_from`** ("before that instant the Node had no Validator to read, so the window is not judged as a silence"), each link contributes a note from `link_description` (:2643, "<validator> (<role|unassigned>, <origin>) linked from <t>[ to <until>]") and each link contributes one answer path `/api/admin/v1/validators/{validator_id}/trend?from=<a>&to=<b>`.

## SERVER — the SQLx details that shaped the module

22. **A silence is measured between real observations, not between bucket edges.** `struct TierInstants { at, previous, received, range, grain_predicate }` (:1472) has two constructors' worth of behaviour in `TierInstants::of` (:1486): an aggregate tier uses `at = first_observed_at`, `previous = LAG(last_observed_at) OVER (PARTITION BY <columns> ORDER BY bucket_start)`, `received = last_received_at`, `range = bucket_start` and adds `AND grain_seconds = ?`; the raw tier uses `at = observed_at`, `previous = LAG(observed_at) OVER (PARTITION BY <columns> ORDER BY observed_at)`, `received = received_at`, `range = observed_at` and no grain predicate. `spacing()` (:1510) is `epoch_of(at) - epoch_of(previous)`, so a bucket tier reports the interruption the Agent actually had rather than the bucket boundary the Server happened to align to (the same distinction migrations/0067_node_metric_aggregates.sql:29-42 draws for metric history).
23. **Two schema facts are load-bearing.** `fn series_key_columns(schema: &HistorySchema) -> &'static str` (:1334) returns `"metric, dimension"` when the schema has a dimension column and `"metric"` otherwise, because the Node's own ledger (`node_metric_series_state`) has **no dimension column** while the Host's does — an `ORDER BY` that assumed `dimension` would simply fail on the Node ledger. And every instant is bucketed with `fn epoch_of(column: &str) -> String` (:1329), `CAST(ROUND((julianday(<column>) - 2440587.5) * 86400) AS INTEGER)`, so aligned-bucket arithmetic is done by SQLite on the same second-precision UTC coordinate the Rust side uses; `aligned_count(from, to, grain_seconds)` (:1312) counts inclusive epoch-aligned buckets for the expected-point grid. Bounded reads are bounded on purpose: `LEDGER_ROW_LIMIT` = 2048 (:1190) sets `truncated` and a note ("this source holds more than 2048 series; the counts below cover the first 2048 of them") rather than folding an unbounded ledger, and `PAUSE_ROW_LIMIT` = 512 (:2804) does the same for refused stretches.
24. **One read, one transaction-free pass.** `investigate_node(pool, node_id, window, now, timezone)` (:2857) resolves the Node (`NODE_SQL` :2776), reads `component_status` for the node and host scopes (`COMPONENT_SQL` :2785) and the capacity pauses (`PAUSE_SQL` :2792) once, then hands the same `SourceContext` to the six source functions — so the six panels describe the same instant, the same pause set and the same component states instead of six independent reads that could disagree.

## The error codes this ticket adds or reuses

25. `invalid_investigation_window` (`INVALID_WINDOW_CODE`, crates/platpulse-server/src/investigation.rs:102) — every window refusal on `GET /api/admin/v1/nodes/{node_id}/investigation`, including an unreadable query ("the investigation window could not be read; name a preset, or pass from and to together"); it is answered 400 with the module's own reason string.
26. `invalid_history_range`, `invalid_grain`, `invalid_query` — the Peer range route's three refusals, 400.
27. `alert_validation` — the Incident route's range and filter refusals (a bad range, an unknown state/severity/rule/subject kind, a blank subject key), 400.
28. `not_found` (404) — a Node the Server has never seen; **a purged Node is deliberately not a plain 404**: a missing `nodes` row is re-read through `DELETED_NODE_SQL` (:2781, `SELECT deleted_at FROM deleted_nodes WHERE node_id = ? ORDER BY deleted_at DESC LIMIT 1`) and answers `InvestigationError::Purged { deleted_at }` (:1160), which the handler renders 404 as `node_purged` with "this Node was purged at <t>; its evidence was deleted by design and cannot be reconstructed" — "we destroyed it" is not "we never had it".
29. `unavailable` (503) — a database failure on any of the three routes. The handler's envelope is a read-only message with a request id (crates/platpulse-server/src/http/admin.rs:2895 `dynamic_error`); the reason strings above are the module's own wording and carry no SQL, path or storage detail.
