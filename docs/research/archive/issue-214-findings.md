# Issue #214 findings — multi-precision Node metric history for days 2 to 30

**#214** (Stage 2 ticket 12/23, parent #202, user stories 46, 47, 48, 58 and 59, common constraints 1–8 and 80–81) asked for the aggregate tiers that extend the Owner's Node metric history past the 24 hour raw window: bounded 1-minute buckets from the raw cutoff up to day 7, 5-minute buckets from day 7 up to day 30, and a range read that keeps extremes, counts, coverage, grain and source honest while it pages under one budget. It was blocked by #213, which shipped in commit `12b3ce6` (`feat(server,web): 可信的 24 小时 Node 原始指标历史 (#213)`).

The ticket states the boundary contract in UTC exactly: `最近24h raw，>24h至7d为1m，>7d至30d为5m；极值/count/真实coverage/gap/粒度来源保留，旧桶放大不恢复raw，不空桶补零或常量外延`, and requires an incremental, bounded aggregate/index/query/cleanup path with the 30 day floor registered and wired to the existing guard and Retention, with a replay never accumulating twice. Everything below is the working tree as it stands; the implementation is frozen while this document is written.

## SERVER (the real gaps)

1. **The read path had exactly one tier, and its own contract said so.** The #213 surface answered with `grain = "raw"` and `aggregate_supported = false`; docs/design/platpulse.md:632 still carries that sentence (the section's own text: `grain = "raw"` … `aggregate_supported = false` … 1m/5m 聚合层与 30 天下限属于 issue #214), which is what the previous ticket shipped. There was therefore no tier at all beyond the raw window, so nothing answered day 2 through day 30: a request that reached past the raw cutoff could only be answered with the raw points that were still retained, and the older stretch had no evidence behind it. The shape that replaced it is admin.rs:4814-4815.
2. **No table kept a counted observation after its raw row was released.** The series ledger counted observations (observation_count, replayed_count, coverage) and recorded `released_before` (retention.rs:254-262), but a count is not a value: once the cleanup released the row, a stretch the Server had counted and a stretch it had never observed were indistinguishable — both were simply absent rows. The bucket table exists precisely to end that: migration 0067_node_metric_aggregates.sql:23-27 — "A bucket row exists only when at least one observation arrived in it. An empty bucket is simply absent: it is never a zero, never a carried-forward value, and never a straight line across a stretch the Server did not observe."
3. **The retention catalog had no family for any aggregate tier.** `POLICY_CATALOG` held 14 families and the `retention_policies` family CHECK did not contain `five_minute_aggregate`, so with the old constraint in place the family's default seeding was skipped silently (`INSERT OR IGNORE`, retention.rs:847) and a family with no policy row is invisible to the Owner and skipped by its own cleanup path: the 5-minute tier would have grown without bound, which is exactly what registering the 30 day floor is meant to prevent (migration 0067_node_metric_aggregates.sql:91-107). The 30 day investigation horizon had neither a declared floor nor a cleanup target, and the one aggregate family the catalog did carry, `one_minute_aggregate`, was declared as a never-produced placeholder (`supported = 0`, default 90 days, bounds 7..365) whose row the seeding wrote on every database — so an upgraded database would have gone on keeping 1-minute buckets for 90 days, and the Owner's retention surface would have called a family the Server now really produces `not produced in the current phase`.
4. **A bucket's accumulation could not be derived from retained raw rows.** A released observation has no row left to re-derive from, and the tempting alternative — deriving buckets at read time — is wrong for a second reason: "Deriving the tiers at read time instead would state a count the Server never counted, and would count one stretch twice the moment it is read at two grains (issue #214, design §11.6)" (http/report_ingestion.rs:884-891). The tiers therefore have to be written when the observation is accepted, and only then.

The constants this ticket is built on: metric_history.rs:147 `ONE_MINUTE_MAX_AGE_DAYS: i64 = 7`, :156 `FIVE_MINUTE_MAX_AGE_DAYS: i64 = 30`, :160 `AGGREGATE_GRAINS: [i64; 2] = [ONE_MINUTE_SECONDS, FIVE_MINUTE_SECONDS]` (60 and 300 at :140 and :144), :95 `DEFAULT_SAMPLE_LIMIT: i64 = 5_000`, :99 `MAX_SAMPLE_LIMIT: i64 = 20_000`, :121 `MAX_OBSERVED_CADENCE_SECONDS: i64 = 300`; retention.rs:224 `AGGREGATE_CLEANUP_BATCH: i64 = 2048`; the bucket's identity is the primary key `(node_id, metric, grain_seconds, bucket_start)` (0067_node_metric_aggregates.sql:58). #213's `NODE_METRIC_SAMPLES_PER_SERIES` history is untouched by this ticket.

### Accumulation at ingestion

- **crates/platpulse-server/src/http/report_ingestion.rs:892-916** adds the only write of the tiers, inside the receipt transaction and before `record_delivery` (which runs at :919):

  ```rust
  match delivery {
      Delivery::Observed => record_aggregates(tx, node_id, metric, &observed_at, received_at, value),
      Delivery::Correction => recompute_aggregates(tx, node_id, metric, &observed_at, received_at, value),
      Delivery::Replay => {}
  }
  ```

- `Delivery::Observed` is the classification the series ledger already accepted as a new instant (classify_delivery at :887), so a bucket can never count something the ledger did not count; `Delivery::Replay` contributes nothing at all, and a repeated delivery of an instant already counted never reaches this match.
- The low-space protection branch returns earlier: `if let crate::capacity::HistoryGate::Paused { interval_id } = history` at :849 records the skip through `capacity::record_skipped_series` at :856 and returns, so **a protection pause accumulates nothing** — the stretch it covers has no bucket, exactly as it has no raw row.
- A correction does not accumulate: it restates (see the tier engine below).
- `save_host_metric` is untouched. Host series have no tier and their history remains raw-only, which is what the issue's scope says.
- retention::cleanup_expired_metric_aggregates runs after each accepted Report (report_ingestion.rs:3120), so a Server that only ever writes still expires its own tiers.

### The tier engine

**crates/platpulse-server/src/metric_history.rs** carries the whole engine.

- **Alignment.** `pub fn aligned_bucket_start(instant: &str, grain_seconds: i64) -> Option<String>` (:200) refuses a non-positive grain, requires `canonical_instant(instant)?` (:937), and returns `Some(format_rfc3339(OffsetDateTime::from_unix_timestamp(aligned).ok()?))` for `aligned = parsed.unix_timestamp().div_euclid(grain_seconds) * grain_seconds` (:210). Buckets are aligned on the Unix epoch in UTC (`div_euclid`, so an instant before the epoch still floors towards the past), and the function answers `None` rather than a guess unless the instant is canonical.
- **The upsert.** `AGGREGATE_UPSERT_SQL` (:1059) is one statement both the ingestion path and the tests beside it run: `INSERT INTO node_metric_aggregates (…) VALUES (?, ?, ?, ?, 1, ?, ?, ?, ?, ?, ?, ?) ON CONFLICT (node_id, metric, grain_seconds, bucket_start) DO UPDATE SET sample_count = node_metric_aggregates.sample_count + 1, min_value = MIN(node_metric_aggregates.min_value, excluded.min_value), max_value = MAX(node_metric_aggregates.max_value, excluded.max_value), last_value = CASE WHEN excluded.last_observed_at >= node_metric_aggregates.last_observed_at THEN excluded.last_value ELSE node_metric_aggregates.last_value END, first_observed_at = MIN(…), last_observed_at = MAX(…), last_received_at = CASE WHEN excluded.last_observed_at >= … THEN excluded.last_received_at ELSE node_metric_aggregates.last_received_at END, updated_at = excluded.updated_at`. The two CASE guards are the point: `the newest reading follows the newest *observation* rather than the newest delivery` (:1055-1058), so a bucket held back by a spool cannot pass an older reading off as the newest one, and `updated_at` still moves on every accepted observation (`so a bucket that changed only in count is still visibly current`).
- `pub async fn record_aggregates(tx, node_id, metric, observed_at, received_at, value)` (:1114-1142) loops `AGGREGATE_GRAINS` and writes **both tiers for every counted observation**, whatever the raw policy currently says (:1069-1076, the loop at :1122: the tiers `answer a stretch the raw window may cover today and release tomorrow, and skipping the write under a wide policy would leave a hole if the policy were later narrowed`). An instant the alignment refuses contributes no bucket: `a guard rather than a policy`, because stored observations are canonical by construction.
- **The correction rule.** `pub async fn recompute_aggregates` (:1211) repairs a bucket only when it can prove the replacement (:1186-1200). Per tier it reads `BUCKET_STATE_SQL` (:1166): a bucket with no stored row is skipped (`continue`, a pre-#214 stretch has no envelope to repair), and so is a bucket whose window retains no rows at all. When the retained raw rows account for every observation the bucket counted, `BUCKET_REPLACE_SQL` (:1170) recomputes the whole envelope from them. Otherwise the bucket keeps the extremes it proved while it held them and only `BUCKET_CARRY_SQL` (:1190) runs — `UPDATE … SET last_value = ?, last_received_at = ?, updated_at = ? … AND last_observed_at <= ?` — **a stale extreme is preferred over an understated one**, `because understating a stretch the Server no longer has the evidence to restate would be worse`. The count never changes: `a correction is not a new observation, and the ledger already counted the instant`.
- **The types.** `MetricAggregate` (:216), `MetricRangePoint` (:305) with `instant, grain, source, value, min_value, max_value, sample_count, last_observed_at, received_at, judged_at, cadence_seconds`, `MetricRangeSegment` (:337) with `from, to, grain, source, point_count, truncated`, `MetricRange` (:354) with `points, segments, ledger, gaps, coverage_seconds, truncated, continuation`, and `RangeQuery<'a>` (:378) with `before: Option<OffsetDateTime>, limit, raw_cutoff, now`. #213's single-window type `MetricWindow` is gone: a range read is now a set of segments, and the type system says so.

### Read path: regions, budget, paging

- `load_range` (:1080) builds **three non-overlapping, deterministic UTC regions**: the raw window `[later(from_text, raw_cutoff_text), raw_ceiling]` (:1109-1110), the 1-minute tier `[later(from_text, one_minute_floor), earlier(aggregate_ceiling, raw_cutoff_text))` and the 5-minute tier `[later(from_text, five_minute_floor), earlier(earlier(aggregate_ceiling, one_minute_floor), raw_cutoff_text))` (:1156-1170), with `one_minute_floor = now - 7d` (:1089) and `five_minute_floor = now - 30d` (:1091). Every bound is exclusive-or-inclusive the same way on every call, so two reads of the same range cannot overlap or leave a seam.
- **One shared budget, spent newest tier first.** `remaining` is a single limit for the whole answer; the raw region is read while `remaining > 0` (:1110), each aggregate region is skipped once the budget is spent (:1522). When it is spent **and** an older region still holds evidence, the read stops and says so: `BUCKET_EVIDENCE_EXISTS_SQL` (:1666, used at :1530) probes `SELECT EXISTS(SELECT 1 FROM node_metric_aggregates WHERE node_id = ? AND metric = ? AND grain_seconds = ? AND bucket_start >= ? AND bucket_start < ?)` and sets the stopped flag. **The exact-fit case probes for older evidence instead of assuming completeness** — a page that ends exactly at the end of the 1-minute tier must still report `truncated` when the 5-minute tier holds a point, otherwise the answer would be silently incomplete (:1522-1546).
- **Paging.** `truncated = any segment truncated || stopped` and `continuation = points.first().instant when truncated` (:1588-1592). The continuation is therefore *the oldest coordinate this answer returned*, and the next request passes it as `before`, which moves both ceilings: `(aggregate_ceiling, raw_ceiling) = (before, before - 1s)` when paging, else `(to, to)` (:1355-1362). The raw SQL is inclusive and the aggregate SQL is half-open, which is why the ceiling moves back by exactly one second for the raw region: no point is repeated and none is skipped between two pages.
- Points are sorted by instant ascending and segments by `from`, so the answer is ordered the way a reader walks it. The raw region produces points with `min_value == max_value == value` and `sample_count 1` (:1447ff) through `RANGE_SAMPLE_SQL` (:1647); a bucket produces `value = last_value`, its own extremes and count, `received_at = last_received_at`, `judged_at = first_observed_at` and `cadence_seconds = grain_seconds` (:1560-1583) through `RANGE_BUCKET_SQL` (:1656), which is ordered by `bucket_start DESC LIMIT ?` and served by the primary key.
- **The reported grain comes from the points, not from the segments.** http/admin.rs:4728-4747 derives it as the finest grain the answer actually carries: `raw` if any point is raw, else `1m` if any point is 1-minute, else `5m` if any is 5-minute, else `none` — so a segment that was consulted and held nothing cannot mislabel an answer that came from a coarser tier.
- Gaps and coverage run through `continuity_from` with `window_end = aggregate_ceiling when paging else to` (:1628-1632), which is what keeps **a silence across a tier boundary a single gap** instead of one gap per tier.

### Retention, cleanup and the 30 day floor

- retention.rs:39 `pub const MIN_INVESTIGATION_AGGREGATE_DAYS: i64 = 30`, :52 `FAMILY_ONE_MINUTE_AGGREGATE = "one_minute_aggregate"`, :57 `FAMILY_FIVE_MINUTE_AGGREGATE = "five_minute_aggregate"`, and :96 makes `PolicyClass::Investigation` floor at those 30 days.
- `POLICY_CATALOG` (:346) went from 14 to 15 entries: `one_minute_aggregate` is `7/7/7` with `PolicyClass::Contract`, `supported: true` and `TARGET_ONE_MINUTE_AGGREGATES` (:370-384, comment :373-377: `Its window is its contract … a shorter one would leave a hole between the raw window and the 5-minute tier`), and `five_minute_aggregate` is `30/30/30` with `PolicyClass::Investigation` and `TARGET_FIVE_MINUTE_AGGREGATES` (:385-397, comment :388-390: `30 days is both the window the reader may ask for and the registered floor of this family`). The coarse tier carries the registered 30 day investigation floor; the fine tier's fixed 7 day window is a contract.
- **Bounded deletes** (:237-252): each family declares exactly one target on `node_metric_aggregates`, with `count_sql` `SELECT COUNT(*) FROM node_metric_aggregates WHERE grain_seconds = 60|300 AND bucket_start < ?` and `delete_sql` `DELETE FROM node_metric_aggregates WHERE rowid IN (SELECT rowid FROM node_metric_aggregates WHERE grain_seconds = 60|300 AND bucket_start < ? ORDER BY bucket_start LIMIT 2048)` — an index range read of `node_metric_aggregates_expiry_idx`, never a scan of the tier (:233-236).
- `AGGREGATE_CLEANUP_BATCH: i64 = 2048` (:224) carries a compile-time assertion (:228-231): `assert!(AGGREGATE_CLEANUP_BATCH >= platpulse_core::protocol::MAX_NODE_OBSERVATIONS as i64 * 5, "the per-Report aggregate batch must cover one maximal Report")`. The reason is stated: a bound below the rows one maximal Report can add to a single grain `would let the backlog grow at steady state` (:220-227).
- `pub async fn cleanup_expired_metric_aggregates(pool, now) -> Result<u64, sqlx::Error>` (:757-778) loops the two families, reads each window with `aggregate_retention_days` (:737-748, policy row first, catalog default as fallback), skips a `retention_days <= 0` window (`A keep-forever window has no cutoff, so it can never expire a row`), converts the cutoff with `family_cutoff` and runs each target's bounded delete. Its doc (:750-756) states the ordering that matters: **the 1-minute buckets leave first while the 5-minute buckets covering the same stretch stay**, `that is what makes an old bucket unrecoverable as raw samples and still answerable at a coarser grain`.
- The cleanup runs at Server startup — cli.rs:952, before `ensure_seeded` at :965 — and after every accepted Report (report_ingestion.rs:3120). A process that restarts into an expired tier and a process that never stops both expire it.
- **The upgrade path for the never-produced placeholder.** Before #214 the catalog declared `one_minute_aggregate` as a family that was never produced (`supported = 0`, default 90 days, bounds 7..365) and `ensure_seeded` wrote exactly that row on every database (`INSERT OR IGNORE`, so it survives every later start). Because the rebuild above only copies rows and the seeding only inserts, an upgraded database would have kept 1-minute buckets for 90 days instead of the delivered 7, and the Owner's retention surface would have called a family the Server now really produces `not produced in the current phase` (retention.rs:1125-1134, the `skip_reason` code `retention_unsupported`). 0067 therefore ends with a guarded UPDATE (migration lines 113-132): `UPDATE retention_policies SET retention_days = 7, min_days = 7, max_days = 7, supported = 1 WHERE family = 'one_minute_aggregate' AND retention_days = 90 AND min_days = 7 AND max_days = 365 AND supported = 0`, applied **only while the row still carries that exact never-produced placeholder**. Any other value is an Owner's own edit of the old window, which a migration must not overwrite (migration lines 121-125): that row keeps the Owner's window and is corrected against the new 7..7 bounds on the next edit, because `validate_policy_days` reads the catalog. `five_minute_aggregate` needed no alignment: it was not a legal family name before 0067, so no row could exist, and first-start seeding inserts the new 30/30/30 contract. The upgrade path is pinned by `aggregate_tier_migration_aligns_the_never_produced_policy_placeholder` (crates/platpulse-server/src/database.rs:862), which runs `migrations_through(SCHEMA_BEFORE_AGGREGATE_TIERS)` with `const SCHEMA_BEFORE_AGGREGATE_TIERS: i64 = 66` (:864) and asserts the untouched placeholder becomes `(7, 7, 7, 1)` while an Owner-set 30 day window survives.
- `pub fn audit_catalog() -> Result<(), String>` (:1967) keeps the catalog honest at build time: no duplicate family and no negative bound (:1970-1979), bounds coherence (:1980-1992), and **a supported bounded family's floor may not sit below its class floor** (:1993-1998) — which is what made it impossible to leave `one_minute_aggregate` supported without also giving it the 7/7/7 contract and a cleanup target. The test beside it asserts the catalog holds 15 families (retention.rs:2724) and that `one_minute_aggregate` no longer accepts a window other than 7 days (:2683-2688).

## The Admin contract

`GET /api/admin/v1/nodes/{node_id}/metric-history` (http/admin.rs:4541) is unchanged in shape — Owner-only, same route group, same error envelope — and gains tier semantics. Nothing changed for Host series: the metric must pass `is_node_metric` (:4569-4580), so Host series are not served on this endpoint at all (Host history is a later ticket).

- **Query** (`AdminMetricHistoryQuery`, :4329-4337): `metric` (optional at the type level so an unknown name answers with the same error body as every other rejected query), `from`, `to`, `before` and `limit`. `before` is documented as `Exclusive upper bound of a paging request: the continuation coordinate a previous truncated answer returned` (:4333-4335).
- **Validation**: a query that does not deserialize is `400 invalid_query` (:4548); a non-canonical or inverted range is `400 invalid_history_range` (:4565, with the checks at :4590-4603); `metric` that `is_node_metric` rejects is `400 invalid_metric` (:4577); `before` is parsed with `canonical_instant` and must satisfy `before > from && before <= to`, otherwise `400 invalid_history_range` (:4608-4619) — `a cursor outside it would answer a stretch nobody asked about` (:4604-4607); an unknown Node is `404 not_found` (:4626-4632); a database failure is `503 unavailable` (:4634).
- **limit**: `params.limit.unwrap_or(DEFAULT_SAMPLE_LIMIT).clamp(1, MAX_SAMPLE_LIMIT)` (:4652-4655), i.e. 1..20000 spanning **every tier** — one budget for the whole answer, not one per tier.
- **Availability is now expressed against the 30 day horizon** (:4641-4649): `horizon_cutoff = now - FIVE_MINUTE_MAX_AGE_DAYS`, then `None` when `from >= horizon_cutoff`, `Some("unavailable")` when `to <= horizon_cutoff`, else `Some("partial")`. The answered range is clamped with `effective_from = from.max(horizon_cutoff)` (:4650) and `requested_from` keeps what the caller actually asked for, so a clamped or paged answer says what it clamped or narrowed (:4474-4476).
- **Per-point fields** (`AdminNodeMetricSample`, :4342-4375): `observed_at` (the observation instant of a raw sample, or the aligned start of a bucket), `received_at` (for a bucket, the receipt of the bucket's newest observation), `value` (a bucket's newest value), and the five new fields `grain` (`raw`/`1m`/`5m`), `source` (`raw`/`aggregate`), `min_value`, `max_value` and `sample_count`, plus `last_observed_at`, `delay_seconds` and the clock evidence. A bucket says so instead of looking like a closed stretch: `A thin bucket says so here…` (:4360-4363).
- **Segments** (`AdminNodeMetricSegment`, :4444-4458): `from`, `to`, `grain`, `source`, `point_count`, `truncated`, with `the older end inclusive, the newer end exclusive, matching what the reader asked of the tier` (:4445-4447). The doc above the type states the purpose: no surface has to `infer the resolution from the points themselves or present a bucket as if it were a sample` (:4439-4441).
- **Response** (`AdminNodeMetricHistoryResponse`, :4466-4505): the new fields are `history_horizon_days` (:4483-4485, built from `FIVE_MINUTE_MAX_AGE_DAYS` at :4813), `segments` (:4492-4493) and `continuation` (:4501-4504, built from `range.continuation` at :4818), alongside `availability`, `raw_retention_days`, `grain` and `item-level evidence`; `aggregate_supported` is now `true` (:4815). `truncated` is documented as `the newest points are returned and the rest is reported, never dropped silently` (:4498-4500). The whole response is wrapped in `no_store` (:4801-4804): `Owner-only Node history is per-session data`.

## DECISIONS

- **Both tiers are written for every counted observation, even under a wide raw policy.** `record_aggregates` loops `AGGREGATE_GRAINS` and writes both tiers unconditionally — because the tiers answer a stretch the raw window covers today and may release tomorrow, and skipping the write while a wide policy is in force would leave a hole the moment that policy is narrowed (metric_history.rs:1122-1129).
- **Accumulation happens at ingestion, not at read time.** The bucket is written inside the receipt transaction for a delivery the classification accepted as new, because deriving it from retained rows would `state a count the Server never counted, and would count one stretch twice the moment it is read at two grains` (report_ingestion.rs:894). A released observation has no row to re-derive from at all.
- **The 1-minute window is a fixed contract (7/7/7), the coarse tier carries the registered 30 day floor.** The fine tier serves the stretch between the raw window and day 7, and its window *is* its contract: a bucket kept beyond what the reader can be served at that grain is storage nobody asks for, and a shorter one would open a hole between the raw window and the 5-minute tier (retention.rs:374-380). The coarse tier is where the investigation horizon lives, and it is registered as the family's safety floor as well as its default (retention.rs:389-396), so `POLICY_CATALOG` cannot describe a horizon the retention layer does not keep.
- **Every instant is answered exactly once: a tier hands over on a bucket edge, and a request that starts inside the raw window consults no tier at all (review F2).** The handover is the end of the bucket that straddles it (`aligned_bucket_end`, metric_history.rs:223): the coarse tier answers that whole bucket and the finer tier starts where it ends, so nothing inside a served stretch is dropped and nothing is claimed twice — which matters because `continuity_from` sums consecutive intervals, so overlapping evidence would inflate `coverage_seconds` (this is why the overlap alternative was rejected). The raw floor is then request-dependent (`load_range` :1350): when the request starts inside the raw window every sample it asks for is still stored, so raw answers it alone and no empty tier is consulted or listed; only a request that reaches below the cutoff hands the straddling minute to the tier that counted it and starts raw at the minute edge - and only when that tier's bucket really accounts for the minute, because `STRADDLING_MINUTE_LEDGER_SQL` returns the bucket's count and the rows the minute still stores in one round trip and `handed_over` requires the count to cover them (review N2, tightened by review round two): a series counted before the tiers existed has stored raw rows and no bucket, and handing its straddling minute to a tier that cannot account for it is how the promised 24 h window lost evidence it still had on disk. Disclosed cost: up to 1 minute just inside 24 h and up to 5 minutes just inside day 7 are answered at the coarser grain (docs/design/platpulse.md §11.6).
- **A correction has three cases, and it never lowers a bucket's count.** `recompute_aggregates` (:1211) skips a bucket with no stored row at all (a stretch from before the upgrade is absent, never inferred); when the retained rows account for every observation the bucket counted it restates the whole envelope from them; otherwise it carries the corrected reading only, and `BUCKET_CARRY_SQL` (:1190) widens `min_value`/`max_value` for any carried value while moving `last_value`, `last_observed_at` and `last_received_at` together, and only when the instant is not older (review F5, tightened by review round two: the value and the instant it was observed at are one pair, because the Admin contract reads that pair back as the point's value and its delay) — a stale extreme is preferred over an understated one, because the Server must not state a range it can no longer prove. The count is never recomputed, because a correction is not a new observation. Check: the carry assertions in `a_correction_restates_a_bucket_only_from_rows_that_account_for_it` (min 0.5 / max 8.0 / last 0.5).
- **One shared budget, spent newest tier first, with paging — not a per-tier limit and not a middle hole.** A per-tier limit would make the answer's size a function of how the range happens to straddle the tier boundaries; one budget makes the cost of a read predictable, and spending it newest-first means the points a reader is most likely to be looking at survive truncation. What is dropped is always the oldest end, and `continuation` names it, so the omission is a seam at the edge rather than a gap in the middle (`the omitted stretch is a seam and never a hole in the middle`, AdminNodes.tsx).
- **The exact-fit case probes for older evidence instead of assuming completeness.** When the budget runs out exactly at the end of a tier, the read asks `BUCKET_EVIDENCE_EXISTS_SQL` whether an older tier still holds a point and reports `truncated` accordingly (metric_history.rs:1553-1573). Without the probe the answer would claim completeness while a coarser tier still held evidence — a silently incomplete answer, which is the failure the acceptance test exposed.
- **The reported grain is derived from the points, not from the segments.** A segment can be consulted and hold nothing (the E2E case asserts exactly that for the raw segment of a 29 day answer); labelling the answer from a segment would then mislabel it with a tier that contributed no point (http/admin.rs:4728-4747).
- **Host series stay raw-only.** Host observation belongs to the Agent and is referenced by Node views; the tier contract is written for Node metric series, and this endpoint's metric filter is `is_node_metric`. Host history is a later ticket (webui/design follow-up), so nothing here changes what a Host series read returns.
- **Tiers introduced after the fact make pre-#214 stretches absent, never inferred.** A bucket row that was never written is missing, and the correction path skips a bucket with no stored row rather than inventing an envelope from retained rows (metric_history.rs, `BUCKET_STATE_SQL` branch). The migration adds no backfill: yesterday's history simply has no day-2-to-day-30 evidence, and the empty state says so.
- **Declared storage scale.** At the declared cadences a single series costs about 18.7k aggregate rows over the 30 day horizon (7 d × 1440 1-minute buckets + 30 d × 288 5-minute buckets = 10,080 + 8,640), roughly 93k rows for a Node with five series. That is the number that justifies a bounded per-Report cleanup batch (2048) and a per-bucket upsert rather than a rewrite.
- **A bucket contributes coverage only between the observations it really holds (review F1).** `node_metric_aggregates.max_gap_seconds` is maintained inside the ingestion upsert (`candidate_gap_seconds` :1093, `MAX` in `AGGREGATE_UPSERT_SQL` :1059 — a maximum needs no threshold and no cadence assumption, and a correction can only raise it). At read time a bucket adds `span = last_observed_at - first_observed_at` to `coverage_seconds` only when `max_gap_seconds < silence_threshold_seconds(cadence, 0)` (:622); otherwise it contributes 0 while still returning its count, extremes and span, and the hole travels to the surface as `maxGapSeconds`. The judged cadence is the one the answer measured in its raw window, falling back to `grain_seconds / sample_count`; the raw tier's own rule is unchanged, so #213's coverage numbers stay byte-identical.
- **The served 24 h boundary is a contract, not the storage policy (review F3).** `metric_history::raw_window_cutoff(now)` (:136, `RAW_WINDOW_HOURS = 24`) is the boundary the answer is presented against (http/admin.rs:4661), so the same request is answered the same way whatever the raw family's `retention_days` says; the policy still decides what is *stored* and is still reported as `rawRetentionDays`.
- **A tier's serving window is its contract, most visibly in a migration (review F4).** 0067 normalises **every** `one_minute_aggregate` row to `(7, 7, 7, supported 1)`, `ensure_seeded` upserts the catalog tuple for the two bucket families and `aggregate_retention_days` (:775) answers from the catalog rather than the stored value, while the operator's own number survives in `audit_events` — because cleanup reads the stored days, a surviving `(30, 7, 365, 0)` row would have kept 1-minute buckets for 30 days against a 7-day contract (4.3× the promised budget), and the Owner update path cannot repair `supported`/bounds`.
- **The judged cadence is truncated to whole seconds on both sides of the wire (review N1).** The Server's fallback is integer division (`(cadence_seconds / sample_count.max(1)).max(1)`, metric_history.rs:1635), so a 5-minute bucket of seven observations is judged at 42 seconds and its hole threshold is 126; the WebUI now mirrors that rule (`Math.floor` in `metricJudgedCadenceSeconds` and `metricGapThresholdSeconds`, metricHistory.ts:290/:339) instead of keeping the fraction and rounding the threshold up to 129. A page and a Server that disagree by one rounding step disagree exactly at the boundary, which is the only place the two judgements have to agree: on the wrong side of it the Server reports a hole in the coverage it proved while the panel draws one continuous line through it.
- **Coverage between two buckets requires their windows to abut (review N3).** `silence_threshold_seconds` allows `window + cadence`, which exists so that a coarser tier's own window width is not mistaken for a silence - and that allowance only makes sense between two windows the tier really counted. A bucket is written exactly where an observation arrived, so a missing window is a stretch nobody observed, and the pair loop now also requires `windows_abut` (metric_history.rs:594): two aggregate neighbours one whole bucket apart are a gap whatever the allowance says. Cross-tier and cross-grain handovers are contiguous by construction (a coarse bucket ends exactly where the finer tier begins) and a mixed bucket/raw pair keeps the cadence rule alone, so the rule only fires on a window the tier did not write.
- **The upgrade seam keeps the raw evidence it already has (review N2).** 0067 creates the aggregate table empty and backfills nothing (migrations/0067_node_metric_aggregates.sql:43), so a series counted before #214 has retained raw rows and no bucket at all. The raw floor is therefore conditional on that bucket accounting for the minute: `load_range` asks `STRADDLING_MINUTE_LEDGER_SQL` for the bucket's `sample_count` and for the rows the minute still stores, and only starts raw at the minute edge when the count is at least the stored rows (metric_history.rs:1418; the second re-review tightened the probe from `buckets_hold_evidence`'s bare EXISTS to the count, because one delivery after the upgrade opens a bucket that covers only itself). Always handing the minute over answers nothing for it - no raw row is read and no bucket exists - and silently drops observations that were inside the promised window and still on disk, which is the failure the seam test pins.
- **Cleanup must not release a bucket that still holds protected observations (review F2).** `retention::release_cutoff` (:632) subtracts one bucket width for the two bucket families and is used by the delete (`cleanup_expired_metric_aggregates` :806), the estimate (`plan_family_targets` :996) and the persisted preview (:1281) so the three agree; the cost is one bucket of extra storage per tier.

**Defects the tests caught, and what they cost:**

1. **`aligned_bucket_start` bucketed a non-canonical instant.** A lenient `parse_rfc3339` accepts a fractional-second instant, so `2026-10-03T04:05:06.789Z` would have been silently floored into a bucket and counted as if it were a canonical observation — and a non-positive `grain_seconds` would have panicked on `div_euclid(grain_seconds)`. The function now returns `None` unless the instant is canonical (`canonical_instant(instant)?`, metric_history.rs:200-214) and unless the grain is positive, and the caller treats `None` as 'contributes no bucket' rather than as a zero.
2. **The exact-budget truncation bug, exposed by the Playwright acceptance test.** A page walk that ended after the 1-minute tier was spent *exactly* reported `truncated: false` and `continuation: null` while the 5-minute tier still held a point: the answer was silently incomplete. It was fixed by probing with `BUCKET_EVIDENCE_EXISTS_SQL` before declaring completeness (metric_history.rs:1553-1573, :1697) and by pinning the case in a new unit test (`a_budget_fitting_the_newer_tiers_exactly_still_reports_older_evidence_as_truncated`, :3095). The lesson is the same one the ticket's risk note predicted: an aggregate path fails by being quietly short, not by throwing.
3. **Acceptance harness lesson.** A seeded run must align a bucket **once** and then step off that boundary (`grainRun` aligns the first instant and then steps +60 s per value). Re-aligning each offset collapses a bucket's observations onto a single instant, which the Server correctly reads as one observation delivered repeatedly — a fixture bug that looks exactly like a Server bug. The spec comments the helper accordingly, and the paging assertion (5 pages of `limit=1` whose reversed instants equal the one-shot answer) exists to make that class of mistake fail loudly.

4. **The acceptance spec's own coverage expectation was wrong, and the real stack said so.** The tier flow asserted `coverageSeconds = 2 * MINUTE_SECONDS` with a comment claiming coverage is 'the stretch two neighbouring buckets prove, never a bucket's own span'. That contradicts the rule F1 established and docs/design/platpulse.md:630 states: a bucket claims the span between its first and last observation whenever its `max_gap_seconds` sits below the threshold the answer's judged cadence implies, and a bucket holding three observations two minutes apart really did observe those two minutes. The Server answered 240 s — the 5m bucket's own two proved minutes plus the two one minute intervals between the three one minute buckets — so the assertion and its comment were corrected to `4 * MINUTE_SECONDS` (`platpulse-web/e2e/metric-history-acceptance.spec.ts:562`) and re-run green on `desktop-1280` in 10.8 s. The lesson is the one the F1 finding already taught: coverage is what the evidence proves, so a fixture's expectation has to be derived from the evidence rather than from a slogan about which points may claim it.

The #213 seams were reused rather than duplicated: the delivery classification, the series ledger, the released-before stamp and the pause/gap ledger are all the same code paths as before, and the tier code only consumes them.
