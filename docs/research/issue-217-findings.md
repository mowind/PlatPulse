# Issue #217 findings — synchronization and consensus evidence: five numeric series and one state change log

**#217** asked for two kinds of evidence about how far a Node has got, and for them to be kept apart. The migration this ticket adds states both its subject and its place in the design: "Synchronization state and key consensus-height history (issue #217, design §11.4, §11.5, §11.6 and §11.7, parent #202 stories 46, 53 and 59)" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:1-2). The *numeric* key heights — a Node's sync current and highest block and the epoch's highest QC, lock and commit block — are quantities, so "Migration 0070 therefore extends node_metric_samples with exactly those five series and reuses node_metric_aggregates and node_metric_series_state unchanged" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:13-15). A synchronization or consensus *state* is not a quantity: "a numeric aggregate would erase an Error or Unknown stretch the moment it fell into a bucket, or invent a transition where the Server merely missed a Report" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:20-22), so states are an append-only change log with its own ledger and its own retention family instead. The ticket is committed as a1d07ce on top of #216 (commit 70f4a82); the tree additionally carries the post-review repairs, which are still ordinary working-tree changes to crates/platpulse-server/src/state_history.rs, crates/platpulse-server/src/http/report_ingestion.rs, crates/platpulse-server/migrations/0070_sync_consensus_history.sql, crates/platpulse-server/tests/state_history.rs and docs/design/platpulse.md (`git status --short` lists exactly those five). Where this note and the POST-REVIEW AMENDMENT disagree, the amendment is the current word because it was read against the repaired tree. The design section for it is **§11.7** of docs/design/platpulse.md, not §11.6 — §11.6 is already the metric-history section (`### 11.6 可信的指标历史：24 小时原始样本、30 天聚合层与共享 Host 系列（issue #213、#214、#215、#216）`, docs/design/platpulse.md:621), and the code comments that cite "design §11.6" do so for the numeric engine only, which is exactly where that engine is documented.

Everything below is the working tree as it stands, at the line references it was read at. Nothing in it is a plan, and nothing in it is a claim about a run this documentation pass did not perform (see VERIFICATION).

## SERVER (the real gaps)

1. **The Node metric set was a closed whitelist with no place for a chain height.** `node_metric_samples` was born with a five-name CHECK whitelist — `process_cpu_percent`, `process_memory_percent`, `data_directory_percent`, `peer_inbound_count`, `peer_outbound_count` (crates/platpulse-server/migrations/0041_node_metric_history.sql:11-15) — and the engine's own list agreed (`pub const NODE_METRIC_SERIES`, crates/platpulse-server/src/metric_history.rs:98). Whatever an Agent collected about its chain position, the Server had nowhere to store it, so story 53's first half could not be answered at all.
2. **No aggregate tier can carry a state, and no sample can carry a failure.** A bucket is a number. "The chain probe failed", "the value shown is the last good one", "the Agent did not say whether it is syncing" and "the syncing flag went from 1 to 0" are facts about an observation (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:17-24). The live projection knew a component's status in place, but nothing retained it as history: "when did this Node stop collecting consensus?" had no answer, and a value still displayed after a failed collection was indistinguishable from a fresh one.
3. **Silence and an unchanged state were the same non-event.** A state that does not change writes nothing, so a reader of history could only say the state was X at some instant long ago and would have to guess whether everything after it was unknown or unchanged — the "missing history described as a known normal period" failure story 59 names. The anchors of crates/platpulse-server/src/state_history.rs:91 (`STATE_ANCHOR_SECONDS = 3600`) exist to answer exactly that, and the migration explains the alternative it rejects: without anchors "two entries of an unchanged state would be arbitrarily far apart and a long silence would look exactly like a state that never changed" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:143-149).
4. **A new log of instants needs the release/replay rule #213 established.** Deleting an entry destroys the Server's ability to answer whether that instant was already recorded, so the cutoff a cleanup applies is stamped on the series itself (crates/platpulse-server/src/retention.rs:352-358, mirrored from the metric family). Without an equivalent stamp, a delivery replayed after a policy widening would be counted twice (issue #213).
5. **Low-space protection had no way to disclose a pause in a state log.** #212's protection stops optional metric history and counts each skipped sample on `capacity_skipped_series` (docs/design/platpulse.md:610-618). A log that every Report appends to raises the same question, and pausing it silently would draw a protected stretch as a Node that never changed.
6. **A new retention family is invisible until the policy table knows it.** The `retention_policies` family CHECK was a closed list of 15 names; with the old constraint in place the default seeding of a new family would be skipped silently (the seeding inserts with `INSERT OR IGNORE`), and a family with no policy row is invisible to the Owner and skipped by its own cleanup path — the state log would then grow without bound, which is the outcome the 30-day investigation floor exists to prevent (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:199-244).
7. **Purge ownership had to be decided, not inherited.** Storage history is Agent-scoped, but synchronization and consensus are properties of one Node's view of the chain, so a Node's Purge takes its state entries with it (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:32-34). Nothing about the two new tables said which side of that boundary they were on until this ticket wrote it down (crates/platpulse-server/src/node_purge.rs:237-240 and :366-367).

## What was added

### The raw tier gains exactly five series, and only the raw table is rebuilt

- `node_metric_samples` is rebuilt (`ALTER TABLE ... RENAME TO node_metric_samples_old`, crates/platpulse-server/migrations/0070_sync_consensus_history.sql:40) with the CHECK extended from five to ten names (:44-55), every stored row copied across (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:62-66), the old table dropped (:66) and both indexes recreated — `node_metric_samples_recent_idx` and `node_metric_samples_observed_at_idx` (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:68 and :71).
- The five names are `sync_current_block`, `sync_highest_block`, `consensus_highest_qc_block`, `consensus_highest_lock_block`, `consensus_highest_commit_block`, in that order in the engine's list (crates/platpulse-server/src/metric_history.rs:98-110, first new entry at :104; `is_node_metric` at :112) and in the migration's CHECK (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:50-54).
- They are separate series "rather than one 'height' series because a highest QC block and a commit block are different facts about the same epoch and a reader must be able to see one advance without the other" (crates/platpulse-server/src/metric_history.rs:99-108), and a failed chain probe writes no sample for them: "a numerical aggregate never erases" what the state log records (crates/platpulse-server/src/metric_history.rs:108-111).
- **Why only the raw table:** the aggregate tables never named the metrics. `node_metric_aggregates` checks only `length(metric) BETWEEN 1 AND 64` (crates/platpulse-server/migrations/0067_node_metric_aggregates.sql:45) and so does the restated raw table of the aggregate ticket (crates/platpulse-server/migrations/0066_node_metric_history.sql:44), so the five new series fit without touching either; the Host whitelist (crates/platpulse-server/migrations/0068_host_metric_history.sql:46) is a different scope and is not involved. The rebuilt table's own rows are therefore the only thing the migration has to preserve, and it does.
- The writes ride the existing optional-metric path in the ingestion transaction: `(\"sync_current_block\", sync.current_block)`, `(\"sync_highest_block\", sync.highest_block)`, `(\"consensus_highest_qc_block\", consensus.highest_qc_block)`, `(\"consensus_highest_lock_block\", consensus.highest_lock_block)`, `(\"consensus_highest_commit_block\", consensus.highest_commit_block)` (crates/platpulse-server/src/http/report_ingestion.rs:1532-1558, `sync_current_block` first at :1535 and `consensus_highest_commit_block` last at :1557).

### The state log and its ledger

- `node_state_observations` (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:117-135): `PRIMARY KEY (node_id, component, observed_at)`, with `component IN ('sync','consensus')`, `entry_kind IN ('change','anchor')`, `collection_state IN ('starting','ok','error','disabled','unsupported')`, `value_source IN ('current','last_good','none')`, `value_observed_at` NULL or 20 characters, `error_code` NULL or 1..128 characters, `syncing` NULL or 0/1, and an FK on `nodes(node_id) ON DELETE CASCADE`. A state is "stored in components rather than one opaque string so a reader can ask 'when did this Node stop collecting consensus?' without parsing" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:119-123).
- `node_state_observations_expiry_idx (observed_at, node_id, component)` (:140) orders the cleanup walk while the read path pins one series newest-first by the primary key.
- `node_state_series_state` (:159-194) is "the twin of `node_metric_series_state`": one row per `(node_id, component)` with `first_observed_at`, `last_observed_at`, `last_received_at`, the last vector's components, `last_entry_at`, the five counters (`entry_count`, `change_count`, `anchor_count`, `replayed_count`, `corrected_count`) and `released_before` defaulting to `1970-01-01T00:00:00Z`, plus a unique index on the pair. It "holds no state value beyond the last one recorded, so it is a series ledger and not a second copy of the history" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:143-151).
- Constants and vocabulary live in one place: `STATE_COMPONENTS = [COMPONENT_SYNC, COMPONENT_CONSENSUS]` (crates/platpulse-server/src/state_history.rs:54), `STATE_ANCHOR_SECONDS = 3600` (:91), `DEFAULT_STATE_LIMIT = 2_000` (:94), `MAX_STATE_LIMIT = 20_000` (:97), the five `COLLECTION_STATE_*` names and three `VALUE_SOURCE_*` names (:56-85), and `collection_state_name(status: ComponentStatus) -> &'static str` (:108), which maps Starting/Ok/Error/Disabled/Unsupported onto "the vocabulary `component_status.state` already uses, so the state log and the live projection cannot drift apart".

### The state vector, and `value_source` derived at write time

- `pub struct StateVector { collection_state, value_source, error_code, syncing }` (crates/platpulse-server/src/state_history.rs:133) is the whole state: "a change of any of them is a state change, which is why a failure and a success never collapse into one row".
- `StateObservation::of_component` (:157) decides `value_source` from the observation plus the projection: a component that carries a value is `current` only when its status is `Ok`, otherwise `last_good` with `value_observed_at = component.latest_observed_at`; a component with no value but a retained instant is `last_good` at that earlier instant; nothing known is `none`.
- `syncing` is kept "only when the collection succeeded (a failed probe is unknown, never false)" — the migration states the rule as design 5.1's Unknown-is-not-false: "storing 0 there would report 'not syncing' for a Node whose sync state is Unknown" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:113-116). The consensus vector never claims a flag at all, because the flag belongs to the sync value (crates/platpulse-server/src/http/report_ingestion.rs:1317-1325).
- `pub async fn retained_value_at(tx, agent_id, node_id, component)` (:221) reads the age of the value the Server still holds from `component_status`, and it runs *after* the delivery being recorded has been written, "because the projection is what the Owner actually sees".
- The ingestion order makes that true: the `save_component` calls for Rpc/Sync/Consensus run first (crates/platpulse-server/src/http/report_ingestion.rs:1241-1263) and the state writes follow at :1279-1325, with the cutoff from the new `state_window_cutoff` (:904).
- The observed instant is the Agent's own attempt instant when it reports one, otherwise the Report's generation instant (`component_instant`, crates/platpulse-server/src/state_history.rs:124), so "a component that carries no attempt (disabled, unsupported) still proves the Node was alive at the instant its Report was generated" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:99-102).

### The change/anchor rule

- `fn entry_kind(...)` (:413): a correction rewrites the instant as `change`; a replay writes nothing; an observed delivery is `change` when the vector differs from the state the log held ("the evidence story 53 is about"), `anchor` when the vector is unchanged and `anchor_due` says an hour has passed, and nothing at all otherwise.
- `fn anchor_due(...)` (:442) is true when either instant fails `auth::parse_rfc3339` — "so a series with no retained row anchors at once" — or when `now - last >= STATE_ANCHOR_SECONDS`.
- The read side discloses the cadence (`anchor_seconds` in the answer) because "the anchor keeps a constant state provable, otherwise the read side could only say the state was X at some instant long ago and would have to guess whether everything after is unknown or unchanged".
- A Report that never arrives writes nothing: "a Node that stopped reporting writes nothing at all. Silence is therefore a hole a reader has to see as a hole, never a manufactured transition" (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:26-30).

### Delivery classification and the ledger counters

- `fn classify_state(...)` (crates/platpulse-server/src/state_history.rs:470) judges a delivery with three pieces of evidence: the ledger's newest counted instant (`last_delivery_at`, crates/platpulse-server/migrations/0070_sync_consensus_history.sql:184), the row held for the instant, and `fetch_predecessor` (crates/platpulse-server/src/state_history.rs:570) - the newest row strictly before it, read whenever the log holds no row for the instant itself (:283-287). Any observation later than `last_delivery_at` (:478) is `Observed`, because an unchanged state writes no row between anchors and the newest row alone therefore cannot tell a repeat from a first sighting. A held row that disagrees with the delivery is `Correction` (:481). At or above the effective floor - the ledger's `released_before` when it is forward of the cutoff, the cutoff otherwise (:484-487) - with no held row: a predecessor vector equal to the delivery is a harmless `Replay` (:498-499), a delivery at the newest counted instant that disagrees with the held row is `Correction` (:501-507, it rewrites that instant's row without counting a second transition), and a predecessor that differs is the transition the late delivery evidences, so it is `Observed` (:509). An instant below the floor with no row, and anything else, is `Replay` (:511). The promise is bounded and the doc comment says so (:452-469): the log counts an instant exactly once only when it holds a row for it, plus the newest instant the ledger counted.
- `record_state` (:262) writes the row only when the instant is not released, the delivery is not a replay and a kind was produced (`!released && delivery != Delivery::Replay && kind.is_some()`), then folds a `LedgerDelta { counted, change, anchor, replay, correction, entry_at }` into the ledger — where `counted = delivery == Observed` and `entry_at` is set only for an instant that really got a row.
- The ledger's counters move by bound deltas against seed constants `1, 1, 0, 0, 0`, matching `metric_history.rs SERIES_UPSERT_SQL`: a constraint is judged before the conflict is resolved, and "binding the delta there would make the CHECK constraints reject the row a replay or an anchor is folded into".
- A correction replaces the row of its instant whole: `store_entry` (crates/platpulse-server/src/state_history.rs:612), called by `record_state` (:262) in the same transaction, assigns every state column from `excluded` (`collection_state`, `value_source`, `value_observed_at`, `error_code`, `syncing`) - the three `CASE` arms that once kept the stored `value_source`/`value_observed_at` are gone, so a correction that knows less than the row it replaces cannot leave a half-old mix behind: the earlier delivery's evidence for that instant is superseded rather than merged, and the ledger's `corrected_count` keeps the trace that a correction happened (crates/platpulse-server/src/state_history.rs:612-660, crates/platpulse-server/migrations/0070_sync_consensus_history.sql:117-135).
- `StateLedger::delivery_cadence_seconds()` (:842) is `(span / (entry_count - 1)).max(1)`, and 0 when there are fewer than two counted deliveries or the span is not positive: the ledger counts every delivery the log accepted, including the ones that wrote no row, so this is the Node's reporting cadence and not the anchor cadence of the rows, and 0 means unknown, never "no interval".

### Low-space protection pauses the log through the existing ledger

- `record_state` on a `HistoryGate::Paused { interval_id }` with a delivery that is not `Observed` returns `crate::capacity::record_skipped_series(tx, interval_id, SkippedScope::Node, node_id, component, "", &observed_at)`: the component is the metric key and the dimension is empty. No new capacity schema was introduced; the pause is "a disclosed boundary (story 59), the delivery is not recorded and the loss is counted on the shared skipped-series ledger keyed by the component the way a metric is keyed by its name".
- The read side turns that into evidence rather than a gap: `load_range` (:904) judges the answer with `metric_history::continuity_with_windows` over points carrying `window_seconds: STATE_ANCHOR_SECONDS` and `metric_history::load_pauses` for the same series, so a stretch inside a protection interval is a `protection_pause` gap with its `skipped_count` when the stretch covers the whole interval, and `collection_gap` when nobody observed.
- The state log is therefore paused by the same protection #212 introduced for optional metric samples, and the Admin answer can say a stretch was a chosen pause rather than a Node that went quiet.

### The retention family: `observation_state`

- `pub const FAMILY_OBSERVATION_STATE: &str = "observation_state"` (crates/platpulse-server/src/retention.rs:56), in the catalog as `PolicyDefaults { family: FAMILY_OBSERVATION_STATE, label: "Synchronization State History", default_days: MIN_INVESTIGATION_AGGREGATE_DAYS, min_days: ..., max_days: ..., supported: true, class: PolicyClass::Investigation, targets: TARGET_OBSERVATION_STATE }` (crates/platpulse-server/src/retention.rs:610-622) — 30/30/30, so an ordinary edit can neither shorten the states a reader still needs nor promise a stretch the design does not.
- `const STATE_CLEANUP_BATCH: i64 = 2048` (:343) with `const _: () = assert!(STATE_CLEANUP_BATCH >= platpulse_core::protocol::MAX_NODE_OBSERVATIONS as i64 * crate::state_history::STATE_COMPONENTS.len() as i64, "the per-Report state batch must cover one maximal Report")` (:346): "A Report can state at most one sync and one consensus state per Node, so the bound that keeps this family expiry rate equal to its arrival rate is the protocol Node maximum times the number of recorded components."
- `STATE_RELEASED_BEFORE_SQL` (:358) stamps the cutoff this pass applies onto every series whose entries are about to leave, and only ever forward (`released_before < ?`), so a state replayed after a policy widening is still recognised as a replay and never counted twice.
- `TARGET_OBSERVATION_STATE` (:360-372) is one `CleanupTarget { table: "node_state_observations", kind: Delete, count_sql, delete_sql }` and nothing else: "the entries are the evidence and the series ledger `node_state_series_state` is deliberately not a target, exactly as the metric ledgers are not: what a series last recorded stays knowable after its entries expire".
- `cleanup_expired_observation_state(pool, now)` (:928) reads `observation_state_retention_days` (:887), returns `Ok(0)` when the window is <= 0 ("a keep-forever window has no cutoff, so it can never expire a row"), computes the cutoff with `family_cutoff`, stamps the ledger, then deletes one bounded batch per target and sums `rows_affected`.
- The window is read through the ingestion transaction as well: `state_retention_days_tx` (:908) exists because "report ingestion holds the Server's single write connection, so a policy read through the pool would wait for a connection only the caller can release, and reading the window inside the ingestion transaction is also the stronger guarantee - no policy edit can land between the read and the states it classifies".
- The migration extends the `retention_policies` family CHECK from 15 names to 16 without changing any operator-selected value, by the rebuild-copy-drop pattern (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:199-244).

### The Admin contract

- `GET /api/admin/v1/nodes/{node_id}/state-history`, Owner-only, registered in the router at crates/platpulse-server/src/http/admin.rs:7839-7841 and declared with `#[utoipa::path(get, ...)]` at :4898; handler `admin_node_state_history` (:4917), response builder `state_history_response` (:4968).
- Query: `component` (required, `sync` or `consensus`), optional canonical second-precision `from`/`to`, an exclusive `before` cursor, and `limit` (default `DEFAULT_STATE_LIMIT = 2_000`, clamped to 1..`MAX_STATE_LIMIT = 20_000`). An unparseable query is 400 `invalid_query`; a component outside the recorded pair is 400 `invalid_component` (`"component is not a recorded state series"`, :4947-4948) "like an unknown metric, so the caller gets the same error body and no empty series that would look like a component nobody ever reported"; an unknown Node is 404; a failed lookup is 503. A cursor must satisfy `before > from && before <= to`, because "a cursor outside the requested range would answer a stretch nobody asked about".
- Entries are returned oldest first (`load_range` reverses a `observed_at DESC` page of `limit + 1` rows, so the continuation is the oldest row of the page and paging older neither repeats nor skips a row). `AdminStateEntry` (:4761) carries the state vector plus `delay_seconds`, `clock_suspect` and `clock_note` derived from `metric_history::sample_timing`.
- Gaps (`AdminStateGap`, :4797) name their kind and a reason: `"low-space protection paused state recording"` for a protection pause and `"no state was recorded in this stretch"` for a collection gap, so no surface bridges silence with a constant state or reads a pause as a change.
- `AdminStateSeries` (:4813) reports `observed`, the first/last instants, the five counters, the latest vector, `entries_returned`, `coverage_seconds`, `window_seconds` and `released_before` ("the floor this series last stamped, so a missing early entry is a boundary and not a quiet start").
- `AdminStateHistoryResponse` (:4858) adds `requested_from` (so a clamped answer says what it clamped), `availability` (null while the whole range is answerable, `partial` when it was clamped to the retention horizon, `unavailable` when the range is older than any retained history), `retention_days`, `anchor_seconds`, `cadence_seconds`, `truncated` and `continuation`. A recorded state has no aggregate tier, so the retention policy is its whole horizon: `horizon_cutoff = now - retention_days`, and the default window is `DEFAULT_WINDOW_HOURS` (24 h).
- Nothing after the newest entry is claimed: "a state is not a constant that extends until the next report", so silence after the newest entry is not a gap.
- The answer goes through `no_store` because "Owner-only Node history is per-session data that must never be stored by an intermediary or a browser cache and replayed to another session (design 12.4, webui.md 6.4)".

## DECISIONS

- **Five numeric series, not one height series.** A highest QC block and a commit block are different facts about the same epoch, and a reader must be able to see one advance without the other (crates/platpulse-server/src/metric_history.rs:99-108).
- **States are a change log, not samples.** Averaging cannot represent "the probe failed", and a bucket would erase an Error or Unknown stretch or invent a transition where the Server merely missed a Report (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:17-24).
- **Rebuild the raw table, leave the aggregate tables alone.** The metric set is a CHECK whitelist on the raw table only; the aggregate tables check metric length, so the new series fit without a migration and the raw table's existing rows are copied across instead of dropped (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:36-40, :62-66).
- **Store the state as a vector of components.** A reader can ask "when did this Node stop collecting consensus?" without parsing an opaque string, and a change of any component is a state change (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:119-123).
- **`value_source` is derived at write time, never recomputed at read time.** The write happens after the projection is saved, so "the Server still shows a value it observed earlier" is answered from the projection the Owner actually sees, and the age of the last-good value comes from evidence (crates/platpulse-server/src/state_history.rs:171, :221).
- **`syncing` is stored only where the collection succeeded.** A failed attempt did not observe the flag, so storing 0 would report "not syncing" for a Node whose sync state is Unknown (design 5.1), and the consensus vector never claims the flag at all (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:113-116).
- **`value_observed_at` is not part of the change vector.** A fresh value instant on every Report is an observation, not a state change; leaving it out is what keeps the change log about states (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:104-111).
- **An anchor at most once per hour, and at least one.** An unchanged state must stay provable, but re-stating it on every Report would fill the log with rows that say nothing new - so `anchor_due` answers true once `now - last_entry_at` reaches `STATE_ANCHOR_SECONDS` (crates/platpulse-server/src/state_history.rs:442), an unchanged vector for an instant the log cannot compare anchors at once (:429), and a series with no retained row anchors its next delivery immediately (`entry_kind`, :413) so it cannot be silent twice.
- **A correction replaces the whole row, so it cannot leave a half-old mix behind.** `store_entry` assigns every state column from `excluded`, which is the review's fix to the earlier partial upsert: an instant's row answers with the newest evidence the Server holds for that instant - a correcting failure says so in `collection_state`, `error_code`, `value_source` and `syncing` - while the ledger's `corrected_count` keeps the trace that a correction happened (crates/platpulse-server/src/state_history.rs:612).
- **The ledger's seed constants are not the delta.** A CHECK constraint is judged before the conflict is resolved, so the insert must already satisfy `entry_count >= 1` and `change_count >= 1`; the delta is applied in the update, exactly as the metric ledger does it.
- **The component is the metric key on the shared skipped-series ledger.** Low-space protection reuses `capacity_skipped_series` with the component in the metric column and an empty dimension rather than adding a capacity schema for states (crates/platpulse-server/src/state_history.rs:310-327).
- **The series ledger is not a cleanup target.** Only `node_state_observations` is deleted; what a series last recorded stays knowable after its entries expire, which is how the Admin surface tells "released" apart from "never recorded" (crates/platpulse-server/src/retention.rs:360-372).
- **The release stamp is written before the rows leave, and only forward.** `released_before = MAX(released_before, cutoff)` under `released_before < cutoff`, so a delivery replayed after a policy widening is still a replay (crates/platpulse-server/src/retention.rs:352-358).
- **`STATE_CLEANUP_BATCH = 2048` with a compile-time assertion.** The bound that keeps the family's expiry rate equal to its arrival rate is `MAX_NODE_OBSERVATIONS x STATE_COMPONENTS`, and the assertion stops the two from drifting apart (crates/platpulse-server/src/retention.rs:343-349).
- **The window is 30 days and immutable by ordinary edit (min == max).** Recorded states annotate the numeric heights of the same window, so they live for the investigation horizon and no longer (crates/platpulse-server/src/retention.rs:610-622).
- **The policy table's family CHECK is rebuilt, and the catalog registers the row.** With the old constraint in place the new family would be seeded silently-skipped, invisible to the Owner and skipped by its own cleanup path; a migration may not invent an operator's policy value, so the catalog supplies the default (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:199-244).
- **The window is read inside the ingestion transaction.** A pool read would deadlock against the single write connection the caller holds, and reading it there also means no policy edit can land between the read and the states it classifies (crates/platpulse-server/src/retention.rs:908-926).
- **An unknown component is 400, not an empty series.** An empty answer would look like a component nobody ever reported, which is a different fact from "that is not a recorded series" (crates/platpulse-server/src/http/admin.rs:4947-4948).
- **The read acknowledges truncation and clamping.** `truncated` plus an exclusive `continuation` for paging, `requested_from` plus `availability` for a clamped or unanswerable range, and nothing claimed after the newest entry (crates/platpulse-server/src/http/admin.rs:4858-4915, crates/platpulse-server/src/state_history.rs:904).
- **Purge takes the state log with the Node, and the required-table list names it.** Synchronization and consensus are properties of one Node's view of the chain, unlike the Agent-scoped storage history (crates/platpulse-server/src/node_purge.rs:239-240, crates/platpulse-server/src/database.rs:94-95).

## REVIEW

### Standards

- **SQLite through SQLx typed SQL, no ORM:** the new code is `sqlx::query`/`query_as` with bound parameters and `ON CONFLICT` upserts, in the same shape as the metric ledger (crates/platpulse-server/src/state_history.rs:262-392); no schema built at runtime.
- **Migrations are append-only and preserve evidence:** 0070 rebuilds two tables and the policy CHECK, and in every case copies the existing rows or the operator's values across before dropping the old table (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:62-66, :199-244).
- **Observations stay scoped per Node:** both tables are keyed by `node_id` with `ON DELETE CASCADE`, and the read route hangs off `/nodes/{node_id}`; the Agent-scoped storage history is untouched (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:117-135, :159-161).
- **Last-good / Unknown semantics preserved:** a failed probe stores no `syncing` and no fresh value; the Server's fallback is recorded as `last_good` with the earlier instant (crates/platpulse-server/src/state_history.rs:171, :221).
- **Server is the trust boundary:** the state is derived from the Agent's own component observation and the Server's projection, never from a client-supplied string; the component pair is validated server-side and answered with 400 (crates/platpulse-server/src/http/admin.rs:4947-4948).
- **Owner-only read, no-store, no control surface:** the route is under `/api/admin/v1` with the existing Owner middleware, answers through `no_store`, and no new endpoint writes, pauses or deletes anything.
- **Documentation voice:** §11.7 is factual Chinese prose with bold lead-ins and file:line evidence, matching §11.4-§11.6; the research note follows the section order of docs/research/issue-216-findings.md.

### 复审后的修复与仍开放的边界 (the post-review repairs, and the boundaries that stay open)

- **The slow-cadence silence is closed by a formula, not by an exception.** An unchanged state writes only an anchor, so the ordinary distance between two recorded states is the anchor interval plus one delivery cadence. `load_range` therefore gives every recorded point a window of `STATE_ANCHOR_SECONDS + cadence_seconds.max(0)` (crates/platpulse-server/src/state_history.rs:976, comment :971-975), and the engine's continuity rule adds the measured cadence once more, clamped at 300 s, on top of that window's floor (`silence_threshold_seconds`, crates/platpulse-server/src/metric_history.rs:877-879: `gap_threshold_seconds(cadence).max(window_seconds + cadence)`). A stretch the Server cannot prove is never reported as silence, which is the whole point of the formula, and docs/design/platpulse.md:687 states it the same way. `an_unchanged_state_spanning_a_slow_cadence_is_not_reported_as_silence` (crates/platpulse-server/tests/state_history.rs:1618) pins it.
- **A late insert states the newest counted state instead of leaving the ledger describing a row the log no longer holds.** `repair_late_insert` (crates/platpulse-server/src/state_history.rs:1022, called from `record_state` at :346-355) writes the row for the instant the ledger last counted (`ledger.last_observed_at`) once a late delivery of an older instant has been accepted, and returns None when that instant is at or after the late one, has been released, or already holds the delivered vector (doc comment :1004-1021). The row it writes is not a delivery, so it moves no counter: it exists so the newest counted state on the record is one the log can actually show, and `a_late_insert_keeps_the_newest_counted_state_on_the_record` (crates/platpulse-server/tests/state_history.rs:1684) is the regression test.
- **Strict deduplication is bounded, and that bound is the boundary that stays open.** `last_delivery_at` makes a repeat of the newest counted instant a `Replay` or a `Correction` rather than a fresh transition, but the log holds no row for an instant an unchanged delivery was counted for, so a repeat of an older such instant is indistinguishable from an instant never seen before (crates/platpulse-server/migrations/0070_sync_consensus_history.sql:152-158; the code's own doc comment says the same at crates/platpulse-server/src/state_history.rs:452-469). Two HTTP counterexamples from the review mark the edge of the guarantee: one series answered `entryCount` 4 with `correctedCount` 0, and another answered `entryCount` 4 with `replayedCount` 0 and `correctedCount` 1. The promise this ticket may claim is therefore the bounded one — an instant the log holds a row for, plus the newest instant the ledger counted, is counted exactly once — and never that any previously counted instant is never recounted.
- **The review's closing state.** F1, F5 and MINOR 6 are closed. F2 is closed under the contract this tree adopts: a silence shorter than the provable threshold is unidentifiable, and nothing may claim to identify it. F3 and F4 are fixed as far as that contract goes, and one boundary stays open with it — deduplication is bounded, not exact. This note therefore does not claim that every finding is closed.
