# Issue #216 findings — storage by mount path: the mount list a storage series is read through

**#216** (`feat: 按挂载路径调查存储使用历史`) asked for storage history that can be investigated per mount path: which paths an Agent has reported, which of them are still being reported, what each one's evidence covers, and how to read one path's series without typing a string nobody can guess. Parent **#202** (stage 2, plan ticket 14/23), user stories 46, 50, 51, 52 and 59, design §11.6; the migration this ticket added states its own place in the sequence and the shape of the read it serves (crates/platpulse-server/migrations/0069_host_mount_coverage.sql:3-14). It follows #215 (the shared Host resource history, commit 9296f41), the ticket that made storage evidence exist per mount path and deliberately left the path unnamed to the client; #216 is the read that makes those paths reachable, and it adds no new collection — the cadence, the coverage and the silence it answers with are the same evidence the metric-history engine already stores.

Everything below is the working tree as it stands, at the line references it was read at. Nothing in it is a plan, and nothing in it is a claim about a run this documentation pass did not perform (see VERIFICATION).

## SERVER (the real gaps)

1. **The identity of a storage series was a string the Server never told anyone.** #215 keyed the storage evidence by the mount path the Report carried — `PRIMARY KEY (agent_id, metric, dimension, observed_at)` (crates/platpulse-server/migrations/0068_host_metric_history.sql:62) over the series ledger `PRIMARY KEY (agent_id, metric, dimension)` (:96) — and its findings recorded the consequence on purpose: "The Admin DTO does not list the mount paths an Agent has reported; the Operator names one" (docs/research/issue-215-findings.md:76), because "The alternative — teaching the Admin DTO to list an Agent's mount paths — would have widened the contract to save one typed field, so the Server DTO was deliberately not extended" (docs/research/issue-215-findings.md:85). A path an Agent stopped reporting was therefore unreachable exactly when an Operator needed it, and the only way to a path was to remember it.
2. **Nothing answered whether a path was still being reported.** The one storage read was the window route (`GET /api/admin/v1/agents/{agent_id}/metric-history`, crates/platpulse-server/src/http/admin.rs:4731, handler :4751), which answers items plus a ledger summary for a requested range. The silence rule the engine already had — `gap_threshold_seconds` (crates/platpulse-server/src/metric_history.rs:734) — judges gaps *inside* a window; no answer said "this path has stopped", and no answer measured the Agent's cadence from stored evidence at all: `observed_cadence_seconds` (crates/platpulse-server/src/metric_history.rs:1067) takes samples already in memory, so it could only be reached by reading a window first.
3. **The ledger read had no index for the order a mount list needs.** The Host ledger's only index is `host_metric_series_state_series_idx (agent_id, metric, dimension)` (crates/platpulse-server/migrations/0068_host_metric_history.sql:99-100) — the equality prefix. A read ordered `last_observed_at DESC, dimension ASC` under equality on `(agent_id, metric)` can use that index for the prefix and must still sort every path the Agent has ever reported before a limit can drop the oldest of them.
4. **No answer carried a coverage bound, so a bounded list would have been a silent one.** A mount list has to be bounded — one Report may declare at most `MAX_HOST_MOUNTS = 128` mount paths (crates/platpulse-server/src/metric_history.rs:83) — and the ledger keeps paths whose samples were long ago released, so a list with neither a stated limit nor a stated truncation would have hidden mounts instead of naming them.
5. **The three boundaries that decide what a path's evidence means had no surface.** Retention stamps `released_before` on the ledger and releases raw samples (`HOST_RAW_METRIC_RELEASED_BEFORE_SQL`, crates/platpulse-server/src/retention.rs:326, "never rewrites a newer stamp" :308); a low-space pause records a skipped append per mount path in `capacity_skipped_series` (`PRIMARY KEY (interval_id, scope_kind, scope_key, metric, dimension)`, crates/platpulse-server/migrations/0068_host_metric_history.sql:167-176) and appears only in the Operations capacity surface; a Node Purge removes Node rows and touches no `host_metric` table (crates/platpulse-server/src/node_purge.rs has no reference to them). A storage surface that could not tell "released by retention", "not appended under a pause" and "never observed" apart would present three different facts as one empty series.
6. **Nothing in the WebUI could list mount paths.** The #215 panels ask for a typed path (`HostMountPathControl`, platpulse-web/src/pages/metricHistoryPanel.tsx:752) and the Agent detail page's section 06 (platpulse-web/src/pages/AdminAgents.tsx:749) had no list above that control.

The risk the ticket named — treating a mount path as a stable device identity — is refused in the shape of the answer rather than by a comment: the mount object carries no identifier and no device, and the same path observed on a different machine is by contract indistinguishable (see DECISIONS).

## What was added

### The ledger gets an index for the order a mount list needs

- **crates/platpulse-server/migrations/0069_host_mount_coverage.sql** (16 lines) is one statement: `CREATE INDEX host_metric_series_state_mount_idx ON host_metric_series_state (agent_id, metric, last_observed_at DESC, dimension ASC);` (:15-16). Its comment states why the trailing pair is ordered that way: the coverage route reads one Agent's storage series newest path first with a limit, so the read "must be served by an index instead of a sort of every mount path the Agent has ever reported" (:3-9), and `(last_observed_at DESC, dimension ASC)` under equality on `(agent_id, metric)` is "what lets the limit drop the oldest paths rather than an arbitrary slice of the mount churn" (:11-14).
- **crates/platpulse-server/src/database.rs:24**: `SERVER_SCHEMA_VERSION: i64 = 69;` (was 68).

### The coverage read: the ledger is the list, the join is the newest reading

- **crates/platpulse-server/src/metric_history.rs:2329 `HOST_COVERAGE_SQL`** joins the ledger to the raw sample at the instant the ledger names — `LEFT JOIN host_metric_samples s ON s.agent_id = l.agent_id AND s.metric = l.metric AND s.dimension = l.dimension AND s.observed_at = l.last_observed_at` — under `WHERE l.agent_id = ? AND l.metric = ? ORDER BY l.last_observed_at DESC, l.dimension ASC LIMIT ?`. The ledger is the source of the list, so a path whose samples were released is still answered; the join is a LEFT join, so a released newest reading answers unknown instead of dropping the path.
- **:2336 `pub async fn load_host_metric_coverage<'e, E: sqlx::Executor<'e, Database = Sqlite>>(executor: E, agent_id: &str, metric: &str, limit: i64) -> Result<(Vec<HostSeriesCoverage>, bool), sqlx::Error>`** reads `limit + 1` rows and returns `truncated = rows > limit`, which is what lets the route state what it left out rather than guess whether anything was left out.
- The three shapes are the answer's own: :2274 `CoverageReading { value, observed_at, received_at }`, :2286 `SeriesCoverage { first_observed_at, last_observed_at, last_received_at, observation_count, replayed_count, corrected_count, released_before, latest }` and :2309 `HostSeriesCoverage { mount_path, coverage }`.
- **:2270 `NO_RELEASE_BOUNDARY: &str = "1970-01-01T00:00:00Z"`** is the ledger's own default, and :2393 turns it back into `None`: a series nothing was ever released from says so instead of naming 1970 as a boundary.
- **:2264 `pub const MOUNT_COVERAGE_LIMIT: i64 = 2 * MAX_HOST_MOUNTS as i64;`** (256) is the list's bound, and it is twice the Report bound because one mount path holds two storage series (`disk_used_bytes` and `disk_total_bytes`).
- Nine unit tests over the helpers `coverage_store()` (:4289) and `store_mount_reading(...)` (:4312): `the_mount_list_answers_the_newest_path_first_and_states_its_truncation` (:4340 — three paths with a limit of two answer `["/new", "/middle"]` and `truncated` true, "the limit must leave out the paths the Agent stopped reporting first", while a limit of three answers the whole list and `truncated` false), `two_paths_observed_at_one_instant_are_ordered_by_the_path` (:4396), `a_released_newest_reading_is_unknown_with_its_release_boundary` (:4420), `the_agent_cadence_is_measured_from_its_newest_host_observations` (:4470), `a_collection_interval_that_just_changed_states_no_cadence` (:4536 — a legal `collection_interval` change leaves the previous interval disagreeing with the newest one by more than `CADENCE_AGREEMENT_FACTOR`, so the answer is cadence 0 and the panel says it could not measure a cadence rather than measuring the old rhythm), `the_merged_mount_list_is_cut_at_the_bound_it_states` (:4591), `one_answer_reads_one_snapshot_of_the_mount_ledger` (:4657), `a_mount_is_only_called_silent_against_a_rhythm_it_has` (:4745) and `the_mount_coverage_read_is_index_backed_and_never_sorts_the_ledger` (:4776, which runs `EXPLAIN QUERY PLAN` over `HOST_COVERAGE_SQL` and asserts the plan uses `host_metric_series_state_mount_idx`, never contains `SCAN host_metric_series_state`, and contains no `TEMP B-TREE`).

### The cadence is measured, and 0 means nobody could measure it

- **:2557 `SERIES_CADENCE_SQL`** and **:2572 `pub async fn load_observed_cadence<'e, E: sqlx::Executor<'e, Database = Sqlite>>(executor: E, scope: &SeriesScope<'_>) -> Result<i64, sqlx::Error>`** are the answer's second fact: the Agent's cadence, measured from its newest stored observations and fed in the order they happened to the engine's own `current_cadence_seconds` (:1094) — the newest interval is trusted only when the interval before it agrees within `CADENCE_AGREEMENT_FACTOR = 2` (:1076) — over :2267 `COVERAGE_CADENCE_SAMPLES: i64 = 16` observations. The cadence is read from one Host series rather than per mount because the Agent observes its Host once (crates/platpulse-server/src/http/admin.rs:4865-4868) — and that is the whole reason the storage list can judge silence at all.
- The silence rule stays the engine's: `pub fn gap_threshold_seconds(cadence_seconds: i64) -> i64` (:734) is `cadence_seconds.clamp(1, MAX_OBSERVED_CADENCE_SECONDS) * GAP_CADENCE_FACTOR` then `.max(MIN_GAP_SECONDS)` (:735-736), with `MIN_GAP_SECONDS = 120` (:343), `GAP_CADENCE_FACTOR = 3` (:349) and `MAX_OBSERVED_CADENCE_SECONDS = 300` (:358) — so the threshold is three cadences of at most five minutes and never less than two minutes, at most 900 seconds.

### The Admin contract

- **`GET /api/admin/v1/agents/{agent_id}/storage-mounts`** (crates/platpulse-server/src/http/admin.rs:4823, `async fn admin_agent_storage_mounts` :4836, route table :7395; OpenAPI handler crates/platpulse-server/src/openapi.rs:93, schemas :229-231). Owner-only like every Admin route, `no-store`, and the refusals keep the meanings they had on the metric-history routes: `401 auth_required`, `403 owner_required`, `404 not_found` for an unknown Agent, `503` when the read cannot be served. `404 not_found` is for an Agent this Server does not hold and for nothing else: an enrolled Agent that has never reported a Host is answered `200` with an empty `mounts` list, because a registered Agent with no evidence is a real answer rather than a missing subject — `an_agent_that_has_reported_nothing_is_an_empty_list_not_a_missing_agent` asserts both halves (`host_owner_exists`, :5095).
- Three DTOs, camelCase and `ToSchema` throughout: :4546 `AdminStorageSeries { metric, observed, first_observed_at, last_observed_at, last_received_at, observation_count, replayed_count, corrected_count, released_before, latest_value, latest_observed_at, latest_received_at, latest_delay_seconds, latest_clock_suspect }`, :4578 `AdminStorageMount { mount_path, observation_state, silent_seconds, used, capacity }` and :4610 `AdminAgentStorageMountsResponse { agent_id, answered_at, cadence_seconds, silence_threshold_seconds, used_metric, capacity_metric, mount_limit, truncated, collection_paused, mounts }`.
- **The tri-state is the answer's centre, and the rule lives in the engine rather than in the handler.** `pub fn mount_observation_state(cadence_seconds: i64, silent_seconds: Option<i64>, silence_threshold_seconds: i64) -> &'static str` (crates/platpulse-server/src/metric_history.rs:2477) answers `"unknown"` when the cadence is 0 or no age was computed, `"silent"` when the age exceeds the threshold, and `"reported"` otherwise; the handler only feeds it, and the unit test `a_mount_is_only_called_silent_against_a_rhythm_it_has` states the boundary cases including a negative age (a Report whose `observed_at` leads `answeredAt` is still `reported`, never a negative silence). `silent_seconds` is present **only when a cadence was measured and collection is not paused**, so neither an unmeasured cadence nor a pause ever turns an age into a verdict — the age stays visible through `latestObservedAt` and `latestDelaySeconds` instead. `collection_paused` states the second case in the answer itself: it is `state.capacity().status().protected`, and while it is true every path is `unknown` because the Server is holding optional history back, not because the Agent stopped reporting. `silence_threshold_seconds` is `gap_threshold_seconds(cadence)` (:4877) and `0` when the cadence is `0`, whose doc says: "The silence that means 'this path is no longer being reported': three cadences of the Agent's measured cadence, with the cadence a silence is judged against capped at five minutes, and never less than two minutes; 0 when the cadence is unknown. No silence is ever excused by a cadence nobody could configure." (:4620-4625).
- The list is ordered by the Server, newest observation first and then by the path (:4940 `storage_series` uses `sample_timing` :714 for `latestDelaySeconds`/`latestClockSuspect`), so the order a client renders is the order the Server decided and a truncation is never the storage engine's slice. The order is decided twice for a reason: each side's read comes back ordered by the index, and `merge_mount_coverage` re-establishes the same order after merging the two sides by path, then cuts the merged list at `MOUNT_COVERAGE_LIMIT` — so the bound is a property of the answer and not of either read, and a ledger whose two metrics disagree cannot answer more paths than it declares (unit test `the_merged_mount_list_is_cut_at_the_bound_it_states`).
- The generated client carries it unchanged: platpulse-web/src/api/generated/types.gen.ts:86 `AdminAgentStorageMountsResponse`, :708 `AdminStorageMount`, :749 `AdminStorageSeries`, and `adminAgentStorageMounts` in platpulse-web/src/api/generated/sdk.gen.ts:178.

## DECISIONS

- **The list is the ledger, not an inventory.** No new table and no new collection: `host_metric_series_state` already holds one row per path ever observed, so #216 answers from it and reuses #215's storage rather than widening ingestion. The one schema change is the index that lets the answer be a limit instead of a sort.
- **Bounded with a stated truncation.** `MOUNT_COVERAGE_LIMIT = 256` and `truncated` are both in the answer, because a bounded list that does not say it is bounded hides mounts. The bound is derived from the Report bound (`2 × MAX_HOST_MOUNTS`), so it is a stated relationship rather than a number chosen by taste, and the bound is enforced on the answer rather than trusted from either read: both sides are read with it from one snapshot and `merge_mount_coverage` cuts the merged list at it in the same order (crates/platpulse-server/src/http/admin.rs:4853-4872, the cut itself in crates/platpulse-server/src/metric_history.rs:2520-2551). The Server's own contract would keep the union equal to the path set — one Report writes both sides of a path together (crates/platpulse-server/src/http/report_ingestion.rs:855-872) — but the answer no longer depends on that being true, which is what `the_merged_mount_list_is_cut_at_the_bound_it_states` pins.
- **The Server decides the order.** `last_observed_at DESC, dimension ASC` is what the index is built for and what makes a limit falling between two paths observed at the same instant deterministic (`two_paths_observed_at_one_instant_are_ordered_by_the_path`, crates/platpulse-server/src/metric_history.rs:4396).
- **A cadence nobody could measure silences nothing.** `cadenceSeconds == 0` answers `observationState: "unknown"`, `silenceThresholdSeconds: 0` and `silentSeconds: null`: an age is not a verdict, and the panel says exactly that instead of rendering `0` as a reading. This is the same rule the rest of the product follows for last-good age. A pause is answered the same way but for a different reason, and the answer says which one: `collectionPaused` is true while low-space protection is holding optional history back, so the panel names the Server's pause rather than the Agent's silence.
- **The silence rule is the engine's own threshold, described precisely.** The first draft's copy ("three measured cadences") was only true between 40 and 300 seconds of cadence; the shipped sentence names the cap and the floor, so the UI cannot promise a rule `gap_threshold_seconds` does not implement (crates/platpulse-server/src/http/admin.rs:4620-4625, platpulse-web/src/storageMounts.ts:130-132).
- **The cadence is the rhythm the Agent is keeping now, not the fastest it ever kept.** `current_cadence_seconds` (crates/platpulse-server/src/metric_history.rs) trusts the newest gap only when the gap before it agrees within `CADENCE_AGREEMENT_FACTOR = 2` and answers 0 (unknown) otherwise, while the range reader keeps #215's `observed_cadence_seconds` (the fastest gap in the window), because a window's summary is about the window. The first draft took the fastest gap of the newest sixteen samples, so a legal `collection_interval` change from 5s to 300s kept answering cadence 5 — and therefore a 120s threshold — until sixteen slow samples had displaced the fast ones: a path that was still reporting every 300s would have been called silent for up to ~75 minutes after the change.
- **The three reads are one snapshot.** `load_mount_coverage` runs both coverage reads and the cadence read inside the transaction the handler opened, so the two sides and the cadence cannot come from three different moments of a ledger ingestion is writing to; `load_host_metric_coverage` and `load_observed_cadence` are generic over `sqlx::Executor`, so the same SQL serves the pool and a transaction. The Server's single write connection (crates/platpulse-server/src/database.rs:29, exclusive locking at :491) already serializes writes, but the guarantee is the transaction and not the pool size.
- **A pause is not a silence, and the handler says so from the capacity state it already holds.** `state.capacity().status().protected` is read for every answer: while it is true no path is judged, every state is `unknown`, and `collectionPaused` tells the client why. The pause test needs a **measured** cadence to be worth anything — the pre-existing pause test had a single observation, so the cadence was unmeasurable and the defect was masked — so `a_pause_is_not_a_silence_while_the_agent_keeps_its_rhythm` establishes a 600s rhythm first, asserts the path is silent while reporting, then pauses collection and asserts the same path is `unknown` with its last reading intact, and resumes to see it silent again.
- **A mount path is compared literally and never normalized.** The typed control stays (platpulse-web/src/pages/metricHistoryPanel.tsx:752): the list offers the paths that hold stored evidence, and a path that was never stored is still asked with its original spelling, because the Server compares the path as bytes.
- **No identity is invented for a path.** The mount object's key set is asserted (`["capacity", "mountPath", "observationState", "silentSeconds", "used"]`), the DTO names no device, and the same path on another machine is by contract indistinguishable — the honest answer, since the Agent reports a path and not a filesystem identity.
- **A released newest reading is unknown with its boundary, not a missing path.** The ledger drives the list and the raw sample is joined by `observed_at`, so retention releasing a reading removes the value and keeps the series, its counts and its `releasedBefore`.
- **The card keeps the standard responsive shape.** The table uses the repo's `data-stack` + `data-label` card layout below 47.9rem and a local scroll region above it (platpulse-web/src/pages/AdminBackups.tsx:104, platpulse-web/src/pages/AdminAudit.tsx:225), so five viewports and both themes are covered by the existing layout rather than by a special case.
- **The list follows the Agent's own signals.** An Agent signal already refreshes that Agent's Host history (`applyAdminInvalidation`, platpulse-web/src/api/admin.ts:1715); the mount list is the same stored evidence, so it is registered there too rather than left to a focus refetch.
- **The list is a read.** No control in the panel writes, retries ingestion, or clears evidence; the only interactive element per row reads that path's series.

## Not delivered, and what is open

- **No device identity, by design.** The list names paths, not filesystems: a mount that moves to another device appears as one series ending and another beginning, which is true rather than a stable identity the Agent never reported. A path that changed meaning on the same machine is indistinguishable from a continued one — the boundary Story 52 states and this ticket keeps.
- **The list is per Agent, not per fleet.** There is no route that answers the mount paths of every Agent at once; cross-subject queries are #220/#221's subject, and the ledger read here is deliberately scoped to one Agent.
- **The Node detail page keeps the typed control.** The list is the Agent's evidence and lives on the Agent page; a Node page reaches it through the Agent link it already renders (platpulse-web/src/pages/AdminNodes.tsx:771), and a Node's own Host panel still asks for the path by name. Putting a per-Agent list on a Node page would suggest the paths belong to the Node.
- **Truncation needs three Reports to observe end to end.** One Report carries at most 128 paths, so more than 256 paths — the only way to see `truncated` — takes at least three Reports; both the HTTP test and the acceptance case plant exactly that, and the unit test states the same rule at a limit of two.
- **The pause ledger still has no retention target.** `capacity_skipped_series` is never deleted, so its evidence grows by one row per interval per series — now per mount path as well. Unchanged from #215 and still a stated boundary of §11.6.
- **Silence is judged against the Agent's Host cadence, not per path.** An Agent that keeps reporting its Host while one mount disappears for other reasons is answered silent only once the measured cadence has passed three times over; a finer rule would need evidence the Agent does not send.
