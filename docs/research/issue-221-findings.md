# Issue #221 findings — 基于记录关系的跨主体历史联查 (cross-subject history from the relations the Server recorded)

**#221** is the relationship ticket of the #202 roadmap (stage 3, ticket 19/23; blocked-by #219 and #220, both merged). It answers stories 60, 61, 65, 66 and 68 of the #202 story set — related subjects may only be named from recorded relationship evidence and must be labelled as such (60), an unrecorded association is `unknown` and is never back-filled from the key a Node carries now (61), a Node and a Validator are related only through Server-recorded Node Validator Link intervals (65), those intervals are correspondence times rather than on-chain key-change times and prove no continuous protection (66), and a shared Validator identity/history survives a Node purge while the deleted Node association stays clearly unavailable (68) — plus the cross-subject acceptance rules of stories 1-8/80-81 (safe DTOs, the Server as the trust boundary, Unknown != 0, the WebUI matrix, no jsdom/CSS-zoom fakes).

What this ticket adds is not a second evidence surface. The Server already recorded, at every accepted Report and every completed Node Transfer, **which Agent and which Network a Node belonged to** — it simply wrote the *current* value onto the Node row and threw the history away. #221 writes that history down from the moment the migration lands, and lets the #220 investigation window read it. Nothing is back-filled, and no existing evidence is re-attributed.

Two rules govern every judgement below: **the record is the Server's own writing** (so it is quoted as such, never presented as an on-chain fact), and **an unrecorded stretch is unknown, never inherited** from the value the Node carries now.

Everything below is the working tree as it stands, read at the line references given, with the runs in VERIFICATION as the authority for the claims it makes about behaviour.

## SERVER — the record itself (crates/platpulse-server/migrations/0071_node_relationship_intervals.sql, crates/platpulse-server/src/relationships.rs)

1. **One new table, and it is created empty and prospective only.** `node_relationship_intervals` holds `interval_id` (TEXT primary key, `uuid::Uuid::new_v4()`), `node_id` (TEXT NOT NULL REFERENCES nodes(node_id)), `relation_kind` (`CHECK (relation_kind IN ('agent','network'))`), `related_key` (TEXT NOT NULL), `origin` (`CHECK (origin IN ('enrollment','transfer','network_change'))`), `valid_from` (TEXT NOT NULL), `valid_until` (TEXT, nullable = still held) and `recorded_at` (TEXT NOT NULL), with `CHECK (valid_until IS NULL OR valid_until > valid_from)`. Timestamps are RFC 3339 UTC at second precision, the project-wide wire idiom, so lexicographic text comparison is chronology. Two indexes carry the reads: `node_relationship_intervals_node_idx` on `(node_id, relation_kind, valid_from, valid_until)` and `node_relationship_intervals_related_idx` on `(relation_kind, related_key, valid_from, valid_until)`. Two triggers — `node_relationship_intervals_no_overlap_insert` and `..._no_overlap_update` — refuse an overlapping interval for the same Node and relation kind with `RAISE(ABORT, 'node_relationship_interval_overlap')`, comparing `COALESCE(valid_until, '9999-12-31T23:59:59Z')`, so "the Node had two Agents at once" is impossible at the storage boundary rather than by convention. The migration header states the contract in the file itself: the table is created **empty**, recording is **prospective**, and **nothing is back-filled** — the Agent and Network keys already on `nodes` are the *current* values and are never turned into history. The same header explains why no separate Host relation row exists: a Host observation is collected once per Agent (`host_metrics` answers about `agent_id`), so a Host alert subject keys on the Agent, and a parallel Host relation would be a second description of one fact.
2. **The schema is version 71 and the table is required.** `SERVER_SCHEMA_VERSION: i64 = 71` (crates/platpulse-server/src/database.rs, was 70) and `REQUIRED_TABLES` gained `"node_relationship_intervals"` after `"node_state_series_state"`, so a database without it is refused rather than silently read as empty.
3. **The vocabulary is named, not inlined.** crates/platpulse-server/src/relationships.rs defines `RELATION_AGENT` = `"agent"`, `RELATION_NETWORK` = `"network"`, `ORIGIN_ENROLLMENT` = `"enrollment"`, `ORIGIN_TRANSFER` = `"transfer"`, `ORIGIN_NETWORK_CHANGE` = `"network_change"`, `RELATION_KINDS` = `[agent, network]` and `INTERVAL_COLUMNS` = `"interval_id, relation_kind, related_key, origin, valid_from, valid_until, recorded_at"`; `pub struct RelationshipInterval { interval_id, relation_kind, related_key, origin, valid_from: String, valid_until: Option<String>, recorded_at }` derives Debug/Clone/FromRow and carries `valid_from_at()`, `valid_until_at()` and `open()`.
4. **The write is idempotent and the instant is the Server's receipt, not the Report's clock.** `pub(crate) async fn record_relations(connection: &mut SqliteConnection, node_id: &str, agent_key: &str, network_key: &str, recorded_at: &str) -> Result<Vec<&'static str>, sqlx::Error>` (crates/platpulse-server/src/relationships.rs:215-272) sets `valid_from = recorded_at = now_text`, the instant the Server accepted the Report — deliberately **not** the Report's `generated_at`, because the record is the Server's own act of writing and a back-dated Agent clock would forge the record. Its three cases: the same key ⇒ **no write at all** (a Report that changes nothing does not create an interval, so the record stays a record of change); a changed key ⇒ the old open interval is closed with `valid_until = close_instant(valid_from, recorded_at)` and a new interval opens with origin `transfer` / `network_change`; no open interval for the kind ⇒ one opens with origin `enrollment`. Both kinds are recorded together, so an enrollment writes the Agent row and the Network row in the same transaction as the Report's receipt. `fn close_instant(valid_from, recorded_at)` (crates/platpulse-server/src/relationships.rs:324) returns `recorded_at` when it is later than `valid_from`, else `valid_from + 1s` — because a change inside the same second would otherwise produce `valid_until == valid_from`, which the table's own CHECK forbids and which would describe a zero-length stretch as if it were a border.
5. **It is written where the change actually happens.** In crates/platpulse-server/src/http/report_ingestion.rs, `resolve_node_transfer` (from :1731) calls `crate::relationships::record_relations(tx, &node.node_id.to_string(), reporting_agent, &registered_key, now_text).await?` right after the `UPDATE component_status SET agent_id = ? WHERE node_id = ?` that performs the handover (crates/platpulse-server/src/http/report_ingestion.rs:1874-1883), inside the same transaction that completes the Transfer; and the accepted-inventory upsert loop (crates/platpulse-server/src/http/report_ingestion.rs:2581, after `INSERT INTO nodes ... ON CONFLICT(node_id) DO UPDATE`) calls it with `(&auth.agent_id, node.network_key.as_str(), &now_text)`, whose error path answers 503 `unavailable` / "Server database is unavailable". A declaration by an Agent that does not own the Node is routed to `ownership_mismatches` / `rejected_nodes` (crates/platpulse-server/src/http/report_ingestion.rs:2485-2516) and **never reaches recording**, so a rejected Report cannot write history. Note that `resolve_node_transfer` requires the report's *own* Node observation to carry a successful Network Identity probe (`chain.network_identity.status == Ok`, :1810) whose `genesis_hash`/`chain_id`/`p2p_network_id`/`address_hrp` agree with the registered network (crates/platpulse-server/src/http/report_ingestion.rs:1816-1827) — otherwise the Transfer resolves as `Unverified` (:1812) or `IdentityMismatch` (:1828) and no handover is recorded.
6. **Reading is a pure derivation over rows, and it is where "unknown" is computed.** `load_intervals(pool, node_id)` (crates/platpulse-server/src/relationships.rs:300) reads every interval for the Node ordered by `valid_from` — the whole record, deliberately without a window predicate, because a window-bounded read cannot tell "the Server has never recorded this" from "the Server recorded this before the window opened". `pub struct RelationSpan { related_key, origin, from, to, continues }` (crates/platpulse-server/src/relationships.rs:77-87) is one clipped stretch; `pub struct RelationView { kind, spans, unknown_spans, recorded_from, recorded }` (crates/platpulse-server/src/relationships.rs:91-104) is the window's view of one relation kind; `spans` are the interval edges **clipped to the window** and two adjacent intervals that name the same key are merged into one span, because "the Agent did not change" is what the reader is being told; `unknown_spans` is the window minus every span, and `recorded_from` is the earliest instant ever recorded **even when it lies outside the window** — which is what lets the answer distinguish "the Server has never recorded this" from "the Server was already recording before this window opened". `RecordedRelations::derive(rows: Vec<RelationshipInterval>, window_from, window_to)` (crates/platpulse-server/src/relationships.rs:168) documents exactly that in the source: "Rows outside the window still contribute their recorded_from, so the Reader can say when recording began." Presentation helpers live here too — `relation_kind_label` ("Reporting Agent"/"Network", crates/platpulse-server/src/relationships.rs:367), `related_subject_label` ("the reporting Agent"/"the Network"), `origin_label`, `describe_span` — so the prose the Reader serves is written once, next to the rows it describes. The review's Standards axis deleted the speculative half of this API — `load_intervals_for_window`, `RecordedRelations::current_key` and `::current_origin`, `RelationView::key_at` and the `recorded_in_window` counter, all described here before that deletion — and the deletion was not cosmetic: the window-bounded read had also been handed to `derive` in `investigate_node`, so a Node whose rows all lay outside the window read as a Node the Server had never recorded (see REVIEW DISPOSITION).
7. **Recording is proven by unit tests on the pure parts, not only end to end.** `cargo test -p platpulse-server --lib relationships` runs seven cases: `no_recorded_interval_leaves_the_whole_window_unknown`, `a_relation_that_changed_leaves_the_earlier_stretch_with_its_old_subject`, `recording_that_starts_inside_the_window_leaves_the_earlier_part_unknown`, `adjacent_intervals_with_the_same_subject_merge_into_one_span`, `an_interval_outside_the_window_covers_nothing_but_still_dates_recording`, `a_change_in_the_same_second_does_not_collapse_the_interval` and `describing_a_span_stays_about_the_server_record` — the last one asserting that the wording attributes the record to the Server rather than to the world.

## SERVER — how the investigation answer reads it (crates/platpulse-server/src/investigation.rs)

8. **The record is the first family, and `SOURCE_ORDER` is now seven long.** `pub const SOURCE_RELATIONSHIPS: &str = "relationships";` and `pub const SOURCE_ORDER: [&str; 7] = [SOURCE_RELATIONSHIPS, SOURCE_NODE_METRICS, SOURCE_NODE_STATE, SOURCE_HOST_METRICS, SOURCE_PEERS, SOURCE_INCIDENTS, SOURCE_VALIDATOR];` (crates/platpulse-server/src/investigation.rs:508-516). It is first because it is what every other family's attribution rests on: a Reader that is told about an Agent's evidence before being told whether the Server recorded that Agent in this window is being told about an attribution it cannot check. The family answers `subjectKind` `node` with the Node id as its `subject`, and its time basis is the new `TimeBasis::ServerRecord` (`"server_record"` / "Server record time", crates/platpulse-server/src/investigation.rs:385) — not the observation clock of anything measured.
9. **A stretch the Server never recorded is a boundary, not silence.** `BoundaryKind::RelationshipUnknown` (`"relationship_unknown"` / `"No recorded relationship"`, crates/platpulse-server/src/investigation.rs:428) is attached over every unrecorded stretch inside the window by `uncovered_record_boundary` (:1274-1294), and over an unrecorded stretch of a *relation* by `uncovered_relation_boundary` (:1301). Each carries the Server's own sentence, in two variants chosen by whether the record began before the window: "the Server has never recorded which Agent or Network this Node belonged to, and recording is prospective, so this stretch is not attributed to the relations the Node has now", or "the Server recorded nothing about which Agent or Network this Node belonged to from <a> to <b>, so this stretch is not attributed to the relations it had before or after it". `other_subject_boundary` (:1253-1265) says the mirrored thing for a family that answers about a subject: "the Server recorded <relation> <key> for this stretch, so this family holds no evidence attributed to <subject> it answers about". Coverage therefore degrades to `partial` honestly: #220 already answered `partial` for the pre-enablement stretch, and the record adds an explained boundary rather than a new verdict.
10. **The family is derived from the whole record, never from a window-bounded slice.** `investigate_node` reads `let intervals = load_intervals(pool, &node.node_id).await?` and derives `RecordedRelations::derive(intervals.clone(), window.from, window.to)`, passing `&intervals` on to `relationships_source`. This is a deliberate correction: it was first written as a window-bounded load, and the defect that produced (an interval opening in the request's own second is excluded by `valid_from < to`, so the family printed the never-recorded wording while holding rows the Reader needed, and lost the record's own start) is exactly what the "read the record, clip in the reader" split prevents. `relationships_source` (crates/platpulse-server/src/investigation.rs:2745-2849) is consequently a plain, non-fallible function over `&[RelationshipInterval]` with no query of its own: ledger `first_observed_at` = the earliest `valid_from` clamped down by `ctx.first_seen_at` (crates/platpulse-server/src/investigation.rs:2754-2759), `last_observed_at` = the furthest `valid_until` over open-ended rows ending at the window end (crates/platpulse-server/src/investigation.rs:2760-2763), `last_received_at` = the newest `recorded_at` (crates/platpulse-server/src/investigation.rs:2764-2784) — three different instants that mean three different things (when recording began, how far the record reaches, when the Server last wrote one down), which is why the family's ledger is worth reading rather than decorative. Its notes state the record's nature and then the record itself (crates/platpulse-server/src/investigation.rs:2787-2792, per-kind spans at :2799-2805), and its single grain is `GRAIN_RECORDED_INTERVAL` = `"recorded_interval"` (crates/platpulse-server/src/investigation.rs:2830-2847) with `pointCount` = recorded spans and `sampleCount` counting only the intervals that actually overlap the window (:2812-2827) — a row read solely for the record's own start is not a sample of this window. `cadenceSeconds` and `longestGapSeconds` are left null on purpose: the distance between two records is not a missing observation and no interruption can be proven from it.
11. **Attribution is a field, not a footnote.** `pub struct InvestigationRelatedSubjectResponse { subject_kind, subject, role, basis, basis_label, from, to, detail }` is carried by every source (`related_subjects: Vec<...>`, empty when nothing was recorded as related), with `SUBJECT_ROLE_SOURCE` = `"source"` / `SUBJECT_ROLE_RELATED` = `"related"` and the bases `BASIS_RECORDED_RELATIONSHIP` = `"recorded_relationship"` / `BASIS_RECORDED_VALIDATOR_LINK` = `"recorded_validator_link"` (crates/platpulse-server/src/investigation.rs:519-528). `SourceBuilder::attribute_relation` marks the stretches the record gave to another subject and the family's own; `attribute_own_relation` does the same for `host_metrics` and additionally raises `other_subject_boundary` where the record gives the stretch to a different Agent, so the Host family **never credits another Agent's Host records to the Agent it is answering about**. The generated TypeScript type makes `relatedSubjects` required, which is the point: a client cannot render an investigation answer without deciding what to do about attribution.
12. **The Incident family counts a related subject's Incidents only inside the stretch the Server held that relation for.** After the Node's own Incidents, `incidents_source` walks `relations.spans()` for `RELATION_AGENT` and, per recorded span, counts Incidents on `agent` and `host` subjects **inside that span only** (crates/platpulse-server/src/investigation.rs:2957), adding a grain note ("<n> of these Incidents are on subjects recorded as related to this Node, inside the stretches the Server held that relation for", crates/platpulse-server/src/investigation.rs:3041) and one answer path per related subject whose own note is "only the stretch the Server recorded this relation for is asked, not the whole window" (crates/platpulse-server/src/investigation.rs:3085) — so a Reader following the path cannot accidentally widen it back to the window and re-import the Incidents of a stretch the record does not attribute to that subject. No answer path is invented for the Networks: the Alert catalog holds no rule on a Network subject (only the enum arm exists), so a recorded Network relation can never produce an Incident, and the family says that in a note rather than drawing a row the catalog cannot produce. Because the relation record need not cover the whole window, the family also says when its own related-subject count is zero for that reason: "no Incident on a related subject is counted for this window: the record of this Node's relations does not cover all of it, and a stretch with no recorded relation is a gap in the record rather than an absence of Incidents" (crates/platpulse-server/src/investigation.rs:3053), while the Node's own Incidents stay counted over the whole window because that count rests on the Server's own history rather than on the record (see REVIEW DISPOSITION). The old "Incidents on the reporting Agent" path was removed — it was the one that attributed a stretch's Incidents to whichever Agent the Node carries *now*.
13. **A Validator link is served as the correspondence it is (stories 65 and 66).** `validator_source` reads `node_validator_links` in the window (`valid_from < ? AND (valid_until IS NULL OR valid_until > ?)`, ordered newest first) and, per link, pushes a `relatedSubjects` entry with `subjectKind` `validator`, `role` `related` and basis `recorded_validator_link`/`Recorded Validator Link`, with the stretch clipped by `clipped_span`. Its wording is the ticket's story 66 in a sentence — `link_description` (crates/platpulse-server/src/investigation.rs:3196) says "the Server recorded <validator> (<role|unassigned>, <origin>) as linked from <t> to <until>", or "… as linked from <t> and still holds it" — and the family carries the note (crates/platpulse-server/src/investigation.rs:3314) "a Validator link is the Server's own record of when it began and stopped reading a Validator for this Node: its edges are correspondence times rather than key-change times, and it proves no continuous protection between them". The word "linked" is doing load-bearing work: an interval that opens when the Server started reading a Validator and closes when it stopped is not evidence that the on-chain key changed, nor that the Validator protected the Node continuously in between.
14. **No new endpoint, and that is a decision rather than an omission.** docs/design/webui.md:1329 already fixed the rule for this panel — "The panel must not invent a link, must not turn the investigation itself into a second answer surface, and a source that sent no answer path reads as a Server statement rather than as a broken link" — and the record family is precisely the case it was written for: its evidence is *inside* this answer, so an endpoint would be a second surface describing the same rows, and no existing route lists Node relations. The family therefore sends no answer path and says why in its own note: the recorded relations are the Server's own writing and are read in this answer, "which is the only place the Server serves them, so this family points at no other path" (crates/platpulse-server/src/investigation.rs:2791). The alternative — reusing `/api/admin/v1/nodes/{node_id}` as a link — would have pointed a Reader at current values as if they were the window's, which is the exact confusion story 61 forbids. The #220 invariant "every non-unsupported source sends an answer path" was narrowed **by source key** in crates/platpulse-server/tests/node_investigation.rs for this one family, so the invariant still holds for the other six.
15. **Story 68 is enforced at the purge boundary, in counts and in rows.** `NodePurgeCounts` gained `pub relationship_intervals: i64`, honoured by `add`, `total_owned_rows()` and `measure()` (crates/platpulse-server/src/node_purge.rs, via `count(connection, "node_relationship_intervals", &node_id)`), and `remove()` deletes `node_relationship_intervals` in the same run as the Node (`DELETE FROM nodes WHERE node_id = ?`) — after `node_validator_identity_status`, `node_validator_links` and `node_transfers` — while the Agent, Host, Network, Validator and Incident history those rows pointed at is untouched. The purge's own doc comment says so: the relationship intervals go with the Node while shared history survives. The wire DTO had to learn the count as well (`AdminNodePurgeCounts.relationship_intervals` at crates/platpulse-server/src/http/admin.rs:432, mapped in `fn node_purge_counts` at :509), because a purge preview that hides a row it is about to delete is the same failure as one that deletes a row it did not count.

## WEB — the readable half

16. **The list is rendered from the Server's words, with no client vocabulary of its own.** `RelatedSubjectTable` (platpulse-web/src/pages/AdminNodeInvestigation.tsx, immediately before `CollectorTable`) renders `data-slot="investigation-related-subjects"` — columns Subject, Read as, Recorded basis, Stretch, What the record says — directly under the boundary table, and the empty state `data-slot="investigation-no-related-subject"` says "The Server records no subject related to this family inside this window. Attribution is only ever made from the Server's own record, so nothing here is credited to a subject the record does not name." The empty state deliberately does **not** claim every point is the family's own subject: a family can carry a `relationship_unknown` boundary over the stretch it cannot attribute, and the two messages must not contradict each other.
17. **`relationship_unknown` needed no client code, and that is the design test.** Boundary rows render `boundary.kindLabel` straight from the Server, so `No recorded relationship` appears without a new client-side kind list, and `relatedSubjectKindLabel` (platpulse-web/src/nodeInvestigation.ts, beside `timeBasisNote`) only maps the four kinds the Server records (`agent`/`host`/`network`/`validator`) and returns an unknown kind **as the Server wrote it** rather than inventing a label. The coverage card's claim changed from six families to seven ("All seven families are listed, whether or not each holds evidence"), because the list of families is a claim about the answer and would otherwise have gone stale silently.
18. **The wire field is required, so every fixture had to answer it.** Adding `relatedSubjects` to `InvestigationSourceResponse` made the generated TypeScript property required, which broke the type-check in exactly one place (the `source()` factory in platpulse-web/src/nodeInvestigation.test.ts). The page's own test fixture builds an untyped object literal, so it kept type-checking and failed **at runtime** with `Cannot read properties of undefined (reading 'length')` until `relatedSubjects: []` was added to `sourceFixture` — a reminder that a required field added to a generated DTO is only half-enforced by `tsc` when a fixture is not typed as the DTO.

## REVIEW DISPOSITION

Two-axis review of this change (Standards and Spec, cliproxyapi/gpt-6.1-sol at high reasoning effort). Every finding is dispositioned below; the code edits it produced are in the same commit as the feature.

### Spec — four findings

| # | Finding | Disposition |
|---|---|---|
| P1 | Validator evidence was not limited to the Link intervals (issue story 65): a snapshot row matched every overlapping link of that Validator, and each link's trend answer path asked for the whole window | **Accepted, fixed in two places.** The snapshot join now carries the link's own correspondence: `AND s.received_at >= l.valid_from AND (l.valid_until IS NULL OR s.received_at < l.valid_until)` (`crates/platpulse-server/src/investigation.rs:3160`, and the horizon count at `crates/platpulse-server/src/investigation.rs:3146`). `received_at` is the Server's own receipt clock — the clock the link's edges are written from — so a day read under an earlier link, or before any link existed, is not credited to this one, and two links to the same Validator inside one window cannot each claim the same stored day. Each link's answer path is now asked for that link's own clipped stretch and says so: "only the stretch the Server recorded this link for is asked, not the whole window" (`crates/platpulse-server/src/investigation.rs:3345`). Regression test `a_recorded_link_answers_only_for_the_stretch_the_server_held_it` in `crates/platpulse-server/tests/node_investigation.rs`; reverting only the SQL bound reproduces the reviewer's double count (three stored days reported as `pointCount` 3 / `sampleCount` 6 instead of 2 / 2) |
| P2.2 | A Node with no recorded Link read as a known absence | **Accepted, fixed.** The empty-record branch now also states "the Server holds no link interval for this Node inside this window, and holding no record of a link is not evidence that the Node had none: this family states what the Server recorded and never what the current link implies about the past" (`crates/platpulse-server/src/investigation.rs:3257`). The pre-existing unsupported reason is unchanged, because both sentences are true and the e2e flow asserts the second |
| P2.3 | The Incident family did not disclose that the relation record need not cover the whole window | **Partially accepted — disclosure without a coverage change.** The family's own subject is the Node and the Server evaluates Node Incidents over the whole window from its own history, so the completeness of that count does not rest on the relation record at all; marking the family Partial would misattribute another card's gap. Instead, when the family counts no related-subject Incident while the record does not cover the window, it names the gap: "no Incident on a related subject is counted for this window: the record of this Node's relations does not cover all of it, and a stretch with no recorded relation is a gap in the record rather than an absence of Incidents" (`crates/platpulse-server/src/investigation.rs:3053`) |
| P2.4 | The one-second tie-break in `close_instant` silently shifts attribution | **Dispositioned, behaviour kept.** `crates/platpulse-server/src/relationships.rs:324` closes the earlier interval at `valid_from + 1s` when the change arrives in the same second. The tie-break is bounded, never moves a closure backwards and never rewrites a written interval, so the record stays append-only and the Server never back-fills a relation it did not observe; a same-second change costs at most one second of attribution, which is the resolution its own clock records in. The doc comment was extended to say exactly that, and `a_change_in_the_same_second_does_not_collapse_the_interval` covers it |

## DESIGN DECISIONS worth keeping

- **Record, then clip — never clip, then record.** The write path never consults a window, and the read path never filters before deriving; the ledger and the wording both depend on rows that lie outside the window.
- **The record's instant is the Server's receipt.** Both `valid_from` and `recorded_at` come from the Server's own clock at receipt, so an Agent cannot back-date a relation by lying about `generated_at`.
- **`relatedSubjects` is a field rather than a note.** Prose can explain a judgement; only a field can be asserted on, rendered in one column per subject, and re-checked by a client that must not re-derive attribution itself.
- **Unknown beats inherited.** Where the record is silent the answer says `relationship_unknown` and degrades coverage, even though the Node row carries a plausible current value — because the plausible value is exactly the one that would be wrong for the earlier stretch.
- **No second answer surface.** The record is served inside the investigation answer and nowhere else, so there is no second place that could disagree with it.
- **Changed in the same second.** `close_instant` keeps the interval positive (`valid_from + 1s`), trading a one-second inaccuracy for an honest non-zero stretch and a CHECK the storage can enforce.
- **A link's evidence is bounded by the link itself.** A stored Validator day is credited to a link only while the Server held that link, read through the same receipt clock the link's own edges are written from, so two links to one Validator inside one window cannot each claim the same day and each trend path asks for the stretch its link was recorded for rather than the whole window.
