# Issue #215 findings — shared Host resource history, stored once for the Agent

**#215** (`feat: 共享 Host 资源历史`) asked for Host resource history that a Node view can show without owning a copy of it: the Agent observes its machine once, the Server stores that observation once, and every Node that Agent reports reads the same series. The migration this ticket added states its place in the sequence itself — parent **#202**, user stories 46, 50, 51, 52 and 59, design §11.4, §11.6 and §6 (crates/platpulse-server/migrations/0068_host_metric_history.sql:1-12). It follows #213 (the trustworthy 24 hour raw window, the `raw_metric_sample` retention family and the Node series ledger) and #214 (the 1-minute and 5-minute tiers, the 30 day horizon and the range read that pages under one budget), both of which were already in the tree: the point of this ticket is that the second scope is answered by the same engine, not by a second history that drifts from the first.

Everything below is the working tree as it stands, at the line references it was read at. Nothing in it is a plan, and nothing in it is a claim about a run this documentation pass did not perform (see VERIFICATION).

## SERVER (the real gaps)

1. **Eight of the ten collected Host quantities had no history at all.** crates/platpulse-server/migrations/0041_node_metric_history.sql:26-40 created `host_metric_samples` with `metric TEXT NOT NULL CHECK (metric IN ('network_rx_bytes_per_sec', 'network_tx_bytes_per_sec'))`, `PRIMARY KEY (agent_id, metric, observed_at)` and no dimension column. Host CPU, memory used, memory total, the three load averages and the two per-mount storage quantities existed in the Report but nowhere as a series, so no retention bound, no ledger, no bucket tier and no Owner answer could exist for them. The only surface that ever served a Host row to a human was the Public Node Detail trend, which reads the two network rates (crates/platpulse-server/src/http/public.rs:1436).
2. **The series key had no room for a second mount of one Host.** With `PRIMARY KEY (agent_id, metric, observed_at)` a single Report stating `/data` and `/mnt/data` at the same instant wrote one row and silently replaced the other. The rebuild comment says exactly this — the mount path, not the metric name, is what tells the two storage series apart (crates/platpulse-server/migrations/0068_host_metric_history.sql:20-24, :58-62).
3. **There was no Host series ledger.** Only `node_metric_series_state` existed (crates/platpulse-server/migrations/0066_node_metric_history.sql). Without a Host twin, #213's counting rules (crates/platpulse-server/src/metric_history.rs:1124 `classify_delivery`) and the release stamp could not be applied to Host evidence, so a Host series could not say what it had observed once its samples expired — a stretch the Server had counted and a stretch it had never seen were both simply absent rows.
4. **There was no Host aggregate tier.** The bucket table `node_metric_aggregates` (crates/platpulse-server/migrations/0067_node_metric_aggregates.sql) is Node-scoped, so Host history could only be answered inside the raw window: days 2 to 30 had no Host evidence behind them at all.
5. **The pause ledger merged the mounts of one Host.** `capacity_skipped_series` (created at crates/platpulse-server/migrations/0065_capacity_protection.sql:59) was keyed `(interval_id, scope_kind, scope_key, metric)`, so a low-space pause that skipped rows for two mount paths of one Agent counted them as one series with one number — the very losses the ledgers exist to make visible, added together and unseparable.
6. **The Host raw cleanup batch was sized for the two-rate era.** The Host bound was 128 rows per pass while a Report was about to state `8 + 2 x mounts` Host samples on every accepted report. A batch below one Report's own arrival lets expiry lag its writes, and a lagging expiry is the backlog that ends in the low-space pause the same subsystem exists to avoid (crates/platpulse-server/src/retention.rs:196-201).
7. **There was no Owner read path for Host history.** The only metric-history route was crates/platpulse-server/src/http/admin.rs:4537 `GET /api/admin/v1/nodes/{node_id}/metric-history`, whose identity is `scope_kind: "node"` (crates/platpulse-server/src/http/admin.rs:4605-4608) and which answers that Node's own Process series. Nothing could ask the Server for the series the Agent collected.
8. **Nothing in the WebUI could ask for Host history.** docs/design/webui.md §15.16 described one Node panel over the five Node Process series, and the Agent detail page had no Host section at all.

The constants and shapes this ticket is built on: crates/platpulse-server/src/metric_history.rs:83 `MAX_HOST_MOUNTS: usize = 128` (the same bound as crates/platpulse-core/src/observation.rs:73), :86 `NODE_METRIC_SERIES: [&str; 5]`, :116 `HOST_METRIC_SERIES: [&str; 10]`, :95 `is_node_metric`, :132 `is_host_metric`, :145 `HistorySchema`, :160 `NODE_HISTORY`, :171 `HOST_HISTORY`, :190 `HistorySchema::sql`, :218 `SeriesKey`, :228 `SeriesScope`, :236 `SeriesScope::node`, :249 `SeriesScope::host`; crates/platpulse-server/src/retention.rs:218 `HOST_METRIC_CLEANUP_BATCH: i64 = 512` and :241 `AGGREGATE_CLEANUP_BATCH: i64 = 2048`; crates/platpulse-server/src/database.rs:24 `SERVER_SCHEMA_VERSION: i64 = 68`; the Host series identity is the primary key `(agent_id, metric, dimension, observed_at)` (crates/platpulse-server/migrations/0068_host_metric_history.sql:62). The ten stored Host names are `cpu_percent`, `memory_used_bytes`, `memory_total_bytes`, `load1`, `load5`, `load15`, `network_rx_bytes_per_sec`, `network_tx_bytes_per_sec`, `disk_used_bytes` and `disk_total_bytes` — the last two identified by the mount path they were read from (crates/platpulse-server/src/metric_history.rs:116-131).

## What was added

### Schema, the series key and the shared ledger

- **crates/platpulse-server/migrations/0068_host_metric_history.sql** (193 lines) rebuilds `host_metric_samples`: `agent_id TEXT NOT NULL REFERENCES agents(agent_id) ON DELETE CASCADE`, `metric` with a CHECK over the ten Host names (:44-57), `dimension TEXT NOT NULL DEFAULT '' CHECK (length(dimension) <= 4096)` (:58), `observed_at`/`received_at` canonical RFC 3339 UTC (20 characters), `value REAL NOT NULL CHECK (value >= 0)`, and `PRIMARY KEY (agent_id, metric, dimension, observed_at)` (:62). Retained rows are copied across with an empty dimension and the old table is dropped; both indexes are recreated (`host_metric_samples_recent_idx (agent_id, received_at DESC, metric)`, `host_metric_samples_observed_at_idx (observed_at, agent_id, metric)`).
- The same migration creates **`host_metric_series_state`** (:83-96) as the Node ledger's twin: `(agent_id, metric, dimension)` primary key, `first_observed_at`, `last_observed_at`, `last_received_at`, `observation_count >= 1`, `replayed_count >= 0`, `corrected_count >= 0`, `released_before` defaulting to `1970-01-01T00:00:00Z` with `CHECK (length(released_before) = 20)` and `updated_at`, backfilled from the retained rows with `MIN`/`MAX`/`COUNT` and the newest `received_at` so a series that already had samples does not restart its count at the migration.
- It creates **`host_metric_aggregates`** (:137-153) as the bucket table's twin: `(agent_id, metric, dimension, grain_seconds, bucket_start)` primary key, `grain_seconds IN (60, 300)`, `sample_count >= 1`, `max_value >= min_value`, the first/last observation instants, the newest receipt, `max_gap_seconds` bounded by the grain, and `host_metric_aggregates_expiry_idx (grain_seconds, bucket_start)` for the bounded delete. Its comment states the tier contract and the decision behind it: grain 60 answers `>24h..7d` and grain 300 answers `>7d..30d`, "both tiers guarded by the EXISTING retention families — Host adds no new tier and no new family".
- **`capacity_skipped_series`** is rebuilt with the dimension in its key (:167-176): `PRIMARY KEY (interval_id, scope_kind, scope_key, metric, dimension)`, `dimension TEXT NOT NULL DEFAULT '' CHECK (length(dimension) <= 4096)`, `scope_kind` still CHECKed to `node`/`host`, existing rows copied with an empty dimension and both lookup indexes recreated with the dimension column, so a pause can report each mount path separately and the Node-scoped rows keep the same predicate shape they had.
- **crates/platpulse-server/src/database.rs**: `SERVER_SCHEMA_VERSION: i64 = 68` at :24 (was 67) and `REQUIRED_TABLES` gained `"host_metric_series_state"` and `"host_metric_aggregates"` at :92-93, so a database that predates the migration is refused rather than served without the shared tables.

### One engine, two scopes

- **crates/platpulse-server/src/metric_history.rs:145 `HistorySchema`** is the whole generalization. Its own doc says why: "There is one history engine, not one per scope. A scope differs in exactly three ways: the tables it writes, the column that names its owner (a Node or an Agent), and whether its series identity carries a dimension."
- The two constants are data, not code paths: :160 `NODE_HISTORY` (`node_metric_samples` / `node_metric_aggregates` / `node_metric_series_state`, owner column `node_id`, no dimension) and :171 `HOST_HISTORY` (`host_metric_samples` / `host_metric_aggregates` / `host_metric_series_state`, owner column `agent_id`, dimension present).
- :190 `HistorySchema::sql(&self, template: &str) -> String` renders one statement text for either scope by substituting `{raw}`, `{agg}`, `{ledger}`, `{scope}`, `{dim_column}`, `{dim_bind}` and `{dim_predicate}`, and drops the dimension fragments entirely for a dimensionless scope — so the Node SQL is byte-for-byte what it was and the Host SQL differs only where the identity really differs.
- **crates/platpulse-server/src/metric_history.rs:228 `SeriesScope`** carries the schema, the owner key and a :218 `SeriesKey { metric, dimension }`, built by :236 `SeriesScope::node(node_id, metric)` or :249 `SeriesScope::host(agent_id, metric, dimension)`; :273 `bind_series` and the :290 `SeriesStatement` trait bind owner, metric and dimension in one place, so no call site can bind them in a different order for one scope than for the other.
- Every statement the two scopes share is one rendered template: the ledger upsert (:1219), the stored-value read (:1242), the raw upsert (:1265), the release stamp update (:1299), `AGGREGATE_UPSERT_SQL` (:1318), `BUCKET_GAP_STATE_SQL` (:1321), the bucket envelope and carry (:1418, :1458), `RANGE_SAMPLE_SQL` (:1965), `RANGE_BUCKET_SQL` (:1974), `BUCKET_EVIDENCE_EXISTS_SQL` (:1984), `STRADDLING_MINUTE_LEDGER_SQL` (:2000), `SERIES_LEDGER_SQL` (:2003) and `PAUSE_LOOKUP_SQL` (:2168, which now filters `dimension` as well). The tier boundaries, the silences and the delivery counting #213 and #214 established therefore apply to Host evidence unchanged, and the 1-minute/5-minute handover and the 30 day floor are not re-derived for the second scope.
- The five Node Process series (:86) and the ten Host series (:116) stay separate vocabularies with separate guards: :95 `is_node_metric` and :132 `is_host_metric` are the only two predicates that decide which kind a name is, and neither list is a superset of the other. :132's own doc states the second half of the problem: "The name alone does not identify a series: the two storage series are told apart by the mount path they were read from."

### Accumulation at ingestion: one write per Report, once for the Agent

- **crates/platpulse-server/src/http/report_ingestion.rs:807 `fn host_series_samples(host: &HostObservation) -> Vec<(&'static str, &str, Rfc3339, f64)>`** turns one Report's Host observation into the series samples to store. Its doc (:795-806) states the ownership rule and the honesty rule together: "Host evidence belongs to the Agent, never to a Node of it: one Report states each quantity once and the history stores it once, so six Nodes on two Hosts bill two series sets and no Node owns a copy of its Host's totals (design §11.6, issue #215)"; and "Only quantities the Report actually carried are listed: a component with no latest value states nothing, and a missing reading is not zero."
- The function emits `cpu_percent`; `memory_used_bytes` and `memory_total_bytes` at the same instant; `load1`, `load5`, `load15`; `network_rx_bytes_per_sec` and `network_tx_bytes_per_sec`; and, per mount, `disk_used_bytes` and `disk_total_bytes` keyed by `mount.mount_path`. A minimal Report is 8 rows, one mount is 10, two mounts are 12.
- **crates/platpulse-server/src/http/report_ingestion.rs:910 `async fn save_metric_sample(tx, history: &crate::capacity::HistoryGate, scope: &SeriesScope<'_>, observed_at, received_at, value)`** is the single writer for both scopes — "a Host series is the same evidence as a Node series. The scope selects the tables, the column that names the owner, and whether the series identity carries a dimension" (:889-909). It writes the raw row, accumulates the bucket and advances the series ledger inside the transaction that accepted the Report, so a Report can never be half-stored; the Host loop calls it at :1163-1167.
- Nothing copies Host rows for a Node view: the Node read path resolves the Agent and reads the same table, so the "collected once, referenced by every Node" rule in AGENTS.md is enforced by the store rather than by convention, and it is the reason the WebUI panels can say the same series answers on sibling Nodes.
- The low-space path is unchanged in shape and now records the loss per mount path: under a pause the sample is not written and the gap row is written instead, in the same transaction (crates/platpulse-server/src/http/report_ingestion.rs:889-909; design §11.4, issue #212).
- Retention is read inside that same transaction (crates/platpulse-server/src/http/report_ingestion.rs:882 `metric_window_cutoff`), so no policy edit can land between the decision to keep a sample and the sample it classifies.

### Read path: two Owner routes over one shared series

- **`GET /api/admin/v1/agents/{agent_id}/metric-history`** (crates/platpulse-server/src/http/admin.rs:4617, handler :4637) answers the Agent's Host series: the metric is filtered by `crate::metric_history::is_host_metric` (:4654) and anything else is `400 invalid_metric` "metric is not a stored host metric series"; the owner is checked against the `agents` row by `host_owner_exists` (:4664, :4785); `dimension` defaults to `""` (:4668); the built scope is `SeriesScope::host` (:4674) and the answer identity is `scope_kind: "host"`, `scope_key: agent_id`, `node_id: None`, `dimension` (:4675-4680).
- **`GET /api/admin/v1/nodes/{node_id}/host-metric-history`** (crates/platpulse-server/src/http/admin.rs:4687, handler :4707) answers the same series seen from a Node page: it resolves the owner with `sqlx::query_scalar::<_, String>("SELECT agent_id FROM nodes WHERE node_id=?")` (:4739), answers `404 not_found` when the Node does not exist and `503 unavailable` when the lookup itself fails, filters the metric with `is_host_metric` (:4724) and echoes `node_id: Some(node_id)` with `scope_kind: "host"`, `scope_key: agent_id` (:4755-4758). The Node page is told whose machine it is reading, which is what makes a shared series honest on a page that does not own it.
- The Node Process route is untouched: crates/platpulse-server/src/http/admin.rs:4537, handler :4556, identity `scope_kind: "node"` at :4605-4608. The two kinds refuse each other's metrics, so neither can be read through the other's contract.
- All three routes share one answer function, `metric_history_response` (crates/platpulse-server/src/http/admin.rs:4845, taking a `SeriesScope<'_>` at :4849 and the `MetricHistoryIdentity` at :4850), whose doc says "all three read the same engine, clamp the range the same way and state the same evidence (design §11.4, §11.6)"; the identity struct itself is :4829-4840 with the dimension documented as "the mount path of a Host storage series, empty for every series that exists once per owner", and the answer echoes it at :5079.
- Query parameters are the #214 set for both Host routes — `metric`, `dimension`, `from`, `to`, `before`, `limit` (1..20000) — and an unparsable query is `400 invalid_query` (crates/platpulse-server/src/http/admin.rs:4766 `metric_history_params`, "query is not valid for metric history"). Router registrations sit together at :7068 (`/nodes/{node_id}/metric-history`), :7075 (`/nodes/{node_id}/host-metric-history`) and :7079 (`/agents/{agent_id}/metric-history`).
- **An unknown dimension is not an error.** A mount path nobody ever reported answers `200` with no `items` and `series.observed = false`, because "this mount path was never observed" is a fact about a series rather than a bad request; an unparsable range is `400 invalid_history_range`, and `not_found` / `auth_required` / `owner_required` / `503` keep the meanings they had on the Node route.

### Retention, cleanup and the shared ledger

- **crates/platpulse-server/src/retention.rs:209-214** gives the existing `raw_metric_sample` family its Host target: `DELETE FROM host_metric_samples WHERE rowid IN (SELECT rowid FROM host_metric_samples WHERE observed_at < ? ORDER BY observed_at, agent_id, metric LIMIT 512)`. The comment above it (:196-201) states the sizing reason: the Host table "states every collected Host series, and the two per-mount series alone make that 8 + 2 x mounts, so the ordinary batch would lag a fully mounted Host."
- **`HOST_METRIC_CLEANUP_BATCH: i64 = 512`** (:218) with a compile-time assertion at :224-229 that it covers one maximal Report — `HOST_METRIC_SERIES.len() + 2 * MAX_HOST_MOUNTS` (10 + 2 x 128 = 266), message "the per-Report Host sample batch must cover one maximal Report" — and the aggregate batch `AGGREGATE_CLEANUP_BATCH: i64 = 2048` (:241) keeps its original Node assertion (:246-249) and gains the same-shaped one for Host (:250-255, "the per-Report Host aggregate batch must cover one maximal Host Report"). The bounds are therefore checked when the crate is compiled, not when a Host is fully mounted in production.
- **No new retention family.** The Host tables are cleaned by the families Node already uses: `raw_metric_sample` for samples, and the two aggregate targets for buckets (crates/platpulse-server/src/retention.rs:274-277 grain 60 with `LIMIT 2048`, :293-296 grain 300 with `LIMIT 2048`). A separate Host family would have had to rebuild the `retention_policies` family CHECK (the reason #214 had to rebuild it for its tiers) and would have given an Owner two settings that mean the same window.
- **crates/platpulse-server/src/retention.rs:326 `HOST_RAW_METRIC_RELEASED_BEFORE_SQL`** advances `host_metric_series_state.released_before` from the same materialized expiry CTE the delete uses, joined on `(agent_id, metric, dimension)`, so an expired sample leaves the count of what the series observed behind it and a releasable stretch is never inferred from an absence.
- The series ledgers are deliberately not cleanup targets (crates/platpulse-server/src/retention.rs:780-790): they are what makes "what a series observed stays knowable after the samples themselves expire" true for the Host scope as well.
- A family with no policy row falls back to `catalog_family(FAMILY_RAW_METRIC_SAMPLE).default_days` (or `MIN_INVESTIGATION_RAW_DAYS`), and a keep-forever policy (days <= 0) releases nothing — the Host samples inherit the 24 hour floor from the same catalog entry the Node samples use.

### The Purge boundary

- **crates/platpulse-server/src/node_purge.rs** removes Node-owned rows only: `node_metric_samples`, `node_metric_series_state` and `node_metric_aggregates` are counted at :223-225 and deleted at :345-347, alongside the Node-scoped rows of `capacity_skipped_series`, which are selected through `NODE_SCOPED_ROWS = "scope_kind = 'node' AND scope_key = ?"` (:259) and deleted at :355-359.
- The Host tables are not referenced anywhere in that file: they are Agent-owned and disappear with the Agent through `ON DELETE CASCADE` (crates/platpulse-server/migrations/0068_host_metric_history.sql:44-45). The purge's own doc lists the class: "Shared Agent/Host/Network/Validator tables, Alert Incidents, Notification Events, Audit, and immutable Agent Report receipts are not referenced here." (:303-314)
- The one place a Host-adjacent table is touched carries its reason in the comment (:355-359): "Gap evidence recorded under low-space protection is Node-owned monitoring history too: a purged Node must not keep appearing in the Operations capacity surface (issue #212). Host and interval rows are shared evidence and stay."
- So purging one Node cannot delete evidence its sibling Nodes still read — the test `purging_one_node_keeps_the_host_series_every_node_of_the_agent_shares` (crates/platpulse-server/tests/host_metric_history.rs:1198) is the executable form of that sentence.

## The Admin contract

- Three routes over one engine, and the scope is stated in every answer: `GET /api/admin/v1/nodes/{node_id}/metric-history` (`scope_kind = "node"`, `scope_key = node_id`, `node_id` set, `dimension = ""`), `GET /api/admin/v1/agents/{agent_id}/metric-history` (`scope_kind = "host"`, `scope_key = agent_id`, `node_id = null`, `dimension`), and `GET /api/admin/v1/nodes/{node_id}/host-metric-history` (`scope_kind = "host"`, `scope_key = agent_id`, `node_id` set, `dimension`). The Node-Host route is the same series as the Agent route with the page that asked named in it — the server never re-labels shared evidence as Node-owned evidence.
- `dimension` is required only in the sense that a storage series cannot be identified without it: for every other Host series it defaults to the empty string (crates/platpulse-server/src/http/admin.rs:4668), and the OpenAPI parameter describes it as "Mount path of a Host storage series (disk_used_bytes, disk_total_bytes); empty for every other Host series". The Admin DTO does not list the mount paths an Agent has reported; the Operator names one (see WEB).
- Failure modes, unchanged in meaning from #213/#214 and applied to the Host routes: `400 invalid_query` (unparsable query, :4766), `400 invalid_history_range` (a range the engine refuses), `400 invalid_metric` (the other kind's series), `404 not_found` (unknown Agent, or a Node the Server does not know), `401 auth_required`, `403 owner_required`, `503 unavailable` (the database is unreachable). All three routes are Owner-only, served `no_store`, and echo the series' ledger state even when the window itself answers nothing.

## Guard instruments: the floors, the cardinality and the cleanup bounds

The ticket's acceptance asks for the new family's floors, its cardinality and its cleanup bound to be registered as evidence a run can fail on. Two instruments that already drive real Reports into a real Server over a temporary SQLite database now measure the Host family; no check in them reads a fixture or a constant alone.

## DECISIONS

- **Generalize the engine instead of writing a Host module.** `HistorySchema` (crates/platpulse-server/src/metric_history.rs:145) exists because the alternative was a second implementation of #213's counting rules, #214's tier boundaries and the gap judgement, which is exactly the parallel framework this ticket forbids; the scope now differs in three declared fields — tables, owner column, dimension — and every statement is one rendered template (crates/platpulse-server/src/metric_history.rs:190).
- **Add targets to the existing cleanup families instead of registering a Host family.** The Host samples are bounded by `raw_metric_sample` (crates/platpulse-server/src/retention.rs:209-214) and the Host buckets by the two aggregate families (:274-277, :293-296). A new family means rebuilding the `retention_policies` family CHECK — the migration #214 had to write for its own tiers — and would offer the Owner two settings that describe one window.
- **Size the Host batches by assertion, not by hope.** `HOST_METRIC_CLEANUP_BATCH = 512` (:218) and the aggregate batch of 2048 (:241) carry compile-time assertions that one maximal Report's rows fit in one pass (:224-229, :250-255), because a batch smaller than one Report's arrival is the backlog that produces the low-space pause this subsystem exists to avoid.
- **Identify a storage series by the mount path the Agent reported, never by a device identity.** Story 52's rule is in the migration comment and in both panels' copy: a path that moves to another filesystem starts a new series, and the Server never claims a stable physical device identity it cannot verify. The consequence is deliberate: a moved mount appears as a series that ends and another that begins, which is true, rather than one series whose values silently change meaning.
- **Put the dimension in the series key and in the pause ledger.** `host_metric_samples` (0068:62), `host_metric_series_state` (:96), `host_metric_aggregates` (:153) and `capacity_skipped_series` (:176) all key on the dimension, because one Report stating two mounts at one instant would otherwise overwrite itself, and a pause that skipped both mounts would otherwise report one merged number.
- **Store the collected quantity, never a Server-baked percentage.** The comment at crates/platpulse-server/migrations/0068_host_metric_history.sql:20-24 says why: the values are the collected bytes, percent, load and bytes per second, so a stored `memory_total_bytes` or `disk_total_bytes` can still re-derive the ratio that was true at that instant; baking a ratio at ingestion would freeze one comparison and lose the denominator. This is also why no Swap and no disk IO series were invented: the ticket stores what the Agent already collects, and neither is collected.
- **A route that answers shared evidence must name the owner of that evidence.** `scope_kind`/`scope_key` in the answer (crates/platpulse-server/src/http/admin.rs:4829-4840, echoed at :5079) and the "The Agent ... reports this Host once for every Node it observes" note in the panel are the same decision on the two sides of the wire: a Node page may show a series it does not own, but it may not imply ownership.
- **Ask the Operator for the mount path rather than widening the Admin DTO.** The Server's Host mount points are not exposed to the Admin client by design, so the panel asks for a typed value and reads nothing until it is non-empty, instead of inventing an owner-scoped inventory endpoint for one field of one series.
- **A Node's Purge keeps the shared evidence.** crates/platpulse-server/src/node_purge.rs:303-314, :345-347, :355-359 remove Node-owned rows and the Node-scoped pause rows only; deleting an Agent's Host series because one Node was purged would destroy evidence the Agent's other Nodes are still published from.

- **Extend the instrument that already measures a family instead of registering a new one.** The Host floors, cardinality and cleanup bounds went into scripts/capacity-baseline.py and scripts/metric-history-baseline.py because those two already plant Reports, pause the subsystem and read the routes back; scripts/release-qualification.py and scripts/final-release-qualification.py were left alone because the same bound asserted in a second place guards nothing new. The one declaration that had to be written down twice is the ten-name family: the instrument compares `DECLARED_HOST_FAMILY` with `HOST_METRICS + HOST_MOUNT_METRICS`, so a series added on the Server and forgotten in the instrument fails the run.
